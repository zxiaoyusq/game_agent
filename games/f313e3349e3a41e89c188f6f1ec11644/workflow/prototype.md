## 结论

按描述，捕获数值 prize 能修复广告返回时读取已切换场馆金额的问题；roundId 与原面板归属检查能缩小旧回调对新界面的影响。但它不是完整奖励事务：广告归属、奖励提交、持久化和界面导航仍是不同边界。不能据此认定不会丢奖励、不会重复领奖或存档可靠。

## 旧代码事实

1. _0x47e567 以 _carromResultCommitted 防止本轮结果创建重复。胜利时先增加一份基础 prize 并调用 _0x3a0318；广告成功再增加一份，因此正常总奖励为 2P，不应将广告增量误改为 2P。失败局没有该胜利广告分支。
2. 旧结果广告回调先移除面板、隐藏共享遮罩，再按成功布尔值增加当前 _0x408018 对应的 prize，然后进入原导航。面板已不存在也不能阻止其余操作。
3. _carromResolveAd 先检查广告代次与 resolved，再标记 resolved=true，取出共享 _0x38b273、清空槽，最后调用业务回调。同代次首次 true 或 false 消耗结果，后续均忽略。即使首次没有业务回调，也会标记完成。
4. _0x4d02b5 在没有 _0x420004 时直接返回，不通知失败；有展示入口时先清空入口、设置共享业务槽，再调用展示函数。
5. afterAd 在代次匹配时恢复声音和 ticker、重置共享状态、清空业务槽并尝试重新准备广告；重新准备是否创建新代次受 _0xcd5b2f 影响。它不先确保业务结果已经交付。
6. 展示函数异常时，若业务结果已 resolved，异常被重新抛出；否则走失败处理并在 finally 中按条件推进代次。准备异常会作废代次及展示入口，但未见向业务槽交付失败的保证。
7. _0x5480e3 重开递增 roundId；已读大厅、选台、商店切换函数没有递增 roundId。因此“同 round”不等于“仍在原结果场景”。
8. _0x3a0318 先同步内存存档对象，再逐键 JSON 序列化并写入 GameSnacks 存储，没有本地写异常处理、业务成功返回或事务回滚。不能从这里推断 SDK 实际持久化时机及原子性。
9. _0x51b412 的普通按钮在 pointerdown 发出 close；广告按钮发出 ad。结果广告入口中的 0x3d0 方法仅隐藏广告按钮，未见它禁用普通关闭按钮。不能把广告点击等同于整个面板锁定。

## 补丁边界与潜在副作用

### 金额捕获

必须捕获原始数值，例如 prizeValue，而非捕获可变 table 对象后延迟读取 table.prize。旧场馆 prize 为 50、125、400、1500、10000。结果时捕获意味着以后配置变化不会追溯改变承诺金额，通常符合玩家对 Claim x2 的期待；但它不修复结果创建之前场馆上下文已错误的情况。新增数值校验属于建议：金额应为有限、非负且符合币值约束的数值。

### 场景退出与旧面板

业务回调实际收到 true 后，即使已经关闭结果、回大厅或开始下一轮，按描述仍先给原金额并存档；随后不满足 UI 条件就停止。这是合理的“奖励归原请求，导航归当前视图”分离。不能把 round 检查提前到入账前，否则真实完成的跨局广告可能不给奖励。

需要注意同轮退出：旧面板可能仍挂在舞台上，或被隐藏、被其他弹层覆盖，roundId 仍相同。仅 parent===stage 不证明它是当前有效结果视图，也不证明共享遮罩属于它。应核对结果实例身份、视图生命周期/失效标志及遮罩所有权。若面板可以嵌套，parent===stage 又可能拒绝仍有效的结果；按实际层级定义检查。其他父节点不是可从 stage 直接 removeChild 的证明。

补丁仅保护广告返回路径；旧普通 close 监听、其他广告调用方和已启动的动画仍需单独审查。仅改变父子关系不等于清理监听、销毁对象或终止补间。是否存在资源泄漏需运行证据。

### 回调重入与重复

同广告代次，resolved 在业务回调前置位、共享槽先清空，能阻止业务回调执行期间再次进入同代次 true/false 导致重复加币，也不会在回调返回后无条件清空一个新业务槽。这是已有有效保护。

但保护范围是一次广告准备代次，不是一个结果的奖励权利。若同一结果重新绑定到新广告代次并再次成功，旧 resolved 不阻止再次加币；_carromResultCommitted 只管结果创建。是否可达取决于新版入口与面板状态，不能认定已发生。需要结果级 rewardId/已领取状态，且先提交再执行可重入的外部操作。异步持久化或存储适配层若会重入，还需在其返回后重新检查 UI 身份。

### 共享广告回调槽与跨代次

_0x38b273 是所有相关广告调用共享的单槽，代次过滤只排除旧代次事件，不能证明当前槽属于当前广告的请求者。新准备发生在旧广告未结束时，可能使旧真实成功被代次检查丢弃；若另一调用取得展示入口，槽又可能归另一业务。单次双击通常因为展示入口已清空而被拦住，不能据此说所有并发都安全或所有并发必然串奖。

关键反例：A 正在等待奖励；若 afterAd 先到，它清空 A 槽并可能创建新代次；之后 A 的 adViewed 即使代表真实成功，也可能无槽可调或因代次过期被忽略。另一反例是在 _0x5480e3 内调用 _0x2e33a4 时，若可准备标志为 false，会推进代次，令旧成功失效。因此“业务回调收到 true 就跨局入账”不等于“跨局真实成功一定送达业务回调”。

建议按 requestId/广告实例保存不可变 callback、roundId、prize 与领取权利；待处理期间拒绝或排队新请求；广告展示生命周期与奖励生命周期分别结算。没有 SDK 事件关联信息时，本地不能凭空恢复真实归属。

### 失败、重复、乱序

旧逻辑为首个终结事件获胜：true→false 保留成功，false→true 保留失败，true→true 只交付一次；afterAd 不是奖励成功事件。若 SDK 把某个 false 事件定义为非终结或允许随后有效成功，旧策略可能漏奖；若 SDK 定义首个终结为最终结果，该行为可能正确。当前没有合同证据，不选择其中一种当事实。

按补丁描述，false 不加广告增量，但 UI 条件成立时仍进入原导航；胜利基础 P 保留。若希望失败留在结果页重试，这是另一项产品变更，不能当作补丁已包含。无展示入口、只收到 afterAd、一直无回调都可能没有业务结束通知；当前面板广告按钮已隐藏，普通关闭仍可能是退路，不能笼统称为所有输入死锁。

### 保存异常与事务

补丁先加金币再保存，再执行 UI 条件检查。若保存同步抛错：内存已加 P，存档可能完全未写或部分写入，后续 UI 操作不执行；resolver 已完成，重复 true 不会重试保存。因 coins 在旧对象声明中位于多个其他键之后，某个前置键写失败也可能使金币键根本未尝试。若金币键写成功后其他键失败，也不能声称“奖励未存入”。

内存显示增加、重载后回退，或奖励已保存但面板残留，都可能发生；不能盲目再加币重试，也不能在部分写后简单回滚余额，否则持久与内存可能分叉。业务回调同步抛错还可能沿展示/准备的 catch 路径传播并被误记为广告不可用，具体取决于注入事件的调用栈。

应给奖励提交独立幂等键，记录领取与余额的一致持久状态；失败保留待保存信息并显式提示，重试只保存已提交状态，不再次加币。若持久接口返回 Promise 或异步确认，必须按其真实契约等待；旧函数未等待并不证明异步写入完成。仅有逐键存储时不能承诺跨键原子、跨刷新恰好一次或跨设备一致性。

### 用户期待与 UI 更新时机

玩家看到 Claim x2，一般期待基础 P 已保留、广告有效成功后再得 P，退出结果页不取消已兑现的观看权利，失败不扣基础奖励。建议反馈使用英文，例如 Reward added、Reward could not be saved. Retrying.，但本次不新增界面。

补丁绕过旧导航后，当前大厅/选台/商店的金币显示及可购买状态未必刷新：内存已更新并不代表旧 setCoins 缓存同步更新。应通过统一余额通知刷新当前有效视图及购买资格，不借旧导航强制跳页。保存失败应区分“内存奖励已记入，尚未持久化”与“未获得奖励”，仅真实保存成功清除错误提示。

保留原导航仍会从结果创建前余额 _0xe6d291 播到回调时余额。若期间另有消费、入场费或奖励，动画可能把全部差额误呈现为本次广告所得，甚至呈现下降。它是表现，不应写回真实余额。旧补间启动时捕获目标余额，期间再有变动或离开场景，旧 onUpdate 仍可能覆盖显示；需要余额版本、视图生命周期检查和取消旧动画。动画终值应重新对齐当前余额，旧失败路径也可能播放基础奖励动画，不代表广告成功。

## 建议状态与验收契约

本次不重新定义物理玩法、碰撞、步长或输赢；它们不影响当前奖励事务审查。金币断言使用整数精确相等，允许误差为 0；事件由测试控制，不以真实广告等待时间推断状态。

审查状态拆分：结果上下文 {roundId, resultId, prizeValue}；广告请求 {requestId, adGeneration, callbackOwner, lifecycleState}；奖励 {rewardId, pending/committed/persistPending/persisted/failed}；视图 {instance, sceneEpoch, active, maskOwner}。这是后续设计建议，不是旧代码已实现事实。核心循环为结果创建并提交基础奖励 → 请求广告 → 按关联事件确定广告增量 → 幂等提交与保存 → 刷新当前余额 → 仅对仍有效的原结果执行一次导航。

成功条件：每个有效领取权利最多加一次正确增量，跨局有效成功按请求归属入账，失败不加增量，失效视图不被修改，保存失败可见且恢复不重复加币。无结果事件不应伪装成功。输入窗口需明确广告等待时普通关闭是否允许；旧代码不能证明全锁定。
