## 3. 静态可见：选择规则与反例

定义 P(t) 为 `t` 为真值且 `t.valid` 为真值、`t.width > 1`、`t.height > 1`。以下是在 PIXI 全局、缓存和属性读取正常、没有 getter 异常的前提下，从 E-01 推导的结果；不是执行日志。

| 目标 P(texture) | fallback P(bg_0) | 返回值 |
|---|---|---|
| 真 | 不读取 fallback | 原目标对象 |
| 假 | 真 | bg_0 对象 |
| 假 | 假 | 原目标对象，可能无效或 undefined/null |

静态可以确定：

1. 正常目标优先，即使 bg_0 可用也不替换目标；函数本身没有加载、重试、缓存写入或销毁操作。
2. 过滤的是任一维度不大于 1，而不只是严格的 1x1。因此正常但为 1xN、Nx1 的背景也会被回退；若这些资源被有意拉伸使用，候选会改变原行为。摘要“只在无效或 1x1”与代码门槛不完全一致。
3. 两者都不合格时仍返回原目标，不是返回 bg_0、不保证返回空纹理或可用纹理。目标缺失且 fallback 缺失时可返回 undefined。
4. key 为 bg_0 时没有第二级替代；同一对象失败后仍返回该对象。目标和 bg_0 若为同一对象或共享失效 BaseTexture，也不能形成可靠冗余。
5. 不对 `valid` 做严格布尔检查，不做类型检查、尺寸有限性检查、销毁状态检查、基纹理检查或异常捕获。错误缓存对象也可能通过门槛；调用方应证明缓存确为对应版本的 Texture 对象。
6. 参数 key 缺失/错误、PIXI 未初始化、`PIXI.utils.TextureCache` 不存在、访问属性抛错，都不是本函数处理的失败域。真实 API 是否位于该路径需按已加载版本核验。

因此，“始终得到安全背景”的强断言在逻辑上为 **FAIL**（上述两者都失败即构成条件反例）；“当前工程是否实际遇到该反例”仍为未知。

## 4. PIXI 纹理语义与风险

### 4.1 空纹理、帧尺寸与基纹理尺寸

- `texture.valid` 和 `texture.width/height` 的含义要以实际运行的 PIXI 版本实现为准；不能用其他主版本文档替代当前 runtime。
- Texture 的逻辑尺寸、frame/orig、trim、rotate、BaseTexture 的逻辑/实际像素尺寸及 resolution 并不一定相同。大图集上的小帧可能被拒绝；逻辑尺寸大于 1 的纹理不等于底层图像已加载且 GPU 可用。
- 不能仅从“1x1”认定就是 `PIXI.Texture.EMPTY`，也不能认定 EMPTY 必然通过或必然被拒绝；WHITE 等内置占位也不能仅靠名称或颜色识别。应记录对象身份与真实字段。放大的透明/纯色占位可能通过门槛，正确的细条纹理反而可能被拒绝。
- HTTP 404 与缓存状态没有固定一一映射：可能无条目、仍持有上次成功对象、留下无效占位或由既有加载器映射成其他对象。函数不读取 HTTP 状态。
- 宽高与 valid 合格也不能证明视觉正确：透明像素、错误 atlas frame、tint、alpha、遮罩、层级、容器背景或裁切都可能决定最终画面。绿色转述不能单独证明 bg_0 被选中，更不能证明 Golden 美术正确。

### 4.2 fallback 也失败、被销毁纹理

- 无效目标最终仍可能送往 Sprite。调用方式和版本不同，undefined、失效纹理可能表现为空白、保留旧值、默认纹理或异常；本轮不指定一种为已发生结果。
- 函数没有检查销毁标记或 `baseTexture` 是否存在/被销毁。部分版本销毁会使 getter 所需字段失效；读取 width/height 可能抛错。valid 的短路有时避免读取尺寸，但不能据此保证所有生命周期情况安全。
- bg_0 是共享缓存资源时，旧场景执行深度销毁/清缓存是否影响新场景，需要查资源 owner 和销毁参数。候选返回的是原对象引用，没有克隆、引用计数或资源保活。
- 即使调用时通过检查，后续异步销毁、上下文丢失或资源释放仍可能使它失效；选择时检查不提供持续有效性保证。

### 4.3 资源恢复

函数只在被调用时重查缓存，未订阅加载成功或恢复事件。应分别验证：

- 目标对象原地恢复，但 Sprite 已被赋值为 bg_0：目标恢复不会由该函数自动把 Sprite 切回目标。
- 目标在缓存中被新对象替换：已持有旧对象或 bg_0 的 Sprite 不会因为缓存替换就自动重新选择。
- 两者初始失败，Sprite 恰好持有后来原地变为有效的目标：某些版本的更新机制可能刷新画面，但必须验证赋值和更新监听链。
- 后续切场馆或重入若真正再次调用函数，可重新选择恢复后的目标；是否还有“相同场馆跳过更新”等短路未知。

验收前应明确产品恢复策略是“本场保持 fallback，下一稳定边界重选”还是“本场允许自动恢复”。这不是本轮已确认设计；也不能把缺少热恢复直接定性为违反现有产品要求。

## 5. 旧局、重入、背景映射与入口差异

- E-01 无局号、场馆 ID、异步回调或状态写入，不能证明旧局隔离；E-02 也不能证明所有直接缓存读取均被替换。
- 检查初始化、场馆切换、匹配开始/取消、对局创建、重开、退出再进、断线重连、前后台恢复各自的背景 owner 和最终赋值点。异步完成应只影响仍有效的场景/局代，不应由旧请求覆盖新场馆。
- 快速 A→B→A 时，晚到的 B 回调、缓存替换或旧 Sprite 销毁均可能影响结果。函数本身没有新增异步，因此不能把竞态归因为该函数，也不能宣布原竞态被解决。
- 匹配页和对局页可能有不同 key、资源组、缩放和背景容器。允许两页背景不同不等于缺陷；都绿也不等于映射正确。需分别记录期望 key、实际返回身份和 Sprite 身份，不把匹配页截图作为对局验收。
- 独立页面、开发入口、生产 CDN 与宿主 WebView 可能使用不同打包副本、PIXI 版本、相对路径、缓存预热、Service Worker、资源桥接和上下文恢复机制。以实际入口的构建标识、脚本/资源哈希和已加载 runtime 取证。桌面候选证据即使补齐，也不能替代手机或宿主验收。

## 6. 性能判断边界

静态上，每次选择是常数数量的缓存查找与属性读取；目标合格时不查 bg_0。函数体没有显式分配图片、发网络请求、遍历资源、复制纹理或循环。相比直接取缓存，它增加了若干分支和 getter 读取。

不能据此写“零开销”、FPS 不变、包体下降、加载更快或内存优化。调用频率、getter 实现、赋值后尺寸重算、渲染批次、纹理上传、bg_0 保留期及 GPU 内存均未知。若只在初始化/切场馆调用，逻辑开销预计较小，但这是待测预期；若误接到逐帧路径则需另外测量。

候选不改 preload，所以不能保证避免 Golden 的 404 请求、失败超时或加载器启动阻塞。若 preload 失败使初始化根本不发生，候选也无机会生效。
