# Carrom 开球证据缺口定点复核：正式静态报告

## 1. 结论与范围

阶段：原型定义；交付性质：只读静态证据复核，不是游戏原型实现。用户明确要求仅复核 `0x18b2e38` 的输入输出、调用链及 `shotPowerLimits` 是否连接。本轮不新增玩法、界面、资源或运行时参数，不进入美术、代码或测试阶段。

**核心结论：**

1. **PASS（补充片段的指令级结论）**：`0x18b2e38` 读取两个双精度浮点输入 `d0/d1`；输入比较相等时直接返回原 `d0`，不读取或更新 `x0` 指向的状态。不相等路径读取并改写 `[x0]` 的64位状态，随后计算浮点插值并在 `d0` 返回结果。
2. **PASS（补充片段的局部调用边）**：`0x18b9fd0`、`0x18ba01c` 两条 `BL` 的编码目标均为 `0x18b2e38`。第二次调用前，将两个对象字段 `+0x20/+0x28` 的64位浮点值传入 `d0/d1`，将 `0x32c89e8` 传入 `x0`。
3. **NEEDS_CONTEXT（数据流未闭合）**：没有证据证明上述对象与原ZIP中 `0x18b09d4` 构造的配置结果是同一对象；没有提供 `0x18b3620/0x18b38a8` 的函数体。因此，**不能声称 `shotPowerLimits → 0x18b2e38` 已连接，也不能反向声称绝无连接**。
4. **字段关联成立但别名缺失**：原ZIP中 `shotPowerLimits` 查询候选序列，沿局部指令流进入输出 `+0x20/+0x28` 的64位浮点候选字段；这与补充调用方读取的偏移及类型相符，支持连接候选。**相同字段偏移不能替代对象别名证明**。`+0x50/+0x54` 的32位字段来自后续另一项查询，不是该处shotPowerLimits序列。

复核更正：前一条进度消息及初稿将这两组字段来源倒置；最终逐次跟踪临时容器初始化后已纠正。`18b0b24`复制到sp+0x50的是shotPowerLimits序列，`18b0bf8`另行初始化x29-0x30的是后续查询序列，两者不应混同。
5. **NEEDS_CONTEXT（业务身份未证实）**：标称 `0x18b9d34` 的调用方只给出中间节选，没有入口、开球分支条件或业务owner证据。不能将目标函数命名为“对手开球策略”，也不能证明它只用于开球、机器人或对手。

全部结论是提供材料的静态解读。没有执行原生库、模拟器、真机、浏览器或动态采样；没有测得任何力度、角度、随机分布或实际成功率。

### 5.1 可证的整数和浮点结构

以 `U64` 表示64位无符号回绕，以 `hi(u*v)` 表示无符号128位乘积的高64位。以下是指令语义的整理，不是执行结果：

- `p = U64(oldState * 0xbc8f)`。
- `h = hi(p * 0x200000005)`。
- `q = U64(h + (U64(p-h) >> 1)) >> 30`。
- `r1 = U64(p + U64(q - U64(q << 31)))`。
- `p2 = U64(r1 * 0xbc8f)`。
- `q2 = hi(p2 * 0x800000010001) >> 14`。
- `r2 = U64(p2 + U64(q2 - U64(q2 << 31)))`；写回 `[statePtr]=r2`。
- 将 `U64(r1-1)`、`U64(r2-1)` 分别无符号转换为double。
- 设 `K4` 为 `0x12ea3d8` 的double，`K3` 为 `0x12ea4e0` 的double；`alpha = FMA(double(U64(r2-1)), K4, double(U64(r1-1))) / K3`。
- 对正常有序浮点输入，第二次比较 `FCMP b,a` 后，FCSEL构成 `base=min(a,b)`、`top=max(a,b)`；返回 `FMA(top-base, alpha, base)`。

**推断边界：**该形态与有状态伪随机区间插值相容，但缺常量原始值、状态取值约束与owner，不能证明 `alpha∈[0,1]`、输出一定落在输入区间、均匀分布、特定随机库或标准LCG身份。不能把常数加载地址当常数值，也不把除法替换成未经证明的归一化常数。FMADD、浮点舍入及FP环境影响保留，不能声称跨平台位级复现。

NaN使首次比较无序并走NE路径；无序时不能继续用min/max描述FCSEL结果。相等无穷值可以走早返回；非相等无穷、NaN等没有显式有限数过滤。目标没有证实状态指针非空检查，调用方需满足怎样的前置条件未知。

## 7. shotPowerLimits是否连接：逐段复核

### 7.1 原ZIP中的读取和输出候选

依据E-03/E-04：

1. `0x18b0a64/68` 将 `0x11cc3f0`（E-03标记字符串 `shotPowerLimits`）放入x1。该两条之间没有改写x1，局部引用成立。
2. `0x18b0a70` 调 `0x18ab3d4` 准备临时对象；`0x18b0a74–80` 把服务对象+0x40、临时对象及原x0保存值x20传给 `0x26c1074`。按调用模式可称“配置查询候选”，不能恢复未知被调用函数的正式类型或契约。
3. `0x18b0a84–94` 检查返回对象+8的标签是否为4；相符选其首字，否则选回退指针。`0x18b0aa4–ac` 使用x8输出区调用 `0x26e630c`；随后检查标签5，选择候选序列或回退空容器。
4. `0x18b0b14–24` 将候选序列按16字节元素跨度复制至 `sp+0x50`。随后其它查询并未改变此局部序列来源。
5. `0x18b0f88` 从 `sp+0x50` 取该序列首元素指针，`0x18b0f8c` 调 `0x2706e20`，`0x18b0f90` 将d0写到输出 `+0x20`。`0x18b0f98–a0` 取同序列下一16字节元素并转换，`0x18b0fa4` 将d0写到输出 `+0x28`。因此这两字段与shotPowerLimits查询候选存在可追踪的局部数据流；转换函数体未提供，具体缺省与异常行为仍未知。
6. 输出指针在入口 `0x18b09f8` 保存自x8到x19；这是结构体间接返回/输出缓冲区的ABI候选。调用方E-06也确实将栈缓冲区传入x8并拷贝结果。不能因此把字段名称全部恢复。

对照：`0x18b0b38/3c` 准备另一键 `0x11457c0`；`0x18b0b54` 查询，`0x18b0b78–80` 将候选值转到x29-0x50，`0x18b0be0–f8` 初始化并复制到另一容器x29-0x30。`0x18b1068–84` 从该容器两元素转换s0并写入输出 `+0x50/+0x54`。**它并非从sp+0x50复制**。更早首次查询结果x22（键 `0x122e53e`）在 `0x18b0f04` 才转入sp+0x78并用于输出+8的容器；不能把它与shotPowerLimits来源混同。上述另两键名本轮未取得。

### 7.2 原ZIP中的上游分支

依据E-05/E-06：

- `0x18b335c` 读查询结果x21的 `+0x18`；`0x18b3360 CBZ` 决定分支。
- 非零路径：x0=x21、x1=x20、x8=sp+0x38；`0x18b3374 BL 0x18b09d4`。
