## 3. 新旧保存与异常边界

### 3.1 实际关键源码

旧版 E1：

```js
function _0x3a0318() {
  var _0x1a3450 = _0x157421;
  _0x9b0cd();
  for (let _0x2f6f95 in _0x23207e) {
    GameSnacks[_0x1a3450(0x3e5)][_0x1a3450(0x1cc)](
      _0x2f6f95,
      JSON[_0x1a3450(0x23a)](_0x23207e[_0x2f6f95]),
    );
  }
}
```

新版 E1：

```js
function _0x3a0318() {
  var _0x1a3450 = _0x157421;
  _0x9b0cd();
  for (let _0x2f6f95 in _0x23207e) {
    try {
      GameSnacks[_0x1a3450(0x3e5)][_0x1a3450(0x1cc)](
        _0x2f6f95,
        JSON[_0x1a3450(0x23a)](_0x23207e[_0x2f6f95]),
      );
    } catch (_) { console.warn('Carrom save write failed:', _0x2f6f95); }
  }

```

本文将 `0x3e5/0x1cc/0x492/0x23a` 按使用语义称为 storage/setItem/getItem/stringify；尾部表及空方法声明提供支持，但未运行旋转解码，故不把所有数字映射当作动态验证结果。coins/tutorial/lastRewardTime、tables/upgrades/strikers/stones 则有平行字面字段对应。

### 3.2 哪些异常被隔离

| 情况 | 旧版 | 新版 | 限制 |
|---|---|---|---|
| 某字段同步序列化或写调用抛错 | 立即向 caller 传播，后续字段不尝试 | warn 该 key；logger 正常时继续后续字段 | 已成功写入的字段不回滚 |
| storage 缺失、属性 getter 或方法调用同步抛错 | 传播 | 位于 try 中的求值异常可捕获；可能每个 key 都失败 | 方法引用先于参数求值，不能假定失败字段已经完成 stringify |
| `_0x9b0cd` 同步期间抛错 | 传播 | 仍传播 | 本次字段写循环未开始；共享对象可能已部分更新 |
| catch 内 console.warn 抛错或 console 不可用 | 不适用新增 logger | 逃逸并中断循环 | 日志不是受保护的兜底 |
| 返回 rejected Promise 或稍后发生的 callback 错误 | 本保存函数不消费 | 仍不消费 | 无 await/then/catch；不能将晚到异常归入此同步 catch |
| 返回 false、错误码、undefined 或内部吞错 | 无结果检查 | 仍无结果检查 | 不抛错就没有失败日志；返回值不构成持久化确认 |
| 写入完成后方法又同步抛错 | caller 见异常 | 记录 key 后继续 | “记录失败”也不等于“该 key 没写进去” |

七字段都同步失败且 logger 正常时，新版依然可能正常返回 undefined。这不是“保存成功”。for..in 的枚举本身不在 try 内；若以后改成异常 Proxy，枚举失败也不受字段 catch 保护。当前正常对象无需据此宣称必现故障。

### 3.3 序列化失败与不抛错失真

循环引用、默认不支持的 BigInt、抛错的 toJSON、序列化访问 getter 抛错，均可能导致该字段同步失败，后续字段继续尝试。正常七字段主要是数值、布尔和字符串/数值数组；这些异常是故障注入或数据破坏条件，不是已证明的正常游戏必现路径。

另外必须区别不抛错的转换：NaN/Infinity 会变成 null；顶层 undefined/function/symbol 可使 stringify 返回 undefined；对象内部分值会被省略，数组内对应值可能变成 null。新增 catch 不会发现这些失真。适配器接受 undefined、拒绝、转换成字符串还是静默丢弃，需要按实际契约测试。

## 4. 字段一致性、共享状态与重入

`_0x23207e` 声明字段顺序为 tables（5）、upgrades（9）、strikers（9）、stones（9）、coins、tutorial、lastRewardTime。通常的普通对象遍历按此顺序，但代码使用 for..in，没有 own-property 过滤，继承的可枚举字段也可能被写。不能把一般顺序当适配器的异步提交顺序。

E2 中 `_0x9b0cd` 先复制金币、教程、时间，然后逐项写 tables、strikers 状态及 upgrades、stones 状态。它是共享可变对象同步，不是独立不可变深快照。它没有版本号、提交记录、事务标识或失败 key 集合。

- 部分成功产生新旧字段混合。新版“更多 key 继续写入”不是“一起成功”。全字段重写也不是事务。
- 当前状态仍在内存，并不等于失败字段或待重试数据被**持久化保留**。未来另一次保存可能再次尝试当时状态，但没有失败队列或本次交易重试保证。
- 单线程不能排除同步重入：适配器 getter/setItem、toJSON 或 logger 可以同步调用保存，或变更 owner 状态。内层同步会覆盖同一个 `_0x23207e`，外层可能保存前半旧代、后半新代；无限递归也有可能。此处没有保存级锁。
- 普通异步回调通常不会插入同一连续同步栈，但异步适配器内部提交可能跨两次 save 乱序，导致旧写晚到覆盖新值。是否存在这种实现未知，属于条件性测试项。
- `_carromArenaEntryPending`、`_carromResultCommitted`、bonusGranted、match timer/ad token 等分别限制入场、结算或局生命周期，不等于通用保存锁或跨重启幂等机制。

## 5. 调用方、金币、教程和装备

### 5.1 调用方依赖异常的变化

“依赖”在此区分为控制流受抛错影响，和显式 catch 的错误反馈；没有证据证明所有 caller 主观上把抛错设计成保存确认协议。

- E5 入场 `_0x4d0a10` 有内层 save catch，旧版该处本来就会保存抛错后继续，不是新增 catch 才允许入场。新版吞掉字段错后，caller 的 `Carrom arena entry save failed` 通常不再触发，变成统一 key 警告。
- E6 教程完成包装、E8 翻倍奖励包装的 catch 同样不再看见已被保存函数消费的字段异常；快照或 logger 异常仍可能到达它们。
- E7 转盘基础奖励及翻倍回调、E8 胜利基础奖励、E9 商店中的直接保存调用，旧版同步异常可能中断保存之后的 UI/后续语句；新版通常续行。这改善流程，但也可能向玩家展示完成而实际保存不全。
- 没有保存成功汇总、返回状态或玩家可见失败反馈。警告只包含 key，丢弃原始 exception；配额不足、序列化失败、缺方法等原因不能靠该日志区分。

## 6. 宿主、本地适配器与恢复

### 宿主 GameSnacks

保存调用走 GameSnacks 对象，并未在此处声明真实 SDK 版本、持久化时机或同步/异步契约。同步抛错、结果码、Promise、内部缓存及页面关闭时提交，必须依据实际宿主取证。不能只因名称是 GameSnacks 就声称宿主落盘成功或永不抛错。

### 本地 CarromLocalSave

E3 读取每字段时仅在 getItem 结果 truthy 时调用 `window.CarromLocalSave.recover(value, default, key, upgradeDefaults)`；读 catch 后 `_0x13b722` 直接恢复 coins/tutorial，Number 转换时间和 upgrades，按 equiped 恢复索引及物品状态。读循环隔离不保护最后运行态恢复；畸形数组/类型仍可能在恢复阶段出问题。

两版相关读取逻辑相同。**recover 的实现没有提供，不能称其能修复金币与购买/奖励的跨字段交易一致性。** 单字段类型合法，也可能组合成不一致交易。

E4 的 resume 可选调用 `CarromLocalSave.flush()`，外层 try/catch 为空。这里只能证明有调用入口：没有 dirty 队列、持久化失败 key、重试和 flush 成功契约证据。若 flush 返回 Promise，此处同步 catch 也不能据此证明已消费其拒绝。

### 空备用对象

E10 `_0x434610` 明确存在如下方法体：

```js
getItem: function () {},
setItem: function () {},
removeItem: function () {},
clear: function () {},
```

这是“不抛错而不保存”的直接代码例子，不是 localStorage 实现。其在实际启动中是否选中、是否被其他脚本替换尚未确认，不把它说成用户设备当前正在使用的适配器。

如真实本地适配器使用 localStorage，quota/security 等通常可形成同步异常；如先写内存缓存后 flush，正常返回可能只是入队。两者不能混为一个保证。输入未含本地适配器安装、选择条件、配套 HTML 和宿主部署配置。

| T13 | 畸形读取值、truthy/falsy、recover 异常、畸形恢复数组 | 区分读取隔离与 catch 外 `_0x13b722` 异常；验证 schema 与交易组合，不能仅证明 JSON 能 parse |

**判定口径：**

1. 字段隔离能力验收要求 T01/T03 的控制流与 E1 边界一致；不是要求 B 永不抛错。
2. 金币、购买、升级和奖励交易的一致性容差为 **0 个交易错配**，不能用 UI 顺畅或浮点误差容忍来掩盖存档分裂。若产品只接受尽力写入，应明确展示其限制，而不是以此通过“可靠保存”验收。
3. “持久化成功”必须有适配器契约下的确认及关闭后重读证据；“原子性”必须有整笔提交/恢复证据。当前实现不满足这两种声明，不能给它们静态 PASS。
4. 警告需能够区分字段和原始失败类型；是否增加玩家可见提示、重试/阻断属于后续产品与代码决策，本轮未实施。

## 8. 原型阶段的玩法/界面约束与参考取舍

本任务不重定义 Carrom 规则或制作可玩原型。相关状态链为：初始化读/恢复 → 大厅（教程、转盘、商店）→ 入场扣费 → 对局射击 → 胜负结算/广告奖励 → 再次保存；保存是各状态的副作用，不能代替游戏状态提交。参考取舍为保留现有玩法、UI 和 schema，只审查新增异常边界。

界面布局保留大厅、商店、对局 HUD、结果和奖励界面；当前只有开发者 console 警告，没有新增存档状态 UI。未生成屏幕/图片。后续如增加反馈，默认玩家语言 English，例如 “Progress could not be saved. Retry.”；本中文审查不构成切换游戏语言要求。

物理步长、碰撞/计分数值、成功失败规则和可接受物理误差本轮**不改动，也没有足够核验给出完整参数定义**；不能为满足品类模板虚构参数。保存审查的输入窗口是上述业务动作触发保存的同步调用栈。E6 已见合格射击力度阈值 0.25 以及施加射击后完成教程的顺序，仅用于解释调用影响，不是完整物理验收。后续若做 gameplay 回归，应固定时间步及输入重放，对照原版碰撞、计分、胜负、重开与快慢帧；当前没有执行该类测试。
