# Carrom 配置对象运行时虚表复核

## 范围与结论

本轮为只读离线研究，日期 2026-11-13，attempt=1。按用户要求交付本文件，不制作游戏、不修改原包、不推进美术、代码或测试阶段。已采用本轮冻结的 casual-game-production 与 game-competitor-analysis 技能，并读取全部四份选定品类和 Web 资料；其游戏生产要求仅作范围核对，不据此扩展本任务。

核心结论：若操作者提供的地址换算、内存读取和版本匹配均准确，快照显著加强了“该时刻全局指针所指对象的虚表地址点，其 +0x30 槽指向 GameConfiguration.plist getter 候选”的解释。它填补了纯静态分析中对象与运行时槽位对应关系的一部分，但没有证明 CPU 执行过该间接调用、返回过该文件名、读取了对应文件、进入候选解密桥或成功应用配置。不能报告获得明文或密钥。

| 观测 | 在观测准确前提下支持 | 仍不能证明 |
| --- | --- | --- |
| 安装 split 哈希与本地一致 | 所比对安装文件与本地样本一致的用户记录 | 本轮独立验证、运行内存全部代码与磁盘一致 |
| APK 内 SO 偏移 0x4e0000，结合首 PT_LOAD 和 maps 推得 bias 0x33e8000 | 存在可复核的地址换算假设 | 未见原始映射，不能独立确认 bias 或把所有 VA 当文件偏移 |
| 0x2f23a70 全局位置读出对象指针，对象首 8 字节为 vptr，对应 link VA 0x27eba98 | 该次采样存在这种指针关系，与多态对象解释相容 | 对象完整动态类型、生命周期、实际调用时仍为同一对象 |
| vptr+0x28 指向 0x1e3f704，+0x30 指向 0x1e3f710 | 在该地址点下的两个槽位目标；64 位槽间距为 8 字节 | 槽位被执行、虚表起始布局或 RTTI 已完整恢复 |
| 后者运行时 12 字节为 40a1ffb000a02d91c0035fd6，与本地相符 | 该局部代码样本一致；与静态返回字符串地址的短 getter 解释相容 | 整个 ELF 内存完整性、执行历史、文件读取或解密成功 |
| 此前两个静态 getter 分别返回 ValueMap.plist 和 GameConfiguration.plist | 用户先前静态分析结论；B 独立支持后者的字符串引用候选 | 本轮对 ValueMap getter 的完整独立验证，或运行时实际返回值 |

“vptr”按对象首字段的虚表地址点解释；不把地址点直接等同于包含 RTTI/offset-to-top 的整张虚表开头，也不未经布局复核强行给出源码中的虚函数序号。对多重继承、调整 thunk 和对象被替换等可能性保留边界。

## 地址换算复核表

以下仅为对 U1 的 bias=0x33e8000 做十六进制加法，不是新内存读取。规则为 runtime VA = load bias + ELF link VA。

| 含义 | link VA | 按 U1 推算 runtime VA |
| --- | --- | --- |
| 全局指针存储位置 | 0x2f23a70 | 0x630ba70 |
| 虚表地址点 | 0x27eba98 | 0x5bd3a98 |
| +0x28 槽存储位置 | 0x27ebac0 | 0x5bd3ac0 |
| +0x30 槽存储位置 | 0x27ebac8 | 0x5bd3ac8 |
| +0x28 目标 | 0x1e3f704 | 0x5227704 |
| +0x30 目标 | 0x1e3f710 | 0x5227710 |
| GameConfiguration.plist 字符串 | 0x1268b68 | 0x4650b68 |
| 用户给出的调用方 | 0x1c0eeec | 0x4ff6eec |
| 用户给出的对象获取入口 | 0x1e3f0c8 | 0x52270c8 |
| 用户给出的后续入口 | 0x1c0eff8 | 0x4ff6ff8 |
| 用户给出的加载候选 | 0x1e40a34 | 0x5228a34 |

对象自身堆地址未提供，不得把全局指针存储位置当作对象地址。ELF 文件偏移应按所属 PT_LOAD 用 p_offset+(VA-p_vaddr) 换算，并检查文件有效范围；APK 偏移再叠加 SO 在容器中的实际存储偏移，且须满足所用直接映射条件。0x4e0000 不能无条件叠加在运行时 VA 上。maps 条目的 offset 也不能不区分容器与 ELF 语义直接用于减法。

## 尚缺的调用与数据流闭环

待证链为：用户给出的 0x1c0eeec 路径 → 0x1e3f0c8 返回对象 → 在实际间接调用点读取该对象的 vptr+0x30 → CPU 转移到 0x1e3f710 → getter 返回文件名 → 与 gameConfig 一起传入 0x1c0eff8 → 到达 0x1e40a34 → 实际读取来源字节 → 候选解密桥的真实解析目标 → 返回数据 → 解析及配置提交 → 消费者读取新值。箭头均应逐边记录证据，目前不能当作已执行链。

1. 对象身份：记录获取入口的调用点、返回对象地址、当前全局指针值、线程和生命周期，证明它与间接调用使用的接收对象相同。采样前后相同不保证采样间没有变化。
2. 间接调用：需要调用指令地址、调用前目标寄存器和接收对象、实际控制流目标及返回位置。读槽只能证明可用目标，不能证明调用发生。不能把一次主动手工调用 getter 等同于应用原生路径调用。
3. getter 输出：在正常调用返回边界验证 x0 指向的有效、受限长度、以终止符结束的文件名；AArch64 的 x0 是常见标量返回寄存器，但真实签名仍应结合调用点确认。
4. 0x1c0eff8 参数：核实 gameConfig 是路径、逻辑标识、输出对象还是其他语义；记录真实参数位置、长度、类型布局、隐藏返回参数和对象归属。不能凭名称认定其为密文、密钥或明文。
5. 0x1e40a34 来源：确定从 APK asset、私有目录、缓存、下载结果还是内存副本读取，记录实际解析路径、读取长度、输入哈希和分支条件。文件名 getter 不证明文件存在或被打开。
6. 候选解密桥：B 仅记录 decryptAES128 字符串在 0x2711cc4 的引用候选及短范围 0x2711cb0–0x2711cd4；这可能只是名称注册/分发辅助。须确认配置加载路径确实到达该桥、分发到哪个实现、何种输入输出契约。不能从名称确定算法、模式、IV、padding、密钥来源或 AES 实际使用。
7. 输出及应用：需要真实返回状态、输出长度/哈希、合法格式解析和配置版本/消费者读值对应关系。成功返回、可打印文本或出现 plist 标记，均不能单独证明配置已生效。失败回退默认值或旧缓存必须单独标注。

## 输入、时序与最小记录契约

每次事件至少关联 run_id、PID、进程启动标识、线程 ID、单调时间戳、模块身份与本次 bias、link/runtime PC、调用深度或配对编号、接收对象、输入来源、输入长度/哈希、返回状态、输出长度/哈希。字节采样说明上限、截断与读取失败；无必要不记录个人数据或密钥内容。

输入条件需记录：冷启动或同进程重入、操作者动作、页面/加载阶段、网络可用性、现存缓存和配置版本。首次加载、重载和下载回调可能异步执行；必须按同一请求或数据对象关联，不能只把时间接近的两个事件相连。

重点时间边界：全局对象初始化前后、getter 调用前后、文件读取完成、候选桥入口/返回、解析成功/失败、配置提交和消费者读取。一次成功会话也不代表每次启动均走此路径。
