# Carrom 对局静帧诊断证据审查

## 1. 范围、来源与执行边界

本轮为原型定义阶段的只读证据审查，不是开发或测试验收。唯一游戏事实来源是调用方本次请求中的 A/B/C 摘要；没有提供参考文件（references=[]），本审查者未看到原代码、原始截图、RGB 解码结果、测试脚本或运行日志。下文“摘要报告”不等于本审查者独立核验。

只写本报告 `/workflow/prototype.md`，不修改游戏源码、资源、配置、测试或构建产物，不安装依赖，不启动游戏，不调用浏览器、MCP、ADB 或图片工具，不执行自然局或同状态复现。未来诊断步骤均为建议，尚未执行。不得将方案当作验证结果。

方法资料（不是当前游戏的运行证据）：

- `framework/docs/web-common.md`、`framework/docs/canvas-web.md`：输入坐标映射、资源失败与浏览器证据边界。选定 Canvas 配置不证明被审游戏实际引擎或实现。
- `game-reverse-engineering/SKILL.md` 及同包 `references/execution-protocol.md`、`references/global-rules.md`、`references/unknowns-ledger-template.md`：证据分级、单一 owner、未知项登记。

## 2. 已报告的观测与不能推出的结论

| 编号 | 调用方摘要报告 | 本轮证据边界 |
|---|---|---|

B/C 的盘面和随机性不同，只有自动输入与加载条件相近，故不是只改变头像结果的受控配对实验。A/B/C 的局身份、构建身份是否一致也未提供。B 至多反驳“头像404必然使每一局都无法到达败局”的全称断言，不能反驳“404在特定状态下可能相关”的候选假说；更不能据三段摘要估算故障频率。

禁止结论：404就是根因、物理引擎卡死、引导必然拦截、固定坐标必然未命中、故障已修复、完整对局性能正常。当前根因结论为 `NEEDS_CONTEXT`。

## 3. 待观测的玩法契约，而非擅定游戏规则

诊断循环：输入尝试 → 实际命中与接受/拒绝 → 物理演化 → 碰撞/入袋及计分提交 → 回合切换或终局 → 选择页/新局。它是待映射到真实 owner 的观察框架，不是已确认的实现状态机。

- 状态至少区分等待输入、运动中、等待动画/异步、暂停、终局、离开对局；实际名称和允许转换待取证。
- 输入窗口需从真实规则取得：谁可操作、是否要求所有棋子静止、引导是否捕获、拖拽/释放何时提交、取消如何处理。没有窗口证据时，不能以“脚本发过事件”判定游戏必须推进。
- 物理步长不得臆定为1/60秒。需取得固定/变步、单位、累积器、补步上限、长帧截断、暂停及休眠语义；区分渲染帧计数、更新计数与真实物理步计数。
- 碰撞需确认圆盘/边界/袋口的碰撞体、触发器、过滤及对象移除；计分需记录入袋/犯规事件和提交所属局、回合。没有规则，不把分数6擅定为普适终局阈值。
- 成功/失败：当前仅有B/C摘要中的败局，胜局条件未知。诊断成功指找到可复查的停滞边界或排除某候选，不等于游戏验收成功。
- 界面观测区域包括棋盘、比分、回合/引导/暂停遮罩、结算、选择页和开始入口；没有截图，不提供实际坐标、尺寸或布局还原。当前不新增游戏界面或文案，不进行美术及语言验收。

## 4. 最少只读观测方案

先由有访问权限的操作者定位现有诊断入口、事件和实际 owner，再按下列最小信息集采集。字段名称是建议的语义名，不代表源码中已有这些标识。

**只读限制**：优先使用现有 debug 导出、被动日志订阅、浏览器事件/性能/网络观察及截图。不得用补丁、覆盖 handler、强制唤醒刚体、解除暂停、清空队列、修改随机源或 setter 伪装为只读。若闭包内部状态不可访问，记录“不可观测”；新增源代码插桩需要另外授权，不在本轮实施。断点暂停会干扰时序，不作为未受扰动的停摆证据。

所有样本统一关联 `runId / gameId / turnId / sampleSeq / monotonicTime`；局身份改变时切断旧局样本。不要用单一外部定时器证明游戏主循环活跃。

| 观察组 | 最小字段/事件 | 用途与可判定边界 |
|---|---|---|
| 生命周期与循环 | 实际 phase、当前操作者、比分、终局标记；游戏主回调进入/退出计数及最后时刻、更新计数、render计数、物理step计数；外部采样序号，页面visibility/focus、暂停值与原因/owner | 外部采样前进而游戏计数不前进，只定位为循环未观测到推进；需同时排除合法按需渲染、后台节流和暂停。回调进入但不退出需区分同步阻塞、异常与采样不完整 |
| 物理 | 对象id、位置、线速度；实际存在时角度/角速度；active/sleep/removed；对象总数、有限值检查；每步dt、累积器/补步量；接触/入袋/销毁事件与比分提交id | 区分“合法静止”“仍应运动但未步进”“对象已移除却仍渲染”。静态快照不足以证明接触计算执行，需边界事件/步计数 |
| 输入与引导 | 每次脚本动作id与目标；浏览器送达down/move/up/cancel及时间、pointerId、坐标、capture状态；实际命中对象、游戏坐标、接受/拒绝及理由、引导阶段/拦截owner | 把脚本尝试、DOM送达、游戏命中和动作提交分开。没有接受证据，不能认定物理应开始 |
| 动画与异步 | 队列长度、活动任务id/所属局/回合、入队/开始/完成/取消时刻、阻塞对象、截止条件；头像请求开始/404/成功以及消费者完成/失败终态 | 队列存在不等于阻塞。需证明哪个 gate 在等待哪个任务，头像失败是否经过该依赖链；没有消费者关系，404只是共现 |
| 采样真实性 | 截图请求/完成单调时间、页面及画布身份、尺寸、RGB哈希、对应游戏样本序号和render计数 | 检查缓存、重复取同一文件、错误页面/画布。相同哈希仍不必然异常，静止且等待输入时可以合理相同 |

采样建议：转态、动作接受/拒绝、入袋/计分、任务完成采用事件记录；物理对象在有效物理步后记录到有界环形缓冲，疑似停滞时再导出。背景摘要可先每0.5秒一次，截图每1秒一次；这些只是待验证的采集参数，不是故障阈值，也不能捕获所有瞬态。保留异常前后的事件序列，记录采集是否溢出与额外开销；不采集凭据或不必要个人信息。

### 4.1 固定坐标未命中检查（优先级最高的廉价排查）

1. 保留原脚本每次动作的视口/CSS坐标、拖拽完整序列和发送结果；核对实际 viewport、DPR、缩放、滚动、Canvas rect、内部尺寸、棋盘变换及遮罩。
2. 无旋转/额外变换时，先计算 `canvasX=(clientX-rect.left)*canvasWidth/rect.width`，Y同理，再经实际棋盘逆变换；有边框、旋转或letterbox须使用真实内容区域/变换，不能机械套用公式。
3. 记录 `elementFromPoint`、游戏自己的命中对象及处理结果。前者只说明DOM层，不能证明命中Canvas内棋子。
4. 若脚本动作在输入合法窗口送达，但游戏转换后的点在真实命中区外，且没有提交，则支持“该动作固定坐标未命中”；若命中合法对象且接受、产生了对应动作id，则排除该动作的此候选，不能排除整局其他动作。
5. 在同初始状态的另一配对运行中，只把固定坐标改成由当前目标区域计算的坐标，保持动作类型/力度/时机策略不变。若原坐标未命中、目标坐标被接受并推进，支持脚本路径问题；不要用在已改变的盘面上随意补点充当同状态对照。

## 5. 可证伪假说与判断标准

判断前先定义观察窗口W：依据当前规则的动作、动画最大等待及循环节奏制定并记录；没有期限契约，只能写“在W内未完成”，不能宣布死锁。50.83秒文件跨度不直接成为W。记录事件顺序，不能只比较首尾快照。

| 候选 | 支持它需要的联合证据 | 反证或降级条件 |
|---|---|---|
| 合法等待/暂停 | 阶段确实允许等待；输入未被接受或暂停原因有效；对象静止/休眠符合规则 | 已接受需要推进的动作，且无合法等待/暂停，却在契约窗口内未推进 |
| 主循环未推进 | 页面持续可见、同局、需要持续更新、无合法暂停；独立采样连续成功，但真实主回调计数在W内不变 | 主回调计数持续增加。仍可能存在更新/物理子系统停滞，不能因此判整体正常 |
| 物理调度未推进 | 有效动作已提交或存在应运动对象；主更新持续、非暂停；物理step计数不变 | step计数增加，排除“完全没有步进”，不排除碰撞/数值/对象问题 |
| 物理状态异常 | 每步有证据，且对象出现NaN/Infinity、与约定不符的休眠/越界或移除；或应运动但状态持续违反已确认积分规则 | 有限状态及演化符合已确认规则，候选在该窗口不获支持。速度近零本身不是异常 |
| 输入/引导阻塞 | 事件送达，实际处理记录明确拒绝/拦截；有待满足的引导条件及owner | 对应动作被接受并提交。可排除该动作的拦截，不能推广至其余动作 |
| 动画/异步等待 | 阶段明确等某任务，任务未终态且过其约定期限，任务id与局/回合吻合 | 队列为空、任务已终态或无阻塞依赖；队列长度不变但任务id在变化也不是队列冻结 |
| 截图链路重复/表现未更新 | 游戏状态变化而采样仍相同；截图来源/序号有重复可定位采集问题；若新render从新状态绘制却画面不变需另查呈现映射 | 新截图来源与序号明确，实际状态也相同，则不支持“只是截图重复”；仍不足以判定游戏异常 |
| 404相关的状态依赖 | 同状态配对下只改变头像结果，特定失败消费者/gate的事件链与停滞边界一致 | 缺图配对同样推进或正常图配对同样停滞，可反驳该状态下简单的“404必致停滞”解释；不能否定所有其他状态的相关性 |

**可接受误差**：事件身份、计分提交次数、局/回合顺序及离散状态必须匹配，不作近似。连续位置/速度比较应基于同物理step而非截图时间。先从现有引擎/规则取得位置、速度及休眠阈值，记录单位和容差；若未知，保留原始数值，不把“低于自拟阈值”当作静止。跨浏览器不要求逐帧位级一致；RGB全等只是图像判据，不是物理容差。碰撞/入袋阈值附近的重放差异应单列，不能通过放宽容差掩盖计分差异。

## 6. 同初始状态复现与最小对照顺序

### 前置配对门禁

操作者需提供同一构建/配置指纹、运行环境、视口/DPR、存档与引导状态、棋子全状态、当前回合/比分、暂停状态、动画/任务队列、随机源种子及当前位置、AI状态。相同seed不保证相同随机序列；头像加载可能改变随机调用顺序，故还需记录随机消费序列或独立流状态。相同布局也不等于相同隐藏状态。

尽量从现有合法启动/重放接口创建相同S0。若只能通过内部setter、注入随机源或修改源码得到S0，停止并申请另行授权；不把这种操作称为只读。本轮仅提出方案。若没有可用重放接口，继续自然局观察但明确降级为非配对样本；A没有状态日志，不能声称恢复了A的原状态。

### 分步执行（操作者未来执行，非本轮结果）

1. **验证采集与输入链**：用现有启动流程进入一局，在明确合法窗口保留一次动作全链和循环/物理变化，证明观察字段含义与新截图来源。对未知字段先标NEEDS_CONTEXT，不推测。
2. **原路径复现**：从可证明的S0，以原自动脚本和原缺图结果运行，保留输入尝试、接受/拒绝及状态摘要；发现静帧时导出环形缓冲，不解除暂停或清队列后再称“自然恢复”。
3. **单因素输入对照**：从同S0和同缺图条件再次启动，仅使用目标区域计算坐标，比较动作命中/接受及后续边界。坐标对照与头像对照分开，避免两个因素同时变化。
4. **头像配对**：固定S0、同一输入策略和送达序列，分别让同一头像请求成功与404，其他资源与环境相同；使用原有可选条件或经另行授权的外部测试夹具，不改游戏源码。记录请求时刻、响应延迟、失败消费者与终态。若成功/404的时间行为未匹配，则对照的是整个“加载结果及时间路径”，不能单独归因状态码。
5. **边界比较**：按动作id和有效step对齐，找第一个分歧：请求消费者 → gate → 输入接受 → 物理step → 碰撞/计分 → 回合/终局。若规则不允许跨运行绝对时间对齐，用状态事件边界；不要拿不同回合的相同比分强配对。
6. **条件重复**：先做最小一组配对以决定下一步，不用它估计频率。如需考察非确定性，预先指定重复次数、超时及排除条件、交替运行顺序并保留所有分母；无该设计不得报告发生率。

进入败局、返回选择页、开始新局应分别记录游戏id/阶段改变、旧任务及对象归属；能开新局不证明旧局没有对象或监听残留。完整性能评估需另外约定设备、负载、帧时分布、内存与持续时长，本轮不覆盖。
