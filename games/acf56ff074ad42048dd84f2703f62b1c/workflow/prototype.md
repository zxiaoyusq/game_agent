# Carrom 广告与宿主暂停协调只读审查

## 范围与证据边界

本轮为 prototype 阶段的只读风险审查，仅新增本报告，不修改游戏源码、资源、奖励规则或框架，不推进后续阶段。已读取冻结技能 casual-game-production/SKILL.md 及四份选定品类、Web 技术资料。资料中的新游戏设计要求按本任务范围适配，不另造玩法、美术或可运行原型。

唯一源码参考：ref/mcp-inputs/mac-codex/dd8b79747ae3b111ad0a83ec8088b69b7632ec9f122e685b76601e731d52ffe8/Carrom_current_dd8b7974.js。以下定位采用 read_reference 字符区间及函数名，不虚构行号。路径中的哈希未由工具独立复算，不作为本轮计算的文件指纹。

未提供、未读取新版源码。hostPaused、每次广告 token 及统一静音表达式均来自调用方描述；不能证明已正确落地。未执行脚本、构建、单测、浏览器或真实宿主验收。所有时序反例是静态条件推演，所有验收项是建议，均非实测结果。

## 结论

独立 hostPaused 与广告 token 是合理方向：若所有全局静音写入都收敛到同一入口，则一个原因解除不会覆盖其他有效原因。但该方案只能有条件地解决全局静音合成，不能据此认定广告与宿主交错已安全。保留旧 ticker.stop/start、旧奖励回调且只拦截主更新与匹配等待，仍不足以形成完整暂停契约。优先处理 ticker 所有权、广告请求生命周期、奖励事务与旁路输入。

## 方案成立所需不变量

1. 全局静音使用严格布尔值：Boolean(hostPaused || adTokens.length > 0 || sdkMuted || !visible)。原描述中裸 adTokens.length 在短路求值时可能返回数字；不要依赖未提供版本的 Howler 对非布尔参数的处理。若使用 Set，应检查 size。
2. hostPaused 只由宿主事件维护，SDK 音频状态只维护 sdkMuted；广告结束、页面可见与用户设置均不得清除 hostPaused。
3. 每个广告请求拥有唯一、不复用的身份及自己的终结状态；同一请求重复 beforeAd 不得重复加锁，重复终结不得重复奖励或恢复。未知 token 删除必须无操作，数组实现尤其不能 splice(-1,1)。
4. 所有全局 Howler.mute 写入，包括旧广告正常结束与 catch 分支，均走统一入口。仅在删除 token 后补一次同步仍可能产生短暂错误解禁或因后续异常漏同步。
5. 主更新、物理、计时、输入、匹配推进与业务提交明确共享或分别遵守暂停条件；不可将静音条件直接当成所有系统的运行条件。SDK 静音通常只影响音频，游戏弹窗暂停还需独立保留。
6. token 资源清理与业务回调有效性分开：旧代际回调也应释放自己仍持有的 token，但不得修改新请求、界面或奖励；不能因 generation 不匹配直接跳过必要清理。

## 重点风险与具体反例（条件推演，未运行）

### P0：ticker 仍可能被另一广告提前启动

设广告 A 为激励广告、B 为插屏，SDK 或测试替身允许两者回调交错：

- A.beforeAd：加入 a，旧代码 ticker.stop。
- B.beforeAd：加入 b，旧代码 ticker.stop。
- B.adBreakDone：删除 b，旧代码 ticker.start，此时 a 仍存在。

因此 ticker 已运行，而 A 仍持有暂停原因。即使统一静音正确，声音仍静音，且主更新顶端检查 a 后可拦住该主更新；这不改变 ticker 被提前启动的事实，也不证明其他共享 ticker 监听器、输入事件和原生定时器停止。旧应用设置 sharedTicker=true，更需核对实际 PIXI 版本及所有监听器，不能臆定影响范围。

宿主反例：A.beforeAd → host pause → A.afterAd 旧 start；hostPaused 仍为 true，音频可保持静音，但 ticker 仍被启动。主更新守卫是局部防线。

另一个顺序问题：主更新已进入 Tweener.update 时，某个 onComplete 同步触发广告 beforeAd。入口暂停检查已经通过；当前 JS 调用栈可能继续执行后续更新乃至物理步，stop 不会自动中断当前调用栈。应在关键状态提交/物理步前复核或采用明确的延迟提交边界。

建议将 ticker 启停集中到协调器，广告只改变原因；协调器还需包含资源就绪、销毁、游戏自身暂停等约束，不能广告结束就无条件 start。若选择 ticker 常驻而逻辑守卫，必须完整核验所有监听器与副作用，并移除旧启停竞争。

### P0：奖励回调与 token 并不等价

旧 _carromResolveAd 的 resolved 可防同代重复解析，但共享 _0x38b273 仍不能天然支持并发。推演：请求 A 正在显示时再次准备 B，使 generation 前进；A 的 adViewed/afterAd 被旧代际检查拒绝，可能丢失业务结果；若新版释放 token 也放在该检查后，还可能遗留 a。另一种交错中，新调用覆盖共享 callback，而旧 afterAd 清空它，造成新请求回调丢失。实际可达性依 SDK 串行保证和新版接线，未确认。

旧 afterAd 清 _0x38b273，若 SDK 先 afterAd 后 adViewed，则奖励结果可能被吞；若保留代际递增，还可能被当作过期。不能假设所有 SDK 必定按理想顺序回调。

奖励成功回调还可在 hostPaused 或另一广告期间直接改金币、存档和切场景；主循环守卫不会阻止它。建议每请求闭包保存 placement、奖励金额/上下文、callback、requestId 与页面/局生命周期；奖励最多提交一次。确切奖励凭据与业务过期处理由契约决定，不能把 afterAd、超时或恢复宿主当作观看成功。音频清理先完成，业务通知异常不得阻断清理。

### P1：异常覆盖不完整

同步 try/catch 只能捕获该调用栈内异常，不能兜住未来异步 SDK 回调中的异常或未接入的 Promise rejection。beforeAd 内先加 token 后音频 API/ticker 抛错、终结回调中业务代码抛错、show 调用前失败、无填充且没有 beforeAd、重复 beforeAd、完成后迟到 beforeAd，都应定义路径。建议 per-request finalizer 幂等，先标记终结和释放自己的资源，再同步状态，最后隔离执行业务回调。迟到 beforeAd 必须检查 terminal，避免重新加锁。

### P1：广告永不结束

只有 beforeAd 加锁而终结回调从不来，会永久静音并阻止主更新/匹配。旧 ticker 已 stop，因此不能用主更新或 Tweener 驱动的 watchdog 期待其自救。原生计时也会受后台节流，需在可见性/宿主恢复时重新核对经过时间。

建议区分请求等待、实际展示和终结，记录时间与原因；超时进入可诊断恢复状态，不授奖。不能仅因固定秒数到期就解除实际仍展示的广告锁并恢复声音/交互；应依宿主广告关闭确认或明确失败契约恢复。阈值需要 SDK 合约与实际时延数据，本轮不编造。终结后迟到结果按已约定策略处理且不得二次提交。

### P1：音频 API 生命周期

Howler.mute 管输出，不代表暂停播放游标、停止解码、取消排队 play 或成功恢复 AudioContext。旧 playLoop 的 isPlaying 是应用自定义标志，不证明浏览器实际播放成功。用户若期望背景乐原位续播，需要独立的 pause/resume 设计，不能把 mute 方案称为音频暂停已完成。

宿主事件可能早于 Howler、Howl 或应用初始化：先保存原因，依赖可用时重放同步；新建、重建或 unload 后的实例需重新应用组设置及全局原因。查询 SDK 初始音频状态与订阅的先后需避免漏事件。加载/解锁、自动播放拒绝、音频上下文挂起及恢复失败都需真实环境检查，不能无条件调用 resume 并声称已恢复。未提供 Howler 库版本/源码，不对其内部行为作版本性保证。

### P1：静音开关和页面可见性

保留 Music、SFX 的用户偏好，与全局临时静音分层。全局允许出声后，用户关闭的组仍应关闭；临时暂停不能篡改按钮偏好，切换组开关也不能绕过全局锁。新注册声音必须继承当前组偏好。旧设置 UI 的 updateAudio 基于 SDK 静音，是否扩大到其他原因是交互策略，不应把临时 host/ad 原因写成用户选择。

visible 初始值应来自实际页面状态；统一处理 visibilitychange，兼容分支与 pagehide/pageshow 必须核对，不能一次 focus 就覆盖仍隐藏的事实。旧可见性恢复会打开暂停弹窗，应避免与 host resume 双重恢复或重复弹窗。浏览器中文环境不应改变原游戏语言；本次无新增玩家界面或文字素材。

### P1：输入和匹配等待旁路

旧瞄准松手可以直接调用发射，滑杆可以直接改物体位置；暂停主更新仍可能积累这些状态变更。暂停切入时取消正在进行的拖拽/瞄准，释放指针归属；所有 gameplay 入口检查统一暂停条件。恢复不得把暂停前后跨越的 pointerup 当成新发射。

匹配中 setTimeout 回调即使只新增 hostPaused/token 检查，简单 return 会丢失推进；周期重试则可能在销毁后继续。应保存匹配实例身份与剩余有效游戏时间，暂停时冻结，恢复后继续一次，离开页面时取消。原生 ready、startRoll stop 以及后续 start 事件均需覆盖，不能只改其中一处。

## 保留的玩法与暂停验收契约（建议）

沿用观察棋盘→摆放/瞄准→松手发射→物理运动→入袋/犯规→结算/换手→胜负或重开；不修改碰撞、计分、奖励倍率、成功失败规则或布局。旧脚本实际使用 PIXI 与 planck，不能因为项目 profile 是原生 Web 就把参考称作原生 Canvas 新实现。依赖的 CarromDiscRules 未提供，完整胜负与计分细则不在本轮核验范围。

已读旧物理步为 1/60 秒，迭代参数 10/10；暂停期间建议物理步数、回合倒计时与匹配有效时间增量为 0，分数/金币不因重复或过期广告结果增加。合法输入窗口应关闭并取消未完成瞄准；恢复不补算暂停时长。外层累加器应明确丢弃暂停时间与限制恢复补步；旧代码 while >1 的边界及 PIXI delta 限幅须在实际版本验证。

计数、token 归属与奖励次数要求精确一致，容许误差为 0；几何复现可暂以同环境暂停恢复前后位置偏差不超过 1 逻辑像素为待验证阈值，速度不得被重置或出现非有限值。该阈值是建议，未通过运行校准，不承诺跨浏览器逐帧一致。界面保留大厅、匹配、棋盘、暂停/设置、结果与转盘，审查只要求这些界面在广告/宿主交错下不误切换、不重复领奖。

3. P1：覆盖输入、原生定时器和匹配生命周期；处理初始化前暂停、依赖重建、长帧与当前调用栈重入边界。

| 场景 | 应核对结果 |
