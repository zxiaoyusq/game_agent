## 结论与证据等级

【描述推导】在 SDK 会话写入确实成功、原始读取返回当前权威值、dirty 完整记录失败、运行模式不变且后续本地操作成功的前提下，flush 可以使失败键向当前会话值收敛。读取 dirty 键时绕过旧本地值，可以避免本会话读回陈旧值。重复 flush 在没有新业务变更时应得到相同存储内容。

【不能推出】dirty 清零不等于跨会话数据永不丢失，不证明多键事务原子性、奖励恰好一次、真实宿主兼容或浏览器崩溃后的恢复。公开 resume 幂等调用 flush 也不代表 SDK 初始化和异步切换已被正确处理。

【待实现证据】SDK get/set/remove/clear 的同步或异步契约、失败语义、键命名空间、null 与 undefined 的意义、原始方法绑定、安装哨兵、模式判定时点、每键异常隔离及 revision 检查，均未获得新版源码证实。以下反例均为条件性执行轨迹，不是实际复现结果。

## 状态与成功边界

建议将状态明确区分为：会话已接受但待保存、已完成本地 API 提交、读取失败或值不确定、宿主管理模式。可用 dirty 数量表示待重试规模，但不能代表业务事务完成数。成功的最低定义为：目标命名空间内，本次待提交版本的本地写或删实际成功，且期间没有更新版本替换它，才清除此版本的 dirty。SDK 读失败不能当作键不存在。业务奖励成功另需完整状态与去重记录的一致提交。

本轮不新定义或改变 Carrom 的物理步长、碰撞、计分、胜负或输入窗口；这些不属于此次存档评估，旧源码片段不足以核定，也不虚构数值。界面布局和玩法循环维持现状。仅建议保存状态反馈：待保存使用英文 Save pending，失败使用 Save failed. Progress may be lost.，真实重试成功后才清除。该文案属于建议，未集成。

## 具体故障反例

| 场景 | 条件性轨迹与影响 | 必要约束 |
| --- | --- | --- |
| SDK set 失败 | 本地 coins=100；SDK set(150) 抛错或异步拒绝。若仍写本地、错误标记 dirty，或报告成功，两个数据源可能分叉；flush 还可能取到旧会话值并覆盖较新本地值。 | 先明确 SDK 接受成功的判据；失败不宣称接受新值。若 SDK 可能修改后抛错，需版本化状态核对。 |
| 本地 set 失败 | SDK coins=150，本地仍100，dirty 标记；本会话 get 返回150。刷新发生在重试成功前，SDK 内存与 dirty 消失，新会话可能恢复100。 | 明示会话可用与持久化成功的区别；不能靠 resume 消除关闭前窗口。 |
| SDK get 失败 | dirty coins 当前应为150，flush 读取抛错；若统一转 null，会删除本地100并清 dirty。Promise 被当作同步值也可能写入错误字符串。 | 异常或未完成状态保留 dirty；严格核对 SDK 类型和同步性；按键捕获。 |
| 本地 get 失败 | 非 dirty 键读取本地抛异常；若无明确 fallback，调用方可能回默认值并保存，覆盖原进度。若 fallback SDK 未初始化，也不能证明数据完整。 | 区分缺失、访问失败和坏档；失败不能直接成为可保存的默认档。 |
| remove 失败 | SDK 已删除 k，本地 remove 失败，dirty k；若 dirty get 回退本地，旧值复活。原始 get 确认缺失后，flush 删除可修复。若 get 的 undefined 表示未就绪，则可能误删。 | dirty 读取保留删除语义；确认缺失契约，必要时保留显式 tombstone。 |
| clear 遗漏 | SDK clear 清空会话，而本地清理在第2个键失败；若只记录一个标志或只遍历 clear 后的 SDK 键，残留本地键不会进入 dirty，下一会话复活。 | 清理前建立应用拥有键的并集及删除意图；逐键清理和追踪，不调用会破坏同源其他应用的全局 clear。 |
| 多键 partial 写 | 初始 coins=100、lastRewardTime=t0；奖励后 coins=150、时间=t1。只 coins 写成功就崩溃，会得到新金币和旧领取时间，可能重复领取；反向部分提交可能导致已标领取但金币没到账。 | 多字段关联状态需事务边界，单键 flush 不提供此能力。 |
| 重试部分成功 | dirty 有 a、b、c；a 成功、b 失败。若只有外层 catch，c 本轮不重试；若在 finally 清理或提前删除 dirty，则丢失 b 的重试意图。 | 每键隔离，成功才清对应版本；返回仍待处理数并保留失败原因。 |
| 重入或异步竞争 | flush 读到 k=v1，期间业务写 v2 失败并标 dirty；旧 flush 写成 v1 后无条件删 dirty，v2 不再重试。纯同步无重入实现未必存在该窗口。 | 异步或可重入场景使用 revision，清理前比较版本，并串行化或合并 flush。 |
| 跨会话旧值 | 本地旧值100，内存150且 dirty；页面被杀死，无任何后续 resume。新会话没有证据重建150。 | 没有另一份成功持久化的记录就无法恢复该增量。更换存储也需真实提交成功。 |
| 异步 host channel | 安装时尚无 channel、无 gameData，稍后握手进入宿主模式；若 resume 只检查启动时标志，可能继续写本地并混入另一档案。相反，启动时发现 channel 而后断开，也不意味着可安全自动切本地。 | 存储归属随明确状态机决定；读写、flush 和切换都检查模式及会话代次，制定已有 dirty 的隔离策略。 |
| URL gameData | 参数存在但为空、编码异常、解析失败或尚未导入；若只按 truthy 判断，可能意外装本地适配器。 | 明确参数存在性、有效性和失败策略；外部数据模式解析失败不能偷偷回落并覆盖。 |
| 重复安装 | 安装两次，第二次捕获第一次包装后的 getItem 为所谓原始方法；flush 可能递归、读本地旧值，且两个 dirty 集合或 resume 监听并存。 | SDK 对象级安装哨兵、单一状态、仅捕获一次并绑定真正原始方法；兼顾 SDK 对象替换。 |
| 键与类型 | 若 dirty 为普通对象且直接用用户键，__proto__ 等键可能追踪异常；空字符串、字符串 null 与真实 null 混淆也会错误删除。 | 用 Map 或无原型字典并限定命名空间；不要用 truthy 判断存在性，拒绝意外对象及未决 Promise。 |
| 多标签页 | A dirty 保存旧快照，B 已提交新进度；A resume 后按旧会话覆盖 B。单会话最新值不是同源全局最新值。 | 若支持多标签页，规定单写者或冲突检测协议；仅版本号但无协调不足以消除竞争。 |

原生 localStorage 单键操作与业务多键提交必须区分：不能因为多键部分成功就声称单次 setItem 会写入半段 JSON。上述 partial 风险是多次操作之间的混合快照；SDK 包装层是否还有其他语义未知。即使本地 API 返回成功，也不承诺浏览器数据不会被清理、驱逐或因存储设备故障丢失。

## 奖励事务与崩溃恢复

flush 应只重放当前存储状态，不调用发奖、扣费、升级或领取处理。内容幂等写入不能替代业务幂等：重复回调执行 coins += reward，即使每次 flush 都正确仍会重复发奖。

推荐将余额、领取时间、解锁或升级和已处理 rewardId 作为一个受版本校验的业务快照提交；rewardId 必须来自稳定事件身份，不能每次重试生成。单键快照可避免这些字段跨键混合，但不能挽救该键一直未成功持久化时的崩溃丢失。多键协议需要日志、提交标记和恢复算法的完整定义；如果日志写入也失败，依然没有可靠恢复依据。

至少区分三处崩溃窗口：发奖后尚未保存则可能丢奖励；余额保存而去重标记未保存则可能重复发奖；去重标记保存而余额未保存则可能漏发。会话内 _carromResultCommitted 等变量即使存在，也不能自动覆盖重载后的去重。旧片段仅证实该变量声明，不证明其完整使用和持久化。真实货币或外部奖励若有服务端，应依其事务凭据对账；当前未证实服务端存在，不将其当作已有能力。

## 有序建议

1. P0：明确方案保证是本地预览、单会话失败重试；持续暴露待保存状态。flush 抛错、未启用或原始 get 不可用时，返回值不得被误解为已保存。可返回 remaining、attempted、mode、errors 等明确结果；这些是接口建议。
2. P0：补全 SDK set/get/remove/clear 的失败契约，缺失与读取故障分开；每键捕获，只有对应版本实际写删成功才清 dirty；删除和 clear 覆盖所有应用拥有键。
3. P0：确定宿主、URL 数据与本地模式的唯一存储归属；处理延迟握手和 SDK 更换，安装与 resume 注册各只发生一次，原始方法绑定正确。禁止为方便重试而把旧本地档自动迁入宿主。
4. P0：奖励采用稳定事件去重和完整快照事务；确认“已领取”“余额变化”“保存成功”的对外语义，分别处理未持久化和事务不完整。
5. P1：若实际存在异步、重入、多标签页或多用户切换，加入代次、revision 与协调机制；不要把这些假设误报为已发生缺陷。
6. P1：在确有需求时增加有限退避或明确重试入口；resume 不是必达事件，不能作为唯一持久化时机。异常需要可诊断记录，但不要记录完整敏感存档。
7. P2：提供新版 local-save.js、SDK 契约和生命周期接线后，再做实际实现核验和故障注入。当前无需为完成描述评估暂停索取新版。

## 后续验收条件（未执行）

- SDK set 抛错、get 抛错或返回异步值时，不写错值、不误删、不虚报成功；连续同键更新最终以最新已接受版本为准。
- 本地 set/remove/get 分别失败；dirty 读取不泄露旧值；恢复后逐键重试成功才清理。覆盖空字符串、0 的序列化字符串、真实缺失及坏档。
- clear 在第一个、中间、最后一个键失败后，不复活旧档，也不影响非本应用键。
- 三键中一键失败，其他键仍可尝试，剩余计数准确；重入和异步情况下旧成功不能清除新 dirty。
- 连续 resume、多次安装、安装后延迟握手、URL 参数空值与解析失败、SDK 实例替换，均不产生重复包装或跨模式污染。
- 奖励重复回调、每个提交边界崩溃、重载及余额和领取标记不一致时，按明确恢复协议处理；不能只断言 flush 返回0。
- 写失败后立即刷新应如实展示可能丢失的状态；验证恢复来源，不以同一页面内存测试冒充跨会话恢复。
- 若承诺多标签页或多账号，额外验证旧会话不得覆盖新档。
