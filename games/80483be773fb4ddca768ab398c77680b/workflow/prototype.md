## 3. 关键参数与调用上下文核对

### 3.1 键长度与负样本口径

`strikerProperties` 为17个 ASCII 字节：`striker` 7字节，`Properties` 10字节，大小写敏感。字符串长度17通常不包括结尾 NUL；带终止符的存储可能占18字节。不能把分配容量、C字符串终止位置、编码后的标签值或字符数自动等同于比较器使用的字节长度。

20个“长度17”的候选只是解码规则筛出的子集。除非所有277节点都被成功且正确地解码，且长/短字符串分支均覆盖，否则其余257节点也不能直接当作“已排除”。不能从277/20给出漏检概率或统计置信度；这里没有随机抽样或已知检测灵敏度模型。

### 3.2 `+0x40` 与 `+0x188` 的相加只有条件成立时有效

算术为：`0x40 + 0x188 = 0x1c8`。设 `M` 是已确认的 manager 地址，`R` 是 `0x26c1814` 的真实接收对象，查找基址候选为 `B=R+0x188`。

- **仅当 `R=M+0x40` 是同一对象中的内嵌子对象地址且未再调整时**，才有 `B=M+0x1c8`。
- 如果 `manager+0x40` 是存放指针的字段，则可能是 `R=*(M+0x40)`，不是地址直接相加。
- 如果 `0x26c25d0` 返回配置节点、包装器、引用或另一个 manager，随后以该返回值调用 `0x26c1814`，应追踪这个实际返回值作为 `R`。
- 如果存在解引用、基类调整、thunk、缓存或分支，必须纳入对象流；反编译器的命名与伪代码参数不能代替调用点证据。

因此两个偏移恰好相加吻合，只能使 `M+0x1c8` 成为优先核验候选，不能证明扫描了 `strikerProperties` 实际查找的容器。

### 3.3 调用链不能简化成“这里一定有这个键”

需分清 `0x26c25d0` 是查键、取子树、变换接收对象，还是其他包装操作。`strikerProperties` 可能属于外层选择，`extraMaxPower` 属于所得对象内层字段；摘要未给出第二个查找的真实键参数。

线性先后调用不证明每次业务动作都走这条路径，也不证明返回值被用作下一次接收对象。要核对：调用点分支、各实参的来源、返回值传递、空值/异常处理，以及最终 `extraMaxPower` 的读取或默认值分支。未核对前不得推断 getter 使用被扫容器、未命中意味着默认值，或某个常量就是实际生效值。

## 4. 节点结构核对

### 4.1 哈希链表的合理性不等于 ABI 证明

`base+8` 桶数、节点 `+8` 缓存哈希、节点 `+0x10` 进入比较器，与某些64位链式哈希表实现相容。277为质数，且候选 size/bucket_count=1；两者是合理性检查，不是字段布局证明，也没有证明最大负载因子、next偏移、桶指针语义或完整覆盖。

某些 libc++ 哈希表的桶保存的是桶段前驱，head 是哨兵中的 next，全局链表由桶段连接；不能默认桶项就是桶内首节点，也不能默认非零head是可直接解码的真实节点。不同版本、ABI、压缩pair和自定义容器均可改变布局。需先由实际查找与插入/构造代码限定结构，不能据“看起来像 unordered_map”套统一偏移。

### 4.2 `node+0x10` 不等于“那里存放键字符指针”

“将 `node+0x10` 传给比较器”可能是传内嵌键对象地址，而非加载这个位置的64位值作为字符指针；也可能是 pair 起点、包装器或字符串视图。必须区分 address-of 与 dereference，并核对比较器实际从哪一位置取得长度与字节。

libc++ 字符串存在短/长分支及 ABI 布局差异：标签位置、位含义、长度编码、指针位置、容量字段和字节序不能仅凭名称决定。17字节在某些常见64位实现中能放入短字符串，但实际对象仍可能使用长表示，不能只查短分支。控制读取17字节的 ELF 字符串不测试这些分支。

### 4.3 `node+0x18` 的返回语义与字符串假设必须解释

如果同一个节点的 `+0x10` 真是一个占24字节的内嵌字符串对象，那么其范围是 `[node+0x10,node+0x28)`；`node+0x18` 位于其中。对于通常的 `pair<const string,T>` 节点模型，独立 mapped value 不应仅在键起点后8字节开始，24字节键结束及对齐后才是候选位置。

这不是已证实的矛盾，因为“同一个节点”“24字节字符串”“返回独立mapped value”都尚未证明。可能解释包括：键是8字节句柄、node在包装层已调整、返回的是内部成员地址、比较器解引用了包装类型，或摘要省略了指令。审查应要求把三者在同一对象坐标系下对齐，而不是凭猜测把 `+0x18` 改成 `+0x28`。
