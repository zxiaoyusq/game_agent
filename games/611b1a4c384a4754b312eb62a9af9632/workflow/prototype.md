# Carrom 资源观察者与配置传递静态分析

## 范围与结论

当前阶段为原型定义，按用户明确要求交付只读原生分析。交付文件为 `/workflow/prototype.md`。本轮实际读取归档清单、manifest 和选定分析文本，未执行原生库、重组 ELF、反汇编新增地址或观察进程。下文所有地址使用 ELF link VA。

操作者提供的新增结果支持一个条件性解释：接收函数通过参数对象的虚函数槽取得名称，比较输入名称，相等分支进入后续处理并保存另一个输入。若该参数对象在调用时的有效虚表地址点确为 `0x27eb928`，且槽内容和返回语义核对成立，则当前 `+0x28` 匹配候选为 `ValueMap.plist`。`GameConfiguration.plist` 是另一槽 `+0x30` 的返回候选，其进入此调用链仍缺少独立证据。

## 对象与回调布局评估

### 接收函数的角色与字段

在用户描述成立的前提下，`0x1e41c9c` 可暂记为名称匹配及数据接收函数。先用 receiver、nameInput、payloadInput 作为分析标签，具体 C++ 类型继续待定。AArch64 的 x0–x7 参数位置须由调用点和函数序言共同恢复，调用后的 x2、x3 可能已被覆盖，因此报告中的输入 x2/x3 指函数入口值。

`receiver+0xb8` 是输入内容的复制目标候选。复制操作需要进一步区分字符串赋值、容器复制、引用计数句柄复制或其他结构操作。`receiver+0xf0` 是状态字段候选，具体位宽、写入值、读取点和复位条件决定其语义。现有描述尚不足以命名为 loaded、ready 或 decrypted。还需确认两处偏移都相对于同一个 receiver，及 receiver 是否已经经过基类子对象调整。

需从 BL 前后恢复 `0x1e41b0c` 的参数及返回值使用。后续复制和标记只能构成静态分支结构线索，处理失败条件、异常出口及持久化语义仍待核对。

### 虚函数槽

若 vptr 中保存的有效地址点为 `0x27eb928`，按 8 字节指针计，`+0x28` 和 `+0x30` 分别对应第 5、6 个零基槽。其槽单元位置分别为 `0x27eb950` 和 `0x27eb958`。槽编号包含 ABI 产生的虚函数条目，不能直接对应源码声明序号。需要解析这两个单元的重定位，再反汇编最终目标及可能的 this-adjusting thunk。

有效地址点必须来自对象 vptr 写入或明确的构造数据流。符号起始地址、vtable 头和实际地址点之间可能有差值。实际对象还可能使用派生类表、次级表或构造期间的表。必须把 receiver 的身份、当时使用的地址点以及槽目标绑定起来。

### PackageObserver 邻近区域

按常见 AArch64 Itanium C++ ABI 64 位绝对指针布局，若 `0x27ebc00` 经验证是 type_info 对象，则 `0x27ebc00` 应为其 ABI 类型虚表指针，`0x27ebc08` 为名称指针。`15PackageObserver` 与长度前缀类型名称形式相容。还需核对首字段目标和 type_info 的具体类别。

同理，`0x27ebbf8` 的名称指针使 `0x27ebbf0` 成为 AssetPackageObserver 的 type_info 起始候选。其基类信息取决于实际 RTTI 类别，应解析 `__class_type_info`、`__si_class_type_info` 或 `__vmi_class_type_info` 的对应结构后判断继承关系。字符串相邻不能确定继承方向。

若 `0x27ebbc0 → 0x27ebc00` 是虚表头的 type_info 单元，则其前一个 8 字节单元 `0x27ebbb8` 应能解释为 offset-to-top，有效地址点候选为 `0x27ebbc8`。在这一假设下，`0x27ebbd8` 位于地址点 `+0x10`，形成指向 `0x1e461e0` 的第三个零基函数槽候选。需核对前后条目、段属性和 vptr 写入才可接受此解释。

这组地址尚未把 `0x27eb928` 与 PackageObserver 或 AssetPackageObserver 绑定。`0x27ebbd8` 指针单元本身也未证明它是回调注册项。若 `0x1e461e0` 起始的函数经内部 `0x1e46240` 调用接收函数，则可以形成“候选虚函数体 → 名称匹配接收函数”的静态边，但必须核对 `0x1e46240` 究竟是 BL 指令位置、函数入口还是当前记录的范围标签。FDE 仅用于辅助确定范围。

## 两个文件的独立路径

|路径|当前支持|缺少的关键连接|
|---|---|---|
|ValueMap.plist|操作者报告地址点 `0x27eb928` 的 `+0x28` 返回该名称，接收函数调用相同偏移|实际 receiver 使用该地址点、比较输入确为该名称、对应分支及载荷来源|
|GameConfiguration.plist|旧归档存在字符串和 12 字节引用候选，操作者报告同地址点 `+0x30` 返回该名称|`+0x30` 的真实调用者，或其他动态对象的 `+0x28` 返回该名称，以及该路径如何连接接收函数|

若地址点、函数目标和数据流复核成立，ValueMap 具有更直接的槽偏移匹配线索。GameConfiguration 可以通过调用 `+0x30` 的独立逻辑、另一动态类型对 `+0x28` 的实现或后续已证实的数据转交进入相关系统，各种可能性均需分别找边。

静态候选链按以下边界记录。

```text
候选表单元 0x27ebbd8
  → 0x1e461e0                        [操作者提供的重定位]
  → 内部调用位置/范围 0x1e46240      [入口关系待核]
  → 0x1e41c9c                        [操作者提供的直接调用]
  → receiver.vptr[+0x28]             [动态表待定]
  → 名称比较
  → 相等分支 0x1e41d14
  → 0x1e41b0c
  → 复制输入至 receiver+0xb8，置 +0xf0
```

只有当 receiver 的地址点实际为 `0x27eb928` 时，才能将其中的 `+0x28` 候选标为 ValueMap。图中的每条边仍保留本机结果待复核身份。GameConfiguration 的 `+0x30` 当前单独保留，尚缺接入上述图的边。

## 精确可复核步骤

以下是交给具备 ELF 工具的操作者执行的静态步骤，本轮尚未执行。分析过程中保持原文件只读，导出记录保留原始字节、工具版本、地址类别和文件 SHA256。

1. 校验身份。逐片计算 SHA256 并与 manifest 比较，按 part000 至 part005 顺序拼接到独立研究副本，确认大小 49,000,000 字节及整体 SHA256 `4cf2ba474fc9aefda142fbdca46cf7b4d3ebf06a2114ecd8487a3e48448710b4`。任何不匹配均须重新定位全部地址。
2. 导出 ELF header、PT_LOAD、节表和重定位表。每个 link VA 使用所属 PT_LOAD 映射到文件偏移，公式为 `p_offset + (VA - p_vaddr)`，并要求 `0 <= VA-p_vaddr < p_filesz`。保留段属性，避免把零填充区当作文件字节。重定位记录须含 location、type、symbol 和 addend。
3. 导出 `[0x27eb900, 0x27eb980)` 及 `[0x27ebb80, 0x27ebc60)` 的原始字节和全部覆盖重定位，按 8 字节逐单元列出。对 RELA 记录应用其实际类型的语义。若为 `R_AARCH64_RELATIVE`，记录运行时表达式 `load_bias + addend`，静态链接地址关系使用 addend。其他类型按符号规则解析。
4. 针对候选 `0x27eb928` 检查 `0x27eb918` 的 offset-to-top 和 `0x27eb920` 的 type_info 指针，逐个导出 `0x27eb950`、`0x27eb958` 的真实目标。反汇编目标的完整控制流，核对最终返回的字符串或对象表示，保留返回构造及 thunk 的 this 调整。将 GameConfiguration 目标与旧 `0x1e3f710` 候选做地址及机器码对照。
5. 针对邻近表检查 `0x27ebbb8`、`0x27ebbc0`、`0x27ebbc8` 至 `0x27ebbe8`，验证表头解释。检查 `0x27ebbf0`、`0x27ebc00` 的 ABI 类型虚表指针及名称指针，按实际 RTTI 类别解析基类项。遇到相对虚表或其他编码时按实际 ABI 重新计算，保留候选解释被否定的证据。
6. 导出覆盖 `0x1e41b0c`、`0x1e41c9c`、`0x1e41d14`、`0x1e461e0` 和 `0x1e46240` 的完整函数候选范围。以符号、分支、返回及 FDE 共同恢复边界，包含全部分支出口和被调用目标。记录每条 BL/BLR/尾跳转的准确地址。
7. 为 `0x1e41c9c` 建立逐指令数据流表。至少跟踪入口 x0–x3、callee-saved 副本、栈溢出保存、vptr 读取、槽目标、调用返回值、长度与内容比较、匹配及不匹配出口。确认短路条件、字符串实际长度及比较 API，恢复 `0x1e41b0c` 的参数和返回值用途，标明 `+0xb8` 与 `+0xf0` 的对象基址、访问宽度和写入常量。
8. 从 `0x1e461e0` 覆盖的函数追踪接收者与参数。明确 `0x1e46240` 的角色，核对 x0 是否来自成员、捕获对象、基类调整或其他 owner，x2/x3 如何由入口参数获得。导出构造函数中所有相关 vptr 写入及后续替换，搜索地址点引用时同时覆盖 ADRP/ADD、literal load、GOT、重定位和间接转移。仅扫描直接 BL 的阴性结果保留覆盖限制。
9. 独立追踪 ValueMap。找到 `+0x28` 的实际接收类型、名称参数来源和载荷输入生产者，逐边证明直到 `+0xb8` 保存目标，记录每边函数、指令位置、条件及字段偏移。
10. 独立追踪 GameConfiguration。优先查询 `0x27eb958` 目标的代码及数据引用和使用同一地址点 `+0x30` 的调用者，再查派生表的 `+0x28` 实现。若存在独立加载分支，保存其输入输出、owner 与下游调用。只有出现明确转交边时才连接两条路径。
11. 追踪 `+0xb8`、`+0xf0` 的读取和复位。确认这些偏移所属对象布局后，查构造、销毁、赋值、消费者及回调触发点。以字段数据流说明后续是路径、原始字节、解析对象还是缓存句柄，业务命名逐项绑定证据。
12. 如需判断配置处理或加密，继续从各自载荷的真实消费者追踪到解析器或变换函数。`decryptAES128` 字符串只作独立定位线索。算法调用、参数来源和输出解析均须有可达数据流证据后才能作相应结论。当前任务没有密钥结论或解密成功结论。

每项补证建议保存 JSON 行或表格，包含 ELF 哈希、link VA、文件偏移、原始字节、指令、重定位、数据来源、条件、结论和未决项。静态路径即使补齐，也只说明对应机器码中的条件路径。
