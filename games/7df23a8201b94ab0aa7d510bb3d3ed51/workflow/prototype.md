## 3. PT_LOAD 映射应如何成立

对 link VA `v` 的一条四字节记录，应在同一个文件覆盖的 PT_LOAD 中满足：

```text
p_vaddr <= v
v + 4 <= p_vaddr + p_filesz
offset = p_offset + (v - p_vaddr)
0 <= offset
 offset + 4 <= ELF 文件实际长度
```

候选段唯一性应针对**整条四字节区间**检查，不是只检查首地址，更不是要求整个 ELF 只有一个 PT_LOAD。没有候选或有多个候选都应报错，不选第一个段继续。应检查 ELF 头和程序头边界、数值及段大小是否合法；异常输入不能靠 Python 切片短读后静默通过。

- `p_memsz` 超过 `p_filesz` 的区域可能是 BSS/零填充，没有对应文件字节。仅满足内存范围不足以读取原文件指令。
- 若声称这些记录是代码，应核对该段 `PF_X`，以及文本范围/边界的来源。可执行权限仍不证明其中每个四字节都是实际指令，更不证明执行可达。
- E-01 的 14 条 link VA 和 file offset 数值相同。在上述公式有效的前提下，只能说明所选段的 `p_offset = p_vaddr`；**不能把 VA=offset 当作通用规则**。本轮未读取程序头，不能确认该等式的段依据。
- 必须区分 ELF link VA、文件偏移和 runtime VA。运行地址另需已配对模块的 load bias；本轮不计算 runtime 地址。
- 文件映射不依赖节头作为唯一依据；节表可补充代码范围来源，但不能代替 PT_LOAD 文件覆盖检查。

方法选择 pyelftools 是合理的格式解析路线，但“用了 pyelftools”本身不能证明调用方实现了上述边界与唯一性断言。

## 4. 零字节差异能说明什么

若完整输入配对且脚本可复现，零差异支持：对于**实际比较到的那组地址记录**，清单中的四个字节与该 ELF 经有效映射取得的四个字节相等。这有助于排除该组清单记录的字节抄录错误、部分陈旧字节或对应位置的文件差异。

它不单独证明：

1. 286 条是 286 个唯一地址，所有预期行均已解析，或不存在重复、跳行、隐藏失败、范围截断。
2. 整个 ELF、整个函数或全部调用者被覆盖。286 次四字节比较是 1,144 字节的比较工作量，可能包含重复或重叠，不能称为 1,144 个唯一覆盖字节。
3. 清单中的助记符、寄存器、立即数、寻址模式或 PC 相对目标文本正确。若只比较 bytes 列，就没有检验 disassembly 文本列。
4. 函数起点、FDE 边界、对象身份、字段类型、参数签名、符号命名或业务归属正确。
5. 二进制来自所声称的原游戏版本、真实安装包或目标进程。完整 SHA-256 若独立重算，可锚定一个文件身份，但不提供来源真实性或运行副本配对。
6. 指令被执行、分支被走到、内存地址有效、CPU 支持相关扩展、外部调用成功，或结果与原游戏一致。

若清单与第二次解码来自同一生成链，例如都使用相同 Capstone 版本，则不能将“重新解码”自动称为独立解码器交叉验证。原始文件字节比较仍有价值，但它检验的对象与独立性必须说明。

## 5. 286 条均解码的准确边界

AArch64 指令固定四字节。应记录 ELFCLASS、`e_machine`、`EI_DATA` 与 Capstone 架构/端序选项、版本、CPU 扩展相关限制，并将正确 **link VA** 作为每次解码地址传入。

每次结果应明确断言：恰好返回 1 条、`instruction.size == 4`、`instruction.address == link_va`、`instruction.bytes == 原始四字节`。关闭或明确记录 skip-data 等伪指令替代机制，禁止把 `.byte`/数据占位输出算作指令成功。

“能解码”只说明在该配置下解码器接受这些位模式。对齐的数据、填充、不可达代码也可能全部可解码；单条解码不建立连续控制流或真实指令边界。即使输入符合 `v % 4 == 0`，仍需额外范围来源才能认为是代码。

若想检验原清单文本，还须对指令 ID、操作数类别、寄存器、宽度、立即数、内存位移及写回等作结构化比较。`mov` 等别名、十六进制格式、空格差异应正规化，不据此误报不同；也不能因字节相同忽略错误的操作数文本。PC 地址传错时，分支或 ADRP 可能仍成功解码，却显示错误目标。

E-05 的范围长度 `0x3e4`，按四字节连续铺满对应 **249 个槽位**；E-06 的范围对应 756 个槽位。不能仅凭任一文件名或范围把摘要的 286 条计数闭合，应提交实际选取行及计数对账。前七条所在窗口不在 ZIP 清单列出的那些反汇编文件范围内；本轮没有为它们找到直接窗口证据，不能补写“已核对”。

仅作架构语法边界提示，不解释业务：

- `adrp` 生成与当前 PC 页相关的地址，不等于读取该地址的内容；后续 `ldr`/`str` 的对象和值需独立追踪，不能将 `0x2ec2000 + 0x920` 命名为某业务全局对象。
- `b` 不是 `bl`；目标等于某候选起点不证明普通函数调用、尾调用归属或实际执行。
- E-05 在 `0x18b3414` 还有 `010c42f8 ldr x1, [x0, #0x20]!`。若仅按相邻文本描述且该序列实际执行，`!` 表示基址写回，后续 `str x20, [x0]` 使用的是更新后的基址；不能从 `mov x0, x19` 直接认定写入旧 x19 的零偏移地址。
- `0x18b34bc` 的预索引也写回 x19；`0x18b34d0` 又将 x19 设置为 `sp+0x38`。同一寄存器名不代表跨范围保持同一对象身份。
- q 寄存器搬运 128 位数据不证明数据为向量、两个浮点数或物理量；栈位移和写入宽度不提供业务字段名。

这些提示来自 ISA 语法和所读文本，不是本轮 Capstone 执行结果，也不构成运行路径分析。

## 7. 必要反证与负向检验

以下均是**后续应执行而未执行**的检验，不代表当前输入已经发现这些故障。只在只读原件之外的独立测试夹具上构造反例，不修改项目或参考 ELF。

| 检验 | 应观察到的结果 / 要排除的误判 |
|---|---|
| 所选位置翻转一个字节 | 完整文件身份发生变化；若继续在专用比较测试中执行，应报告精确 byte mismatch，不能仍报零差异 |
| 仅改清单 bytes 一位 | 比较失败；即使变更后还能解码也不能掩盖字节差异 |
| 仅改助记符、寄存器、分支目标或去掉 `!` | bytes 检查可能仍通过；新增结构化文本检查必须发现不一致，证明两种门禁不可混同 |
| 删除、重复一行，插入畸形行或截断末行 | 预期条数、唯一地址数、解析拒绝数对账失败；不能跳过后以“全部已处理行通过”冒充全量 |
| 选择没有文件覆盖、仅 BSS、最后不足四字节或文件短读的地址 | 明确拒绝，不映射零填充，不接受部分记录 |
| 构造两个 PT_LOAD 同时覆盖四字节窗口 | 明确歧义失败，不采用第一个匹配段 |
| 构造 `p_vaddr != p_offset` 的合法映射夹具 | 正确计算非同值偏移，捕捉直接 `seek(link_va)` 的错误实现 |
| 非四字节对齐、错误端序/架构、skip-data、少于四字节解码输入 | 对齐/配置门禁或精确 size 门禁失败；不能只看返回对象是否非空 |
| 同一 bytes 用错误 PC 地址解码 | 可解码数可能不变，但 PC 相对目标改变；正确地址和结构化目标检查须识别问题 |
| 调换分块顺序或截断一个 part | 分块完整性/重组尺寸/完整 ELF 哈希门禁失败；正确分块哈希集合不等于正确拼接 |
| 比较范围外另改一字节 | 所选清单仍可能零差异，完整 ELF 哈希改变，说明局部比较不证明全文件相等 |
| 可解码数据或不可达代码夹具 | 即使全部解码成功，也不能输出可达性或业务行为结论 |

## 8. 后续静态检验顺序及验收条件

1. **固定输入身份**：提交这次使用的脚本全文及 SHA-256、完整命令、退出码、Python/pyelftools/Capstone 版本、平台、清单路径及哈希。脚本必须只读目标，失败返回非零；旧报告所引用脚本不自动替代这次脚本。
2. **闭合分块与 ELF 身份**：按 manifest 显式次序校验六块尺寸/哈希，重组到审核用独立副本，实测 48,998,992 字节并独立重算完整 ELF SHA-256。记录 ELF 头、程序头和实际模块名称；名称不替代哈希。
3. **闭合 286 条输入**：提交每条源文件/行号、link VA、expected bytes，记录原始行数、解析成功数、拒绝数、唯一地址数、重复/重叠数、每个范围预期/实际数量和覆盖空洞。每个排除必须有明确理由，不用总数隐藏漏行。
4. **闭合地址映射与字节比较**：逐条输出段索引、`p_vaddr/p_offset/p_filesz/p_memsz/p_flags`、计算偏移、expected/actual bytes、映射唯一性、短读与比较状态。要求 286 条记录对账一致，零未解释解析/映射错误，零 byte mismatch。存在重复时明确统计，不把记录数当唯一覆盖数。
5. **闭合解码与文本一致性**：输出每条解码地址、size、bytes、指令 ID 和详细操作数；恰好一条四字节、无数据占位。分别报告“可解码数”与“清单语义操作数一致数”，正常化别名。选关键 PC 相对目标、宽度及写回与第二个独立解码实现/ISA 编码规则核对，记录工具版本和分歧处理。
6. **边界与负向检验**：执行第 7 节夹具，保留输入/输出哈希及预期失败的真实退出码。独立静态复核最多提升为“该哈希文件、该地址记录集、该配置的静态校验已复现”，不能提升为原游戏验证。

验收以逐条整数地址和四字节完全相等为准，不设浮点容差、指令容错或模糊匹配。反汇编排版/合法别名可正常化，但操作数语义不得容错。审核循环为输入身份 → 地址映射 → 字节比较 → 解码 → 负向检验 → 分层结论，不是玩法核心循环。
