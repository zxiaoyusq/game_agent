# Carrom 季票与离线奖励边界复核

日期：2026-11-12；阶段：原型定义／静态工程分析；attempt=1。

## 1. 结论与证据口径

本次 H5 包的首要问题是保存能力边界，而非季票数值。直接读取可确认：业务经 GameSnacks.storage 保存七个字段；game.html 加载 developer_v2.js 时没有 data-target-origin，SDK 因此使用空消息处理器且 channel=null，setItem 仅更新当前 SDK 实例的内存字典。按包内启动路径静态推导，保存调用返回不代表跨刷新持久化。没有运行浏览器，不能把该推导表述成已复现丢档。

胜局基础奖励在创建结算窗口后即增加金币并调用保存，普通 Claim 按钮负责关闭结果界面；转盘在动画结束时增加金币、更新时间并保存。两条奖励链均未见持久化事务 ID 或领取流水。广告链还有配置与协议不匹配，不能依据广告按钮代码认定当前部署可兑现加倍。

当前完整主业务脚本中未定位到与用户描述相对应的季票免费轨、三级任务替换、任务宝箱进度或 CP 映射实现。不能将竞品观察中的 +200、+250、+10 套进本 H5，也不能将棋盘 Queen 对勾或商店装备勾误认为季票领取标记。

## 3. 启动、加载和存档调用链

【直接代码】`index.html` 的 `iframe#「iframe」` 以 `src="game.html"` 启动，未附 gameData。game.html 依次加载 developer_v2.js、Howler、Pixi、Planck 和 js/game.js；主脚本 `box2d = planck`，使用 PIXI.Application。不能因本轮框架标签是原生 Web 就把参考实现称为纯 DOM 或无引擎实现。

业务链：`game.init → _0xc37276 → _0x358d16 → _0x16b945 → _0x3690db → _0x5ecd40 → _0x13b722`。`_0x3690db` 先读存档，再创建业务界面。

| 可搜索符号 | 输入／输出与实际职责 |
| --- | --- |
| `_0x23207e` | 存档模板：tables、upgrades、strikers、stones、coins、tutorial、lastRewardTime，共七项 |
| `_0x5ecd40` | 遍历模板键，GameSnacks.storage.getItem；取到真值字符串后 JSON.parse，最后调用 `_0x13b722` |
| `_0x13b722` | 将 coins 赋给运行时 `_0xa07851`，tutorial 赋给 `_0x183856`，时间转 Number 赋给 `_0x6d1a83`；恢复数组及装备索引 |
| `_0x9b0cd` | 运行时字段与装备数组回填 `_0x23207e` |
| `_0x3a0318` | 先回填，再逐键 JSON.stringify 后调用 GameSnacks.storage.setItem；未见业务层 try/catch、版本校验、写入确认或失败提示 |

coins 模板默认 0；虽然 `_0xa07851` 早期声明为 1000，正常 `_0x13b722` 会用模板／读取值覆盖它。因此不能把早期声明的 1000 当作最终新账号赠送。

【直接代码】developer_v2.js：

1. `Pn.ba` 从 document.currentScript 读取 `data-target-origin`。
2. 缺失时打印 `Couldn't find targetOrigin...`，选 `new Jt`，且消息 channel 保持 null；`Jt.prototype.send/u` 均为空。
3. `Gt` 创建 `storage=new Dt(channel)`。`Dt` 用 hash／query 中的 gameData 初始化 `this.g`，过程为 decodeURIComponent、atob、JSON.parse。
4. `Dt.prototype.getItem` 从 `this.g` 读取；`setItem` 在 channel 存在时发送消息，随后执行 `this.g[t]=n`。返回处没有持久化 ACK。
5. SDK 重定义 window.localStorage 的 getter 并抛错，提示使用 GameSnacks.storage；不能建议在当前加载方式下直接调用该全局作为现成修复。

【静态推导】本包 HTML 未提供目标 origin，默认入口又未传 gameData，因而默认 SDK 读写只有当前实例内存语义。外层 index.html 已读 message 分支仅处理 next、gameLoadingCompleted、reward，没有实现上述存档通道。外部 adsdk_1.8.0.0.js 未包含在所列本地脚本中且未读取；外部运行时是否改写行为未知。即便未来补 target-origin，也仍需真实宿主处理协议、持久化和恢复输入；增加一个属性不足以证明修复。

坏档风险：`_0x5ecd40` 未捕获字段 JSON.parse 异常；`_0x13b722` 未校验数组类型、长度、金币有限非负整数或升级范围。合法 JSON 的 null、错误类型和超长数组也可能破坏恢复。七键顺序写入缺少业务原子性；当前内存分支没有真正落盘，但未来接宿主后必须检查部分写入风险。

## 4. 实际奖励与消费调用链

### 4.1 对局与胜局

【直接代码】选桌 UI 根据 `_coins >= fee` 控制按钮；业务 `_0x4d0a10(id)` 只检查 id 是否超过数组长度，设置桌号／先手，扣 fee，调用 `_0x3a0318`，随后匹配与开局。未见业务层对负索引、整数类型、余额再校验；不能把 UI 禁用当成规则层完整防线。

`_0xbdafb3` 等待物体静止，处理进球／犯规并判胜负，调用 `_0x47e567(win)`。后者创建 `_0x51b412` 结果窗口；win=true 时直接执行 `_0xa07851 += _0x1ac80c[_0x408018].prize` 并保存。普通结果按钮在 `_0x51b412` 内监听 pointerdown、emit close；外层 close 回调移除窗口、返回选桌并播放金币表现，没有再加基础金币。

| 桌号 | fee | 胜局 prize | 一次正常胜局净变化（未加倍） |
| --- | ---: | ---: | ---: |
| 0 | 0 | 50 | +50 |
| 1 | 50 | 125 | +75 |
| 2 | 200 | 400 | +200 |
| 3 | 750 | 1500 | +750 |
| 4 | 5000 | 10000 | +5000 |

败局 `_0x47e567(false)` 不加 prize；入场费已提前扣除。关闭弹窗与提交奖励是不同时间点。未见 `_0x47e567` 函数自身对 roundId／settled 的拒重条件；调用方有 `_0x3fddb3` 等生命周期判断，但不能据此证明重复结束回调永不重复发奖。正常点击 Claim 不再加钱，也不能证明直接重复结算或旧回调安全。

加倍分支：结果窗 emit ad → 隐藏广告按钮 → `_0x4d02b5(callback)` → 成功布尔值为真时额外加当前桌 prize 并保存。回调读取的是可变全局 `_0x408018`，不是独立冻结的奖励事务快照；需测试旧回调跨局和重复 success。

### 4.2 免费转盘

【直接代码】大厅 Bonus emit → `_0x10184d` 显示转盘 → spin 事件 → `_0x50f739` 禁用控制并按权重选择颜色 → 动画完成 `_0x5b20b9(color)`。该函数先加 `_0xffce48(color)`，记录当前 Date.getTime 到 `_0x6d1a83`，置 `_0x530cb1=false`，调用 `_0x3a0318`，再展示奖励窗口。奖励窗 Claim 使用 once 监听；Claim 是退出与表现触发，不是基础加币点。

颜色奖励为 purple=200、blue=50、green=100、red=50、yellow=500；权重分别 3、15、6、15、1，总计 40。权重是本 H5 配置，不是竞品概率，未通过抽样验证分布。

`_0x66b857=4*60*60*1000`，四小时冷却。`_0x4c7a25` 计算 now-lastRewardTime，采用严格大于冷却值时置可领；刚好相等尚不进入该分支。大厅周期检查和 UI 允许态限制入口；`_0x50f739`、`_0x5b20b9` 未见独立检查冷却资格或持久化领取 ID。系统时间前拨、回拨、未来时间戳均需验证。这是时间门槛转盘，未见按离线时长累积金币的实现。

转盘广告加倍在 `_0x5b20b9` 的 ad 回调中成功后再加同一颜色奖励并保存；未见事务消费标记。

### 4.3 广告适配并未闭环

【直接代码】`_0x2e33a4` 调 GameSnacks.ad.break(type=reward)，beforeReward 保存展示函数到 `_0x420004` 并设置可用标记；`_0x4d02b5` 把业务回调存到单一 `_0x38b273`，调用展示函数。adViewed 直接调用该回调 true；adDismissed 调 false；afterAd 才清空回调并恢复 ticker。未见请求 ID、完成锁、超时和旧局校验。重复 adViewed 在清空前可能多次进入加币逻辑，这是静态风险，未实际注入复现。

SDK `Pn.ga` 读取 data-rewarded-monetizable／data-interstitial-monetizable；当前 game.html 均未设置。`it.prototype.break` 仅在对应属性满足时向 adsbygoogle 推入参数，仍会发 AD_BREAK 消息，但当前 Jt.send 为空。故当前正常 SDK 配置下 beforeReward 可达性有明显断点，不能宣称按钮广告可用。

外层 index.html 另有字符串 reward → h5sdk.adBreak → rewardSuccess／rewardDismissed／rewardFailed 协议。已读主脚本未定位到对应的字符串发送与回执接收链；不能把这条外层协议与上述 `_0x38b273` 回调自动视为已连接。外层 message handler 未见 evt.origin／evt.source 校验，回执也未携带业务请求 ID。

业务还定义备用 `_0x434610`，只在 window.GameSnacks 不存在时采用：storage 方法为空，reward 的展示函数会直接调用 adViewed。当前正常 HTML 已先加载 SDK，不应把该备用分支当正常广告实测；它也不能提供可靠离线保存或真实观看凭证。

### 4.4 金币点击与消费

【直接代码】大厅 `_0x28bd7a` 创建金币区域，设 interactive=true，pointerdown emit `hackcoins`（映射索引 0x463）；初始化注册对应事件后 `_0xa07851 += 0x1f4`，即 +500，再调用 `_0x3771eb` 更新大厅。该路径没有直接调用 `_0x3a0318`。后续胜局、转盘、购物等全量保存会将这笔运行时金币一并带入 SDK 缓存；未来持久化接通后可能被顺带持久化。没有证据说明它是受权限保护的调试功能。

商店购买／升级／装备：`_0x900aee → _0x230373` 购买，`_0x900aee → _0x5a5b07` 升级，`_0x3f64a2 → _0x1e3129` 购买棋子，外层更新界面后保存。购买函数有余额判断，升级函数有最大等级判断；这些是具体消费保护，不等于奖励幂等或存档结构校验。

## 5. 竞品单账号观察及不能推出的结论

【用户观察转述】用户提交：三级任务领取金币 2384→2584（+200），任务宝箱 0/50→10/50（+10），任务位替换；季票免费 250 金币领取后 2584→2834（+250），联网重启后保留；对勾项重复点一次，二次重启仍为 2834。

可支持：该账号在所描述流程里展示了对应增量、任务替换、一次联网重启保留，以及一次重复点击后未观察到额外金币。观察没有包含原始截图、操作录像、版本／包名、网络请求或存储数据，本轮未独立复现。

不能支持：所有领取入口／回调／并发场景幂等；金币、任务宝箱进度和 CP 的确定映射；离线领取或离线冷启动可保存；跨设备同步；写失败恢复；季节切换；领取与金币原子提交；服务器权威实现。一次金币不变也不能区分按钮禁用、客户端去重和服务器拒重。联网重启保留不能区分本地落盘与服务器恢复。

【未知】竞品准确产品身份、开发商、版本、账号环境、CP 含义与对应字段。此处不需要为完成 H5 静态审计暂停，但后续 CP 定量实验必须明确 UI 标签和前后值。未查看竞品 APK、未反编译、未连接模拟器、未进行联网检索。

## 6. 低包体离线改进建议（未实施）

优先级 P0：先明确独立离线版与宿主版的存储适配器能力，不能静默把内存写成功当保存成功。离线版使用可用的 IndexedDB 或明确受控的本地存储入口；由于当前 SDK 拦截 localStorage，需在实现阶段处理架构冲突。宿主版使用现有平台规范与真实确认协议。不得假定不同存储后端可无冲突双写。

建议保存单一版本化快照，含 schemaVersion、revision、coins、装备状态、lastRewardTime、奖励资格及已提交事务信息；奖励状态与金币在同一事务提交。以 rewardId 区分 match 基础奖、match 加倍奖、spin 基础奖、spin 加倍奖，未来季票再使用 seasonId+tierId+track，任务使用稳定 taskInstanceId，不能使用会替换的 UI 槽号做唯一键。事务重试必须沿用同一个 ID；持久化成功后才进入 Committed 和播放完成反馈。写失败保留可见提示 `Progress could not be saved. Retry.`，重试不能再算一遍增量。

状态建议：Eligible → Pending → Committed；失败留 Pending／可重试，不显示已完成；Already claimed 返回同一已提交结果。广告使用 requestId、roundId、冻结 amount、一次完成锁及超时，成功／取消／失败互斥；离线无真实观看结果不授予广告加倍。当前备用 SDK 直接成功路径应在未来独立实现中隔离，不作为正式广告凭据。

冷却按持久化时间判定并对异常时钟作明示策略；建议回拨不增加资格，前拨不能保证防作弊，联网可信时间与离线体验如何取舍需产品决策。纯客户端只能改善正常故障一致性，不能承诺防篡改、卸载恢复或跨设备唯一领取。

季票、任务和 CP 暂不补造。若后续决定增加，先定义 CP 来源、任务领取时点、宝箱溢出、任务实例更替、赛季过期与已解锁未领取政策，再接统一事务。UI 建议使用现有风格与英文文案，增加 `Claim`、`Claimed`、`Saving…`、`Retry`、`Offline`；不需要新增位图或大型引擎。低包体目标建议新增逻辑与配置展开不超过 50 KiB、无新增媒体和 CDN，整体部署小于 10 MB；这些均为未来验收预算，未测量实现结果。

独立离线冷启动还需资源缓存方案。game.html 当前尝试注销上两级范围的已有 Service Worker，不是离线缓存实现；index.html 引用外部广告 SDK，因此文件齐备不等于冷启动离线通过。未来可只对自有静态文件设计版本缓存，广告失联不应阻断基础玩法。

## 8. 与物理玩法有关的边界

本轮不重新设计物理玩法。为避免奖励回归破坏终局来源，保留已读基线：`_0x4bf21a` 累积 ticker delta，while(accumulator>1) 逐次 `_0x49d791(1)`；每逻辑步执行 `world.step(1/60,10,10)`，未见该循环补步上限。进洞为棋子与四袋中心距离 ≤20 游戏坐标单位，移出物理世界／数组后处理得分；计分不等同金币。Freestyle 目标 `_0x153877=160`，红／白／黑分值表 `_0x1c2aac=[50,20,10]`；其他模式以九枚及 Queen 状态判终局。具体判定以 `_0xbdafb3` 为索引。

玩家输入以 `_0x55e693 && _0x209883` 等控制轮次，`_0x36ab44` 开始拖动，`_0x536112` 力度限制到 1，`_0x1e39ba` 在 strength≥0.25 时出杆；非首桌回合时间按逻辑步递减。未来奖励验收需验证暂停、快慢帧、重开及旧动画回调只结算一次。建议同浏览器固定输入比较轨迹最终位置允许 1 游戏坐标单位、静止时间允许 2 个逻辑步，金币和事务次数容差为 0；物理容差是建议，未通过试玩校准。

另有 Freestyle 分支引用 `playerScore`／`oponentScore` 的未限定标识符，而运行时计分主变量使用混淆名称；应列入真实运行复现，不在本轮宣称已触发异常。
