## 3. 输入覆盖：实际支持到哪里

### 3.1 UnfouledStrikerComparator

E-02 对 +0x48 写入单字节，遍历 a、b 各 0..255。若普通模式下脚本成功运行并保留断言，这确实穷举了该**两字节输入域**，包括相等、零对非零及不同非零。不能称为对象全部状态、别名、对象有效性或真实布尔域的穷举。

所用公式为：

```
C(a,b) = 0   当 a == b
         -1  当 a == 0 且 b != 0
         +1  其余情况
```

`ordered_distinct_nonzero_pairs=64770` 与 `255×254` 相符。不过脚本中的 `asymmetric_failures` 仅按 `a != b and a and b` 加一，**没有读取 C(b,a) 并对反对称关系做断言**。它是结构性计数，不是独立的反对称失败检测器。反例可由已检查的公式推导；E-01 未保存这 65,536 个逐例实际返回值。

### 3.2 两个 uint32 比较

输入集合为 `{0,1,2,0x7fffffff,0x80000000,0xfffffffe,0xffffffff}`，各做 49 个有序对。E-01 的每个 `examples` 在本次材料中实际包含全部 49 项，而不是只有几条展示样例。

优势：有相等、双向和符号边界，尤其 `(0x7fffffff,0x80000000)` 可区分有符号与无符号解释。

未覆盖：其余 uint32 值、更多相邻值/随机位型、未对齐访问、同址输入、其他内存布局及坏指针。两个完整 uint32 域的笛卡尔积有 2^64 对，49 对不可称为全域动态验证。所附条件码可提供更广泛的静态语义论证，但不是额外运行次数。

### 3.3 两个 binary64 比较

输入集合为 `{-inf,-1.0,-0.0,+0.0,+1.0,+inf,math.nan}`，分别 49 对。它覆盖了数值顺序、同号无穷相等、异号零相等，以及一个由 Python `math.nan` 经 `<d` 打包产生的 NaN 表示。负长度、负力度或无穷是否可出现在真实游戏中，当前未知；这里仅是人工位型测试。

未覆盖：最小/最大正常数、次正规数及正常/次正规边界、相邻可表示值、不同正负 quiet/signaling NaN 与 payload、FPCR 设置变化、浮点异常状态。输出用 `str()`，NaN 的具体位型与 payload 未被保留。不能把这些 49 对称为“所有 IEEE-754 输入已验证”。

## 4. 原始机器码来源与地址链

### 4.1 脚本检查的价值

E-02 先对 `next(rglob('libgame-*.so'))` 选中的整个文件做 SHA-256 断言，再对每行从首个 `file_offset` 开始、长度 `4×指令数` 的原文件切片，与 E-03 的字节拼接作断言。若使用同一份输入、非优化 Python 且断言通过，可支持“本机执行的字节与该哈希文件中的指定切片一致”。`next()` 的选择顺序不固定，但哈希断言可拒绝错误文件；改为明确路径并记录文件尺寸更稳妥。

**核对同一清单的字节，并不同时独立核对该清单的反汇编、函数边界或名字归属。** 所附文本与结果一致，不能替代独立解码器。

### 4.3 名字重定位不等于函数归属

E-03 中 `r_info=0x403`、symbol_index=0、type=1027 与 AArch64 R_AARCH64_RELATIVE 的表达相符；addend 与所列名字地址相同。若真实，加载时目标槽可指向 `load_bias+addend`。这只支持“某个槽引用该名字”，**不直接证明另一处比较片段属于该名字**。

最重要缺口是名字字符串→typeinfo/RTTI→虚表或其他分发表→具体槽位→比较片段，以及函数边界、签名、可能的 thunk/this 调整。相邻字符串或相邻函数地址不能填补这条链。+0x48/+0x4c/+0x50/+0x28/+0x30 当前只能称为片段访问的字段偏移，不能独立确认业务字段名、单位或生产类型。

## 5. 数值语义与反例

以下推导明确**以 E-03 所列指令文本为前提**，由 E-01 对应样例佐证，不声称独立反汇编。

### 5.1 字节片段

`ldrb` 将字段零扩展。以 x1 为 a、x2 为 b：先由 b 是否为零构造符号，再由 a 是否为零选择，最后原始字节相等时归零，得到第 3.1 节公式。

- 二值域 `{0,1}` 上，该公式满足三路比较的反对称及自比归零。
- 完整字节域中，`C(1,2)=+1` 且 `C(2,1)=+1`，不满足 `C(a,b)=-C(b,a)`；也不满足交换输入后的符号反对称。所有不同非零有序对共有 64,770 个，对应 32,385 个无序对。
- 所有相等字节自比均为 0；不能把该反例写成“字节片段没有自反相等”。

不能因此自动写成“真实排序一定坏了”。若未知消费者只使用 `C<0`，这个字节片段对应“零小于任何非零，所有非零属于同一等价类”，该负值谓词本身可构成严格弱序，虽然原始返回值不符合标准三路比较合同。若消费者用 `C>0`、转 bool 或依赖三路协议，意义不同，必须另取证。真实字段若保证只有 0/1，非零反例也可能不可达。

### 5.2 整数片段

`ldr w` 读取 32 位位型，`cmp` 后的 `ls`（unsigned lower-or-same）及 `hs`（unsigned higher-or-same）决定方向，最后 `eq` 归零：

```
+0x4c: C(a,b) = 0 若相等；-1 若 uint32(a)>uint32(b)；否则 +1
+0x50: C(a,b) = 0 若相等；-1 若 uint32(a)<uint32(b)；否则 +1
```

这不是有符号 int32 比较，也不是减法差值返回。两个公式在 uint32 域满足三路比较的反对称、自比归零及相应数值方向的传递性；上传 49 项各与公式一致。不要把返回值方向直接改写为“游戏最终降序/升序”，那还取决于消费者和调用链。

E-02 对 X0 低 32 位取掩码再按有符号解释，适合本片段写 W0 的三路 int 返回。W0 写入导致 X0 高半部清零，因此直接把整个 X0 当 signed64 会误读 -1；当前处理避开了这一问题，但真实返回签名仍需证据。

### 5.3 浮点片段及 NaN

`ldr d` 读取 binary64；`fcmp d0,d1` 后 `csinc ... mi` 使小于时保持 -1，否则取 +1；最后 `eq` 归零。

ARM 浮点比较的 NZCV：小于为 1000，相等为 0110，大于为 0010，无序为 0011。NaN 无序时 N=0、Z=0，MI 和 EQ 均不成立，因而在非陷阱返回路径上为 +1，而不是“NaN 比任意数更大”。

E-01 两项均展示：

- `C(-0.0,+0.0)=C(+0.0,-0.0)=0`，不是位型全序；
- 同号无穷自比 0；
- `C(nan,0)=C(0,nan)=+1`，反对称失败；
- `C(nan,nan)=+1`，自比归零失败。

每个浮点表中有 13 个含该 NaN 的有序输入对（6×2+1），均返回 +1。这是从已展示表和集合大小得出的计数，不是脚本另行统计的性质测试。

NaN 对标准三路数值比较合同构成反例。即使只取 `C<0`，在含 NaN、0、1 的域中，NaN 与 0、1 都不可比较，而 0<1，不可比较关系不具传递性，因而不能视作该全域的严格弱序。这仍只是片段/谓词层分析，**不是已确认存在真实排序调用**。

不能一概外推到全部 NaN 的运行结果：signaling NaN、异常使能、FPCR/FPSR 和模拟器实现可能影响异常状态或是否能正常返回。普通非陷阱路径的 unordered 条件码解释可以静态讨论；具体目标硬件与所有 NaN 位型需要另测。

## 6. 隔离执行方法的可靠处与可能误差

### 6.1 有利于当前短片段的设计

- 代码映射到 CODE=0x100000，人工对象在 A=0x200000、B=0x201000；两个对象区域均在映射范围内。
- 所列片段无 PC 相对访问、分支调用、栈访问或外部依赖；在指令文本属实的前提下，搬移执行位置合理，不需要模拟整个 ELF 装载器。
- x1/x2 固定为人工对象指针，所列片段不修改它们；每次比较会重新加载必要字段并覆盖计算寄存器和 NZCV。复用一个 Uc 实例**不是当前片段已证实的污染错误**，但也不是通用安全策略。
- 人工输入按 `<I` 和 `<d` 写入，消除了宿主默认打包字节序的不明确性；无算术计算误差或减法溢出被引入预期公式。

### 6.2 应优先加固的执行缺口

1. **assert 可被禁用**：`python -O` 或 PYTHONOPTIMIZE 可删除 SHA、字节和 actual/expected 的检查。脚本仍能执行并写出 `formula_failures:0`，因为这个字段是成功路径硬编码，不是累积实测失败数。应改成不可优化掉的显式条件检查、失败计数和非零退出，并记录启动参数。当前没有证据说明上传方用了优化模式；这是可导致假阳性的风险，不是已发生事实。
2. **末尾 ret 没有执行**：`emu_start(CODE, CODE+len(code)-4, count=100)` 的 until 地址是 ret 所在地址，按该 API 停止语义在到达该地址时结束。已计算 W0，可称“返回值计算片段”，不能称“已验证 ret、LR 或完整调用/返回 ABI”。建议用 X30 指向受控返回哨兵并执行 ret，或者明确保留前 ret 停止并读取 PC 断言结束位置。当前 count=100 大于所列片段在 ret 前的 9 或 6 条指令，理论上足够，但没有 PC/指令数记录来证明真实停点。
3. **上下文未完整控制**：没有每用例初始化/记录 FPCR、FPSR、初始/最终 PC、寄存器、异常、内存读写范围或内存权限。对这些简单片段不能凭空断言存在污染；应加入基线恢复、寄存器扰动、随机用例顺序和越界访问监控来排除假设。
4. **没有运行溯源**：无 Python/Unicorn/底层引擎版本、宿主信息、脚本和输入清单哈希、原始 stdout/stderr、退出码及开始结束时间。E-02 末尾有 print 语句，但上传 txt 是源码，不是已打印 PASS 的运行日志。
5. **清单不完整也可能成功**：循环不要求预期五个唯一名称全部存在；`else` 会把未识别名字按浮点分支处理。当前 E-03 确实列出五项，结果也列出五项，但通用探针应验证集合、唯一性、字节长度和 offsets，而非依赖名称前缀。
6. **预期公式的独立性有限**：预期公式能检测很多执行错误，但如果来自同一反汇编解释，就不独立于该解释。应有第二解码来源、可追溯的指令条件语义，以及直接性质断言；不能把相同信息源的一致性当多重独立证明。

若只能取得一批新材料，优先 P0：**可靠的原件/切片与函数身份链，加上不可被 -O 绕过的本机重跑溯源**。先解决“运行的是哪段字节、为什么属于该名字、结果确实来自这一运行”，再增加更多随机数，证据增益更高。

## 8. 验收条件、原型取舍与品类适用性

本阶段交付物为本报告 `/workflow/prototype.md`，没有新游戏、试玩页面、资源、dist 或 releases。通用品类/原生 Web 配置已实际阅读，但用户任务明确是隔离实验复核：

- 玩法设计与参考取舍：只审查三份真实文本，不制作棋盘，不从比较器名字补造 Carrom 玩法。
- 核心循环：读取材料→检查脚本和结果→按指令文本推导→寻找反例→列出证据缺口。这是审查流程，不是玩家循环。
- 规则状态：区分静态材料一致、上传方运行声明、独立原件核验、目标游戏行为四种证据层级；状态结论见第 1 节。
- 界面布局与英文游戏文案：不适用，没有玩家界面；报告按用户要求使用中文。
- 物理步长、碰撞与计分、胜负、输入时机窗口：不适用，也未从这些片段取得，不能虚构。`count=100` 是模拟器指令数上限，不是物理步长。
- 可接受误差：本实验返回值比较要求精确一致，不引入 epsilon。binary64 相等是数值相等而非位型相等（±0）；NaN 无序不能按“容差”修补。跨设备误差和物理轨迹没有在本轮测试。

本轮完成验收标准：三份材料已真实读取；覆盖规模、输入类型、来源断言及其边界已逐项说明；反对称和 NaN 结论有具体反例；不把本机上传结果冒充 MCP 执行；不推断真实调用/排序；后续证据按优先级列出；未知清单落盘。上述文档审查标准 PASS，不代表实验独立复现 PASS。
