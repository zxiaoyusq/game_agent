# Carrom 主配置入口与虚表路径交叉审查

## 范围与结论

本轮为原型阶段的只读逆向证据审查，按用户明确请求交付研究报告，不制作游戏、不推进美术、代码或测试阶段。玩法循环、计分、物理步长、界面与英文文案不适用于本次研究交付；不从配置名称反推这些游戏规则。未修改原包，未猜测密钥，未执行解密。

结论：操作者提供的 gameConfig 链具备合理的条件性静态数据流解释，但其具体指令、对象来源和控制流尚未在本轮独立反汇编核验。即使 vptr+0x30 槽的重定位及目标函数得到确认，也必须证明调用时使用的对象确实持有该地址点，才能将 GameConfiguration.plist 接入这次调用。valueMap 链只能保留为另一条待证参数链，不能套用 +0x30 的目标或文件名。候选解密桥的可达性、实际执行、输入来源和输出解析成功是四个不同命题，目前均不能写为已完成解密。

## 旧归档实际支持什么

旧配置交叉引用 JSON 记录：GameConfiguration.plist 位于 link VA 0x1268b68，候选引用 0x1e3f710，FDE [0x1e3f710,0x1e3f71c)；decryptAES128 位于 0x127251a，候选引用 0x2711cc4，FDE [0x2711cb0,0x2711cd4)。该文件记载前者 ADRP/ADD 使用 x0，后者使用 x3。

这些是已读取的旧分析结果，不是本轮重新解码的指令。旧扫描只匹配八条指令内的 ADRP/ADD，可能遗漏间接引用，也不能保证中间寄存器未改写。FDE 是展开范围，不能单独证明函数业务身份。特别是 decryptAES128 的引用使用 x3，与名称登记、桥接包装等解释也相容；字符串本身不证明该范围实施 AES。

归档中没有新地址链的专门反汇编或本次 vtable 槽明细。旧 RTTI 文件的两条结果针对 MatchShotSolver 与 physicsStopped，不支持将 0x27eb928 识别为当前配置对象的地址点。旧直接调用文件也没有覆盖本次地址，不能以其未命中否定新路径。

## 操作者本机补证：本轮未独立执行

以下全部来自本次用户陈述，保留为待复核观察：

2. 0x1c0eff8 引用调试字符串 mc::Value::StringMap processEntryFromFile(const std::string &, const std::string &)，并在 0x1c0f0d8 调用 0x1e40a34。

4. 假设 vptr 地址点为 0x27eb928，+0x30 槽 0x27eb958 的 RELA 指向 0x1e3f710，该目标关联 GameConfiguration.plist。
5. 0x1c10070 采用类似方式，但槽偏移为 +0x28，配合 valueMap 字面量。

## 两条参数链的严谨性

### gameConfig 链

条件化表达：调用者 → 0x1e3f0c8 → 实际接收对象 P → 从实际 vptr V 的 +0x30 槽取目标 T → 返回文件名候选 S → 构造字符串对象 A → 0x1c0eff8(A, gameConfig)。

需要逐项证明：

- 0x1e3f0c8 的真实返回约定和后续寄存器传播。返回值可能涉及包装、子对象或指针调整；应以间接调用前实际加载 vptr 的基址为准。
- P 在该时刻的 vptr，而非某处存在的一张相似虚表。跟踪工厂/单例分支、构造与后续 vptr 写入、派生类型替换和对象生命周期；构造期或析构期的 vptr 不必等于正常业务调用期。
- 地址点与表起始分开。若 V 确为 0x27eb928，则 V+0x30=0x27eb958 的地址算术成立；不能将它直接称为整个虚表的第几个业务方法。需校验地址点前的 offset-to-top、typeinfo 或构造链，以及可能的次级表和调整 thunk。RTTI 被裁剪时保留类型未知，不凭名字补齐。
- 校验 RELA 的实际类型、r_offset、r_addend、符号索引和装载规则。若为 R_AARCH64_RELATIVE，运行时槽值通常由 load bias 加 addend 得到；若为符号重定位，则必须按符号解析。不能把文件中原始槽值与运行时槽值混用。
- 复核 0x1e3f710 的完整指令与返回路径。旧记录支持它关联文件名，但本轮未独立证明所有出口均返回该字符串。
- 从虚调用返回至字符串构造、再至调用点做逐指令 def-use；核查中间调用、别名、生命周期和条件汇合，确认 x0 指向构造后的 std::string，而非直接 C 字符串。x1 同样应证实为有效引用。
- 调试签名只能辅助命名，不能决定 ABI。若确为返回非平凡 StringMap 的普通自由函数，AArch64 可能使用 x8 作为间接结果地址；应检查 x8、调用方结果缓冲区和被调方使用。若实际为成员函数或包装函数，参数位置需重新确定。

因此当前可写为：在补证指令准确、实际对象 V=0x27eb928、槽重定位和返回传播成立的条件下，GameConfiguration.plist 可成为传给 0x1c0eff8 的第一字符串参数，gameConfig 为第二参数。不能进一步把 gameConfig 叫作密钥、文件名、根节点或算法参数。

### valueMap 链

独立表达：0x1c10070 相关调用路径 → 实际对象 Q → 实际 vptr W 的 +0x28 槽 → 返回字符串候选 U → 后续处理入口，配合 valueMap。用户只说明同方式，尚不足以独立确认其完整调用目标与参数布局。

必须单独记录调用前对象、槽值、目标、返回值、字符串构造与实际后续调用。如果 W 也为 0x27eb928，则 +0x28 的候选槽地址为 0x27eb950；这只是地址算术，当前没有该槽的重定位或函数内容证据。不得将 +0x30 的 0x1e3f710 或 GameConfiguration.plist 迁移到此链，也不能由 valueMap 名称推断它必定读取另一个具体文件、必定共享解密分支或必定使用某种键。

## 条件分支与候选解密桥

0x1c0f0d8 的直接调用即使复核成立，也只证明存在调用边，不证明该语句在某次启动被执行。0x1e40a34 → 0x1e408fc → 0x26e326c → 0x2711cb0 目前是操作者报告的候选可达链，不是本轮确认的无条件调用链。

复核时为每条边填写：源指令及机器码、BL/BLR/B/条件跳转或回调类型、目标或分发解析、前驱谓词、相关参数定义、正常出口、失败出口和异常清理出口。若中间为回调登记，应分开记录登记时刻与实际回调执行。需要枚举可能存在的文件缺失、读取失败、空内容、格式识别、缓存命中、普通解析、转换失败及 fallback；这些只是待检查类别，不是已发现分支。

即使执行到名称相关入口，也需证明实际处理的数据来自哪次读取、是否只是登记或分发，以及返回值是否交给解析器。桥接到其他运行时还需解析实际分发对象与方法，不从 decryptAES128 名称推断参数顺序、密码模式、IV、编码、填充或密钥。

## 从原包验证运行时输入的可复核实验（未执行）

以下为交给具备本地工具与授权设备的操作者执行的实验规格，不是本轮结果。当前工具无 ADB、调试器、ELF 解码或任意命令执行能力；不借 npm 验证脚本绕过限制。

### 实验一：建立二进制和资源基线

1. 对原始 APK/分包逐件记录文件名、SHA256、包名、版本、签名证书摘要和 ABI；保留只读原件，研究输出使用独立目录。当前输入没有完整 APK，因此签名、资源清单和安装来源均未核验。
2. 逐块校验 manifest 的大小、哈希，再按 part000 至 part005 顺序生成独立研究副本并计算完整 SHA256，要求等于 4cf2ba474fc9aefda142fbdca46cf7b4d3ebf06a2114ecd8487a3e48448710b4。失败即停止地址复用。不得覆盖原库或修改安装包。
3. 导出 ELF 头、PT_LOAD、相关 section、RELA、工具版本及命令日志。link VA 转文件偏移仅对命中的文件支撑 PT_LOAD 使用 p_offset+(VA-p_vaddr)，且 VA 落在 p_filesz 范围；不得因为旧样例字符串的两值相等而推广 VA=文件偏移。
4. 在原 APK/各 split 的真实条目中定位 GameConfiguration.plist 及其可能资源容器，记录条目路径、解压后大小、CRC 与 SHA256。未找到则记为缺失，继续调查资源管理器、缓存或下载来源，不能凭名称伪造文件。

### 实验二：静态闭合两条调用链

导出覆盖相关 FDE、所有出口、直接调用点前后、0x1e3f0c8、两个虚表槽及候选桥的带原始字节反汇编，保存控制流和 def-use 表。对 vptr 的所有相关写入建立引用表，追踪实际对象到调用位置，检查可能子对象与 thunk。给 gameConfig、valueMap 分别建立参数表，不用一个结论覆盖另一条。

验收：另一操作者可据匹配 ELF 与指令字节复算地址、重定位和参数传播；不能只提供截图中的名称或反编译器自动变量名。静态证明仅覆盖所枚举类型与分支，不宣称覆盖所有运行实例。

### 实验三：原安装包上的只读运行观察

1. 使用现有可授权调试环境，保持原 APK 和资源不变，不重签、不注入、不补丁、不强制返回、不改寄存器、不绕过保护；断点优先硬件执行断点，避免软件断点修改代码页。不具备只读观察能力时报告阻塞。
2. 记录实际加载模块的映射、路径、构建标识和匹配哈希。结合 PT_LOAD 与 maps 偏移求 load bias，检查多个段交叉一致；运行地址=load bias+link VA，不能直接使用 maps 第一行起址代替。
3. 在两条链的间接调用前记录线程、事件序号、调用栈、实际 receiver、vptr、槽地址、槽运行值及归一化 link VA。返回后读取字符串候选，并在后续处理调用前读取 x0/x1 所指对象；若 ABI 显示 x8 为结果地址，也一并记录。按本构建 libc++ 布局解析 std::string 的短串/长串、长度与所有权，先做地址和长度边界检查，不固定用某个猜测偏移。
4. 在读取边界记录逻辑资源名、最终解析来源、实际路径或 APK asset 条目、缓冲区地址和有效长度。包内 asset 可能不体现为普通独立 open 调用，需跟踪资源管理层与底层读取两端。文件名参数不能替代这一步。
5. 在 0x1e40a34 及每个候选桥边记录真实命中、谓词取值、参数来源和返回状态；对 0x2711cb0 确认它是处理入口还是名称分发包装。跟踪输入缓冲区到读取结果的直接传播或中间变换，记录长度和字节哈希；不能仅因两个阶段文件名相同就认定字节相同。
6. 在候选转换前后及解析器入口记录字节数、哈希、返回状态和结构验证结果。若实际存在密钥类参数，只记录其来源、类型与长度，不猜值；任何算法结论必须有实际实现或已解析 API 调用证据。仅可打印、低熵或包含 XML 标记都不能独立证明解密成功。

### 实验四：复现和反证

在隔离测试安装中通过应用正常启动及正常可用的 reload 操作观察，分别记录全新状态与保留缓存状态，并在环境允许时比较离线与正常联网。不得为制造结果编辑配置、删除现存用户数据或构造未经授权的网络响应；需要全新状态时使用独立安装环境。每种条件至少两次，记录设备、系统、版本、网络和缓存前提。

如果两次的 vptr、槽目标、路径或内容不同，应按实例拆分结论。没有命中只说明该次观察未触发，不能证明路径不存在。断点可能影响时序，应记录这种干扰。

建议日志字段：run_id、ELF/APK 哈希、环境、线程、事件序号、link/runtime PC、load_bias、receiver、vptr、slot、target、参数类型与值摘要、资源来源、输入/输出长度与哈希、分支谓词、返回状态、调用栈、工具版本。缓冲区复用时必须在有效期内采集，避免把后续覆盖内容当作当时输入。
