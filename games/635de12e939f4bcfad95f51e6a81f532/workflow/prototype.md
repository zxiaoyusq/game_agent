## 设计判断

按描述保存 remaining 并在暂停时 clearTimeout，可以解决被暂停期间仍消耗等待时间的问题。到期先从任务数组移除，有助于一次性消费和回调重入；但只检查 owner.parent 不足以证明任务仍属于当前匹配。没有新版代码，下面均是设计反例或待核验点，不是已复现缺陷。调用方提到的桌面暂停样本和 owner 脱离模拟测试仅为其陈述，本轮未读取相关日志、脚本或运行结果。

|2|P1|旧匹配退出后仍挂在旧容器，或仅隐藏；旧 ready 可通过原监听初始化棋局，读取已被新选择修改的全局球桌/先手配置。|场景退出使匹配失效并 cancelOwner；回调核验当前 activeMatch、捕获的选择配置与代际。|

|7|P2|due 用 Date.now；运行中系统时间前跳一小时，pause 算得 remaining<0；回拨一小时得到超长 remaining。仅 clamp 到零不能解决回拨。|相对等待使用可注入单调时钟；due 与 now 必须同源同单位；只在有效运行区间扣减，暂停期不扣减。若保留墙钟，必须承认并规定跳变降级行为。|

## 建议的最小状态与调度契约

业务状态为 rolling → stopping → waitingReady → shuffling → started；任意未结束状态可进入 cancelled/failed。pause 为正交暂停原因集合，不重置业务阶段。输入仅允许活动场景开始一次匹配；再次开始应先取消旧匹配并生成新代际。目标为一次正确进入棋局，失败为旧任务影响新匹配、暂停时推进或重复提交。界面沿用原布局，不新增交互设计。

任务除 owner、callback、remaining、handle、due 外，应能关联任务身份、matchGeneration、sceneToken、sequence、armVersion、cancelled 状态。有效性由业务令牌决定，parent 只作结构检查。暂停首先标记暂停，再对活动 handle 统一采样 now、计算 max(0,due-now)、clear 并置空；重复暂停不能重新计算已冻结 remaining。恢复先更新原因集合；仍有原因则不 arm；已 arm 的任务不能重复 arm。创建于暂停期的任务保留完整 remaining。回调包装器即使收到旧句柄派发也先验证版本；有效任务先移除并清理内部引用，再通过局部 callback 调用业务。

在 startRoll/取消/销毁时一起处理本代 Tweener、滚动子节点与后续 shuffle 回调。仅替换三处延时不能声称覆盖整个匹配动画生命周期。构造函数调用 startRoll 早于 addChild，故不能在任务注册时简单以 parent 为空就取消正常初次匹配；应使用显式生命周期，或把开始操作移到挂载完成后（本轮仅建议、不改代码）。

真实桌面样本：在首次3000ms等待已过约1000ms时触发真实host暂停，保持5000ms后恢复，记录单调时间、stop/ready/start事件和ticker状态；预期仍等待约2000ms才触发停止请求，之后须完成停止Tween，再消耗1000或3050有效运行ms进入ready。免费和收费各测一次；再在ready等待、shuffle期间暂停。推荐前台空闲样本晚到容差0～150ms作为观测目标，早到不超过计时精度2ms；这不是通用平台保证。确定性假时钟测试边界应精确到1ms且不允许提前；浏览器长任务只允许晚到，仍必须守住顺序、暂停和一次提交不变量，记录实际迟延，不用宽松误差掩盖错序。
