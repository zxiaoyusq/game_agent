# Carrom 物理步进与后台恢复性能风险审查

## 1. 范围与结论

阶段：prototype；attempt=1；只读静态审查。用户要求优先判断是否需要修改，不修改工程、不执行复现、不声称实测。本轮仅新增本报告，没有生成游戏、补丁、测试脚本或试玩包，不推进美术、代码或验收阶段。

**结论：目前不足以要求修改现版步进器。** 现版摘要证明固定物理步长和外层缺少显式补步预算，但不证明实际 ticker 会传入无上限 delta，也不证明后台恢复已经卡顿或结算错误。建议先取得现版实际 ticker 配置与目标设备时序/耗时证据；若可达 delta 与整轮成本均满足预算，保留现状。若真实恢复路径将暂停时长重新带入，先修时间源/生命周期边界；只有确认有限但昂贵的补步超过预算，才考虑保留债务的分批执行。不能把任意截断 delta、改用大物理步、只补 world.step 当作不改变玩法的优化。

## 3. 固定步长及外层精确边界（现版 E-01）

### 3.1 三个计数必须分开

- 一次 ticker 回调：接收一个 delta。
- 一轮 `_0x49d791(1)`：消费一个 accumulator 单位，未必走到物理尾部。
- 一次实际 `world.step`：参数固定 h=1/60 秒，10/10 两个求解迭代参数。10/10 不等于执行十个物理时间子步。

所以“大 delta”增加的是潜在轮数，不会把所述 world.step 的 h 变大。clearForces 每次紧随 step；若每步施力、冲量、阻尼、销毁和碰撞回调受前置逻辑影响，仅保持 h 相同仍不足以证明整体行为相同。物理库版本和具体力/冲量 API 未由摘要给出。

### 3.2 轮数公式

假设 accumulator 初值 r 为有限非负数，delta=d 为有限非负数；本次未被入口阻断，内层不重置 accumulator、不新增债务、不触发 break。按精确算术令 S=r+d：

`N = max(0, ceil(S)-1)`

`rNext = S-N`

若 S>0，则 rNext 属于 (0,1]；S=0 时 rNext=0。严格 `>1` 与常见 `>=1` 的区别在恰好整数边界。

| d（accumulator 单位） | r=0 时 N / rNext | r=1 时 N / rNext |
|---:|---:|---:|
| 0 | 0 / 0 | 0 / 1 |
| 0.5 | 0 / 0.5 | 1 / 0.5 |
| 1 | 0 / 1 | 1 / 1 |
| 1.001 | 1 / 0.001 | 2 / 0.001 |
| 2 | 1 / 1 | 2 / 1 |
| 3 | 2 / 1 | 3 / 1 |
| 6 | 5 / 1 | 6 / 1 |
| 60 | 59 / 1 | 60 / 1 |

表为手工数学推导，不是运行结果。连续 d=1 从 r=0 开始，第一回调不执行、以后每次一轮；总回调 m>0 时共 m-1 轮，不是永久 30Hz，也不是每次都少一轮。从 r=0 连续 d=0.5，第一轮发生在第三次回调，随后平均每两次一轮。

若每轮都实际 step，累计无暂停/重置且累计输入 D>0 时，物理模拟时间为 `(ceil(D)-1)/60`；落后于 D/60 的量大于零且不超过一个 h。若有内层 early return，只能证明消费轮数，不可用该式报告实际物理时间。

只有在真实 ticker 证明 `d=60*elapsedSeconds`、speed=1 且无截断等条件时，1 单位才可对应 16.667ms 墙钟时间。不能仅凭 PIXI 名称套用该换算。

### 3.3 有限上限与可达性

若经取证证明每个 d<=B，且正常回调前 r<=1、没有中断遗留债务，则单回调 N<=ceil(B)。例如假设 B=6 时最多六轮；这是条件示例，**不是声称 PIXI 实际 B=6**。一般初值上界 R 时，N<=max(0,ceil(R+B)-1)。

若内层改变阻断状态导致 break，公式只描述未中断需求；实际执行可能更少，残余取决于该事件是否清 accumulator。暂停清零时应以重置后的值算账。外层已见代码无显式步数/耗时上限，不代表调用方无上限；即使 B 有限，B 轮整轮逻辑仍可能超预算。

小数浮点加减会影响恰好阈值附近的一轮归属，需测试 1±ε 与累计小数；不承诺跨浏览器位级一致。NaN 会污染债务、负值会推迟执行；Infinity 或极大浮点值可能使减一不进展。它们只是输入契约/防御性审查项，无证据表明正常 ticker 会产生这些值，也不能据此宣称实机死循环。

## 4. 后台恢复与长帧（分别推导）

### 4.1 现版摘要能证明什么

入口 matchBlocked 为真时返回，因此该回调的 d 不计入 accumulator。host/ad pause 清零只删除暂停发生时的现存残余，不撤回已完成物理步，也不清除物体速度。

**清 accumulator 不等于重置 ticker 的时间基线。** 恢复后首次未阻断回调若携带跨暂停 d，仍会重新计入。反过来，若 ticker 在暂停期间继续更新基线、start 重置基线或已经限制 d，则可能不会补暂停时长。没有完整 ticker 与事件日志，不能决定属于哪一种。

长前台帧没有显式 pause 时，可能触发按 d 的补步；若 d 被时间源截断，游戏可能相对墙钟慢走。当前时间源是否已有丢时策略未知，不能说改造前绝不丢时间。

### 4.2 历史附件增加的候选路径，不升级为现版事实

- host pause：见置位/清零，不见公开 pause 调用 ticker.stop。若 ticker 持续回调，阻断期间回调返回且可能持续刷新 ticker 基线；若浏览器完全挂起回调，恢复首 d 又取决于 ticker。两种情形都要测。
- ad pause：调用方 stop/start，但 sharedTicker 的实例归属、其他监听器、start 的时钟行为未知。不能凭 stop/start 断言首次 d 必然安全或必然包含广告时长。
- visibility 路径：所见隐藏处理不等于 host pause；可见性变量没有进入历史 matchBlocked。重新可见且在比赛中调用 UI pause。不能把 visibility、host、ad、UI pause 当一个生命周期。
- UI pause：历史 `_0x49d791` 入口遇 `_0x3e61d0` 返回，而外层 matchBlocked 只含 host/ad。若 ticker 仍传 d，外层可消费多轮但没有实际 world.step；这不是物理追赶，仍有空转调用成本。解除 UI pause 的时序不同于 host/ad resume。
- host/ad 重叠：历史 tokens 与 host flag 的 OR 支持剩余暂停原因继续阻断。是否所有入口恢复均正确遵循合成状态需现版取证。

清零会删除暂停前尚未消费的残余（正常完整回调后至多 1 单位）；若暂停在补步中发生也可能删除更多未消费债务。这是已有暂停边界的时间策略，不等于跳过已经发生的碰撞。改造不得悄悄把暂停前活动时间与暂停持续时间合为一段统一丢弃。

## 5. 顺序、一致性与规则状态

### 5.1 历史整轮顺序（E-02f）

1. 入口检查 UI/host/ad，失败立即返回。
2. 递增逻辑 tick；更新动画管理、粒子、Tweener。
3. 再检查 host/ad；大厅逻辑；比赛不活跃则返回。
4. 广告准备倒计时、回合倒计时；倒计时到期可能切回合，或建立 timeout ticket。
5. striker 袋口检查，随后 queen、player、opponent 各组位置同步及袋口扫描；命中袋口的普通子移出物理世界和活动数组、加入待结算队列。袋口判定是到袋中心距离<=20画面单位，不是据此证明传感器接触事件。
6. `_carromFlushTimeoutAfterScan()`。
7. `world.step(1/60,10,10)`，clearForces；随后比赛/表现排序条件。

所见扫描读取发生在本轮 step 前；若同步方法读取上轮刚体状态，袋口判定反映上次物理步，末轮新进入袋口需要下轮才能扫到。同步方法完整实现未在本轮核实，故该读取含义为条件推断。顺序本身已读到。

尤其不能说“所有结算都在扫描后”：Tweener 在扫描前，可能执行 `_0x338c29` 安排的 `_0xbdafb3` 等回调；只有 timeout ticket 的指定 flush 位于扫描后。`_0x56abf7` 还会修改/裁剪速度，不能当成纯查询随意搬动。早期倒计时直接换回合也先于袋口扫描。

### 5.2 补步为何可能影响输入/结算

同步 while 执行期间，通常新的 DOM 输入任务、setTimeout 任务不能在轮间自然插入；但直接调用的 Tweener 完成回调、SDK 同步回调、物理接触监听器能改变状态。外层步后 matchBlocked 是轮边界保护，不是内层事务回滚；历史内层只在指定位置复查 host/ad，不能保证从任意 SDK 回调设置暂停后本轮马上停止。

历史释放路径直接施加击球动作，然后关闭输入并用 `_0x338c29` 排结算；AI 由 Tween/延迟链触发，拥有 turn 去重。一次大回调可能推进多个逻辑 tick、倒计时和 Tween 完成链，而期间没有新的人类输入任务。分批补步允许事件插入，将改变原本的执行交错：仅保留欠步和 h 不足以证明顺序等价。

### 5.3 必须保留的玩法与状态契约

本项目不是新游戏设计；核心循环沿用观察棋盘→摆位/拖拽蓄力→释放击球→碰撞/进袋→静止后计分、犯规或 queen 处理→续回合/换人→胜负。跨局成长不在审查范围。

规则状态至少记录：roundId、turnId、settledTurn、resultCommitted、当前模式/场地/执手、输入状态及指针、物理刚体位置速度/awake/sensor、袋口待结算队列、queen 状态、分数、计时器/Tween、host/ad/UI/visibility 各暂停原因、accumulator。不要把画面节点作为唯一事实源。

历史合法输入窗口：玩家回合且 enable/player flags 为真，UI/host/ad 未阻断，同一指针完成 aim；strength 在 [0,1]，低于 0.25 不击球，击球路径参数为 strength*125（其物理单位/API未核实）。取消、重开跨局指针不应击入新局。现版这些细节需确认，不能由历史阈值直接提出新玩法要求。

碰撞与计分：保留原碰撞体、材质、阻尼/裁速、求解器配置和扫描顺序；历史普通模式计子数，Freestyle 使用类型分值数组 [50,20,10]，queen 覆盖/返还与犯规存在专门分支。普通模式胜负调用外部 hasWon 并结合 queen 列表；Freestyle 见目标160、queen pending限制及双方达标分支。外部 CarromDiscRules 正文未提供，**不补写其完整成功失败规则，也不把历史常量当成现版规则**。

关键不变量：一击只执行一次；一袋口对象只进队列一次；一个 turn 只结算一次；一个 round 只提交一次结果；旧局异步回调不改新局；罚回/queen返还时刚体、队列、分数同步。score/胜负/犯规离散结果不允许以数值容差掩盖差异。

## 6. 处理预算与修改判据

定义：一轮成本 C_i 包含动画/粒子/Tween、规则/数组复制与扫描、接触回调及音效、物理求解、销毁/创建、排序；ticker 一次补步耗时 `Tcatchup=sum(C_i)+Tloop`。整帧还要加入输入/其他 sharedTicker listeners、渲染、布局/GC等成本。

不能只测 world.step。10/10 固定迭代不保证每步耗时固定，接触数量、awake 状态、Tween 回调/广告路径和对象创建影响尾部。历史每步多次 slice/扫描/表现更新是候选成本点，不是本轮已测热点。

目标刷新率 f 的帧时间为 F=1000/f ms；先定义整帧预算、渲染余量与可接受恢复首帧预算 H，再测。若除补步外实测成本为 O、保守每轮成本为 C，则候选容量 K=floor((F-O)/C)；不能用平均 C 掩盖尾部峰值。O>=F 时加步数上限不是完整解决方案。若持续输入债务大于服务能力，保留债务会长期慢走；上限不能解决持续过载。

决策门：

| 条件 | 建议 |
|---|---|
| 可达 B、正常残余、实测整轮成本与尾部均满足预算，无顺序反例 | 保持现版，不因为 while 外观而改动 |
| 恢复实际带入暂停时长，且产品暂停语义不应追赶 | 优先在已确认唯一 ticker/生命周期 owner 处理恢复时间基线；不先全局截 d |
| 活动期间有限长帧补步超过预算 | 先定位可安全削减的纯表现热点；仍不足时评估保留债务的分批完整逻辑 tick |
| 固定 h 下有袋口/结算边界反例 | 单独修 owner 和提交顺序，不能把性能限步当正确性修复 |
| 持续低端机无法服务输入债务 | 需产品决定实时性/慢走/表现降级等取舍；进入修改前调用 request_user_input，不能默许丢时 |

当前未取得前三列所需测量，不能选定具体 B、K、H 或判定修改必要性。

## 7. 不丢失物理行为的改造边界（仅方案，未实施）

优先级从低风险到高风险：

1. **无行为修改取证**：当前真实加载文件/依赖哈希、时间源单位、ticker speed/minFPS/maxFPS与实际有效配置、共享实例、start/stop行为；独立测试环境低扰动计数/耗时。minFPS/maxFPS具体作用必须查当前版本实现，不能按名字推断。
2. **暂停边界最小修复**：若证据说明需要，在有效恢复的唯一 owner 上排除暂停持续时间并遵循 host/ad 合成状态；避免同时启动第二个 rAF/ticker。不改变已完成物理状态，不重复重置，不吞恢复后真实前台长帧；共享 ticker 更改不得误伤其他 listeners。
3. **纯表现优化**：只有证明某项不写玩法状态才可降低表现成本。历史 Tweener 会改阻尼、刚体位置、计分、AI和结算，不是整体可跳过的装饰系统；表现动画还关联对象恢复，不可简单一次 frame 更新替代每 tick 更新。
4. **预算分批**：保留有限、有效的活动时间债务，每批执行最多 K 个完整原逻辑 tick 或在整 tick 边界检查时间预算；不拆半轮、不只补 world.step；维持 1/60、10/10、clearForces、同一步输入/冲量和原顺序。保留 `>1` 原阈值，改变为 `>=1` 是独立行为修订，不能混入性能补丁。应分别记 accepted/consumed/reset/debt，正常保守约束 accepted=consumed+debt，显式暂停重置另列账。
5. **分批输入/异步边界**：若需保持原连续补步语义，在逻辑步索引上冻结/排队新输入和有效回调；维持 round/turn 去重、暂停取消的优先级及超时消费点，避免新输入施加到尚未追赶的旧状态。原 setTimeout 与模拟 Tween 两类时钟要分别处理。排队会增加输入延迟；如希望期间可交互则行为交错有变化，必须明确范围并验证，不能称严格等价。

明确禁止称为无损：`delta=min(delta,D)`；到 K 后 accumulator=0/取小数；将 N 步替换成 step(N/60)；降低求解迭代；跳过中间碰撞/袋口扫描/裁速；提前或统一搬动结算；在债务未清时依据插值画面判袋口。大步会改变接触、阻尼、裁速和袋口采样；限步丢债会改变模拟时间、输入窗口和延迟链。

渲染插值可独立评估，但只能展示已提交物理状态，不能成为命中依据。历史残余区间 (0,1] 不是常见 [0,1)；不可机械套 alpha=accumulator 的模板后声称正确。

## 8. 复现实验设计（未执行）

### 8.1 身份和观测记录

同时记录事件单调时间、逻辑 tick、round/turn、四类暂停原因、start/stop调用、有效输入/冲量序号、袋口与队列对象ID、裁速/awake、分数/queen/结算提交序号、callback/Tween完成顺序。采用有界环形缓冲/批量导出，分别比较无观测/轻观测成本，不在每步大量 console.log。数据采集只含必要合成局面与时序，不收凭据或个人信息。

### 8.2 数学/合成夹具层（不能冒充自然复现）

在独立 harness 用现版确切循环与内层调用边界：r=0、0.5、1；d=0、0.5、1±ε、2、3、6、60，连续 [1,1,...]、[0.5,...] 与相同总量的不同分组。覆盖第 k 轮设置 host/ad blocked、暂停重置、内层 early return，分别断言 N、Np、债务。非法有限性用隔离、有超时的夹具，不向真实页面注入 Infinity。所有人工 d 明记 synthetic，不因 d=60 已触发而说 ticker 自然会传60。

### 8.3 自然恢复层

在大厅、静止瞄准、有效击球运动中、袋口临界、计分/queen返还、AI准备、结果界面分别执行：

- 正常60/30/高刷新率运行，记录真实输入 d，而不假定屏幕刷新率等于 ticker频率。
- 前台人为长任务候选时长50/100/250/1000ms，标记为实验阻塞；这些是注入条件，不是宣称已测长帧。
- 页面隐藏/返回、host pause/resume、ad stop/start、UI pause/resume分别测试；后台候选1/10/60秒；增加浏览器冻结和系统锁屏路径。
- host与ad重叠，双方解除顺序互换；重复pause/resume；暂停前持指、暂停时释放、恢复重新aim；计时器将到期时暂停；旧局回调与重开交错。

每条路径比较 pause前残余、隐藏时ticker是否回调、恢复首 d、首回调 N/Np、首次可输入与首次绘制延迟、P95/P99/最大catchup成本、稳定债务趋势。只有记录能说明自然 d 与热点因果时才报告“复现”。真实宿主/广告验收不能用模拟回调替代。

### 8.4 物理与顺序对照层

固定初始刚体状态、物理配置、随机源与**逻辑tick上的输入事件**，在同一runtime对照单轮、批量轮及候选分批：单子直射、擦边碰撞、密集开球、高速薄边、袋口边缘入/擦过、striker犯规、queen与普通子同tick、最后一子与超时同tick、静止裁速临界。末个step刚入袋时务必再观察下一扫描点，不只在大回调结束取快照。

必须比较每tick位置/速度/awake、袋口采样与移除、事件顺序、分数/犯规/queen/turn/result，而不是只比最终截图或相同墙钟时间的球位。若未锁定随机源，不将AI路径差异直接归因于分批。

### 8.5 建议验收条件与误差

- 算账：有效输入、债务、消费、重置可解释；每次实际物理step参数一致；不得隐藏丢弃活动债务。普通完整路径满足公式；中断/early return单独断言，不混计。
- 同runtime、同输入的调度改造：优先要求同tick状态完全一致；如仅浮点工具差异，初步诊断容差可用绝对/相对1e-6量级并分别注明位置/速度单位，不作为已确认产品标准。
- 跨runtime暂定视觉位置误差<=0.5逻辑像素（不是CSS像素），速度误差需以真实单位和基线确定；这是提案，未经运行标定。袋口<=20、裁速/awake等阈值附近必须保持离散事件结果和先后顺序，不允许容差“放过”进袋、犯规或胜负变化。
- 输入：一次释放只击一次；暂停/取消/重开不会提交旧输入；同tick超时/释放优先级对照现版实际轨迹，摘要不足以预设。
- 结算：turn/result恰好一次、旧epoch无效；分数/queen/罚回/胜负完全一致；恢复后没有永久等待或债务无限增长。
- 性能：先明确目标设备F、H、输入延迟预算；取得无观测基线及候选方案尾部耗时。没有目标设备测量不判性能PASS；存在持续过载或不可接受排队延迟时先做取舍确认。
- 不新增界面。若后续授权诊断面板，建议布局为顶部时间源/delta/债务，中部原棋盘，侧边或下方暂停/输入/结算时间线；显示名使用 `Delta`、`Physics Steps`、`Time Debt`、`Pause Reasons`、`Resume`，不重排原玩家HUD与按钮。
