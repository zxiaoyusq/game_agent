# Carrom Lucky Box 与现有 H5 奖励能力复核

研究日期：2026-11-12；当前阶段：原型定义；attempt=1。仅研究，不开发、不修改原源码、不发布。

## 结论与优先级

优先完成击球核心和可靠离线存档，再修正奖励提交边界，最后评估轻量风险奖励玩法。现有免费转盘可提供入口、金币图标、动画及奖励弹窗参考，但不能直接充当 Lucky Box：它只有一次加权结果和金币入账，没有已核实的逐层风险、未领取奖励账本或箱子库存链路。推荐本轮保持研究结论，后续优先选择方案 A；方案 B、C 均为可选设计，不代表已获开发确认。

最关键的工程差异是：现有转盘在动画结束后先增加内存金币、更新免费奖励时间并调用保存，然后展示领取弹窗。因此“点击 Claim 才到账”不符合这段代码；但调用保存也不等于已获得持久化成功确认。

## 三条实际调用链与边界

### 免费转盘

大厅时间计算 G9 → 免费按钮资格显示 → 进入转盘 G5 → spin 输入 G11 → 本地先抽颜色 G5/G10 → 动画完成 → 基础金币及时间更新并调用存储 G6 → 领取弹窗 → 回大厅表现。该循环没有观察到“继续冒险或带走累计奖励”的决策。

权重配置为 purple:3、blue:15、green:6、red:15、yellow:1，总和 40。在理想均匀随机假设下，代码配置对应 3/40、15/40、6/40、15/40、1/40；合并同为 50 金币的 blue/red 后为 30/40。基础奖励理论期望为 (3×200+15×50+6×100+15×50+1×500)/40=80 金币。以上仅为 H5 静态配置推导，未做随机运行验证，不是 Lucky Box 概率，不代表线上版本或广告后经济收益。无需通过大量转盘点击猜测这里已有的配置。

抽奖函数内未见免费资格、活动 ID 或领取 ID 的再次检查。UI 禁用降低重复点击，但若回调重入、旧回调迟到，仍需验证。冷却时间直到动画完成才更新；刷新是否重抽、丢结果或恢复均未运行验证。

### 存档

G1 模板 → G3 逐键读取/JSON.parse → 运行变量 → G6/G8 改币 → G3 逐键写 GameSnacks.storage。D1 表明适配器自身不是 localStorage 持久后端；在已读 game.html 缺目标宿主属性的配置下，静态链路指向内存存储与空消息路径，刷新持久化缺乏证据。不能因为函数叫 storage 就认定离线保存可靠。若实际部署存在额外宿主注入，应提供运行证据另行判断。

逐键写入金币和时间也不提供跨键原子提交保证。解析错误、错误类型、负值/非有限数、数组越界、部分写入及存储失败是待验收边界，不声称已复现。禁止在现有 getter 被覆盖的情况下建议简单追加 localStorage 调用即可修复；需后续明确适配器替换或注入边界。

### 奖励及广告

转盘基础奖励 G6 与比赛胜利 G8 均直接修改共享金币变量并调用保存；追加奖励经 G7 广告真值回调。没有统一已核查的奖励事务服务。父页 H1 的字符串消息与 game.js 的 GameSnacks 广告回调是两套可见路径；主脚本搜索 rewardSuccess 无匹配，不能宣称父页消息已接通业务加币。混淆及外部 SDK 可能影响最终行为，仍需事件级复现。

D1 中广告推送还受脚本属性开关控制；当前 game.html 未设置对应属性，不能承诺额外广告按钮必现或广告可用。G7 的共享回调清理晚于 adViewed，重复回调可能重复追加、迟到回调可能引用变化后的比赛索引；这是静态风险假设，需注入重复和延迟事件验证，不能作为已证实线上漏洞。

## 单次 Lucky Box 样本审查

调用方记录的动作依次是左上、右上、左下、右下、左上，连续五次成功，随后在第 6 层退出。记录的累计金币为 0→203→464→766→1122，因此第 2–5 次显示增量分别为 203、261、302、356；这些只是本条轨迹的差额，不是固定奖表。第 1 次显示青铜箱×1，不能自行给箱子折算金币。

退出二次确认后余额从 4120 到 5242，差额 1122，支持本次金币实际到账；青铜箱仅有收到提示，库存及开启结果未知；观察期钻石 40 未变。用户描述的“收到金币后再显示箱子”支持分步展示，不能证明后台分笔写入或事务顺序。

每 5 等级保底、选错失去奖励来自调用方转述的页面文案；第 5 层金箱与提示转向第 10 层支持存在里程碑表现，但未验证任意箱必胜、保底奖励是否免于后续失败、退出能否保留、最大层级或奖池个体差异。第 20 层 200 宝石和第 30 层箱子仅是本次页面展示。重启后出现活动不等于每次重启触发、新手必出或广告返回必出。

本条成功轨迹不能估计胜率、失败率、颜色相关性、前五层必胜或点击前后结果确定时机；不进行这种推断。没有亲自运行竞品或查看截图，也没有取得其后台配置、概率或代码。

## 可选 B 的原型定义（建议，不执行）

### 核心循环与范围

局外入口 → 阅读风险 → 开始 → 四选一 → 反馈并累加未领取金币 → 继续或带走 → 确认结算 → 返回大厅。击球仍是主循环，奖励系统不在对局中弹出、不强制启动、不阻塞继续比赛。建议首次内容只覆盖教程局、普通局和恢复边界局，最大层数采用有限配置；具体层数、奖池、失败概率和里程碑间隔待自主方案确认，不把竞品每五层直接设为既定需求。目标时长暂定 30–90 秒，仅为试验假设。

### 状态与转移

最小持久状态：schemaVersion、revision、walletCoins、rewardTransactions、activeRun（runId、phase、level、pendingCoins、configVersion、已提交选择/结果、随机状态或已承诺结果）。表现节点和动画进度不做唯一事实来源。

- idle → rules：打开可选入口；不改钱包。
- rules → choosing：开始后持久化新局，pendingCoins=0；写失败停留可重试，不进入可选箱状态。
- choosing → resolving：仅接受一个合法箱位；按自主配置抽取一次并持久化提交结果后播放反馈。重复输入拒绝。
- resolving → choosing：成功把金币加入 pendingCoins、推进层数；钱包不变。里程碑是否安全和受保护金额须在配置/规则中明确。
- resolving → failed：失败清空未保护 pendingCoins；本建议首版不设保护余额及付费/广告复活，若选择不同语义需改规则后再验收。
- choosing → cashoutConfirm → choosing：取消退出，所有金额不变。
- cashoutConfirm → settling → settled：确认时使用 runId 关联唯一奖励事务，在一个本地快照或 IndexedDB 事务中更新钱包、记录已提交并关闭 activeRun。写成功才展示已入账。
- 达配置终层：自动进入结算确认或统一结算路径，具体 UI 在实现前固定；不得同时走两个派奖入口。
- 重启恢复：已提交结果继续展示而不再随机；已 settled 仅重放提示不再加币；存储失败保留旧有效状态并允许同一事务重试。

成功条件：主动带走或抵达终层后金币准确提交一次。失败条件：自主规则的危险结果结束本局并失去本局未领取金币；基础钱包不被扣减。技术失败不是玩法失败，不能因写存档失败扣奖励或展示中奖后静默丢失。

合法输入仅 choosing 的箱位、确认弹窗的继续/带走、结果页返回；resolving/settling 锁定输入。后台暂停表现，返回按已提交状态重建。关闭页面不擅自视为确认带走或失败。

### 布局、反馈与文案

默认英文，未来页面设置 html lang=en；中文浏览器仍显示英文。顶部显示钱包 Coins；中部 Level、下一里程碑及四个带形状/编号差异的箱位；底部独立标注 Unclaimed coins，与钱包视觉分隔。继续按钮 Continue、离开按钮 Cash Out；二次确认 Cash out your unclaimed coins?，按钮 Keep Playing / Cash Out。规则必须明确 A wrong choice ends the run and loses your unclaimed coins. 该句只适用于上述无保护方案。

结算写成功显示 Coins Added；保存失败显示 Could not save. Try again. 并保持可见，实际成功后才清除。不以颜色作为唯一状态提示；主要触控目标建议至少 44 CSS px，弹窗可键盘操作并管理焦点，尊重减少动态效果设置。初版以 DOM 文本和按钮、内联 SVG 简单几何表现，不为棋盘引入新引擎；若后续嵌回既有 Pixi，则复用单一渲染器，不额外启动第二套常驻绘制循环。

### 最小资源与性能约束

资源建议表：四箱位共用一个原创箱形组件，以编号/形状/描边区分；金币图标一份，来源授权核实前使用自主几何占位；按钮、规则、层级和结算全部实时文本；不新增字体文件、音轨、整屏位图或大图集。这里只定义方案，没有生成或交付美术资源，不创建 art-manifest 冒充美术阶段完成。

建议新增模块与必要资源展开预算不超过 100 KiB，最终完整 dist 展开小于 10,000,000 字节；两者均需未来构建后实测，目前无 dist。不将 reference-inputs 打包，不靠 CDN 转移必要资源来声称离线小包体。新模式按需初始化，不增加首屏关键请求或预加载图像；使用已有音效也需确认授权与实际引用。

离线指资产齐备后断网仍能完整游玩、随机和提交存档；首次安装获取资产与跨设备同步不在承诺内。采用版本化单快照或 IndexedDB 事务保存钱包和 run/receipt；若多标签并行，需单活动实例控制或有条件更新，不能声称单个 localStorage 写就解决并发。可注入随机源用于测试，生产结果先提交后表现；离线本地时钟和存档可篡改，不承诺服务端级防作弊。无广告时不显示依赖在线广告的按钮，不把广告作为退出或领取前提。

性能验收须在同设备、浏览器、视口、相同击球场景与相同测量方式下比较基线/方案；建议至少 20 次开关模式。首屏关键请求数及预加载字节不得增加；击球场景 p95 帧耗时退化建议不超过 5%，超过测量噪声时回退；模式关闭后不得持续占用新的绘制循环或持续增长监听、Tween、粒子与内存。阈值是建议，未测量，不宣称性能不退化已经实现。
