## 当前摘录可确认的结算链

1. _0xbdafb3 使用 turnId 和 settledTurn 防止入口重复，等待 _0x56abf7() 返回假后标记本杆已结算。
2. Freestyle 分支复制进袋队列并记录 actor、foul、queen、ordinary。ordinary 统计两种普通棋，未按颜色或归属筛选。
3. 犯规时，当杆队列中的每颗棋返至中心，不走该循环的得分分支。当杆有任何入袋对象时，不调用历史罚棋。
4. 非犯规时，红棋在遍历时立即入账并写历史。普通棋在飞分回调执行时入账并写历史。回调闭包分别捕获类型、队列索引、round、turn。
5. 仅当 foul 且队列长度为零时调用 _carromFreestylePenalty。该函数要求同 actor、同 round 的历史总数恰为一，唯一记录必须是普通棋、分值有限且大于零，并要求当前总分严格等于该记录分值。
6. 历史罚棋先安排返棋动画、删历史、扣分及更新 HUD，然后等待返棋完成。
7. 延迟结算强制完成当杆返棋，再强制完成飞分，随后调用当前缺失的 freestyleQueen 实现，必要时返红棋并撤分。
8. 红棋状态非 pending 且任一方达到目标时，根据当前行动方调用胜负函数并 return。后面的条件性 50 分扣除因此可能被跳过。

## 发现与最小复现输入

### F1 历史罚棋资格极窄，且当杆返棋与历史罚棋互斥

【当前事实】_carromFreestylePenalty 的 matches 统计包括红棋在内的全部该方本局历史。只要有两条记录，就直接 false，即使其中存在可返普通棋。单条普通棋的分值与当前总分不等时也直接 false。调用点又要求当杆队列为空。

最小输入 A 为同 round、actor=player、history=[普通棋 points=10, 普通棋 points=10]、playerScore=20、foul=true、当杆队列=[]。静态预期为函数返回 false，分数与棋盘均不发生历史罚棋变化。输入 B 改为 history=[普通棋 points=10]、playerScore=10、foul=true、当杆队列=[普通棋]。预期仅当杆棋返桌，历史保留且分数仍为 10。输入 C 为单条 points=10、总分=15、队列为空，预期同样拒绝历史罚棋。

【规则待定】是否应从多条历史中返一颗、当杆返棋是否替代额外罚棋、旧罚分是否形成欠账，均缺少产品规则依据。若目标是一般性的历史罚棋，这些输入构成漏罚。若这是刻意限定的暂行策略，应明确呈现适用范围。不能直接称为竞品规则错误。

### F2 pending 红棋回退与历史罚棋存在顺序依赖

【当前事实】历史罚棋发生在 freestyleQueen 和红棋撤分前。pending 红棋历史也参与 F1 的 matches.length 判断。

最小输入为同局 playerScore=Q+P，history=[player 红棋 Q, player 普通棋 P]，红棋状态为 player 的 pending，当前 player 空杆犯规，队列=[]，Q/P 为正有限分值。历史罚棋先见两条记录而拒绝。

【条件性缺陷】若当前 freestyleQueen 对该输入返回 returnQueen=true、revokeOwner=player，随后仅红棋返桌并扣 Q，最终普通棋仍在历史中、分数为 P。若联合规则要求本杆同时撤销未保红棋并执行一次普通棋历史罚棋，则期望最终分数为 0 且两棋均返桌，现有顺序漏掉普通棋处罚。若规则规定两者择一，则该观察可能符合规则。当前状态机正文缺失，无法确定真实返回值。

建议最小修复方向是在单次结算计划中先决定红棋回退，再以规则认可的可罚历史集合选择普通棋，最后统一提交。实施前需补齐联合处罚规则。

### F3 红棋撤分缺少幂等与数据有效性保护

【当前事实】_carromReturnFreestyleQueen 每次调用均创建红棋。找不到历史时仍使用 _carromFreestyleQueenState.points || 0 撤分，没有 owner、round、phase、已有棋数量或有限分值校验。它始终返回 true，调用点的失败保护无法识别数据异常。

最小输入为旧状态仍为 pending、points=Q>0，history 仅有一条对应红棋，score=Q。连续直接调用该函数两次，且两次之间不替换 queenState。静态预期为创建两颗红棋，第一次删除历史并扣 Q，第二次走 fallback 再扣 Q，最终 score=-Q。若 points 为字符串或 Infinity，还可能使分数出现强制类型转换或非有限值。

【可达性限制】正常调用点在一次 returnQueen 后会替换状态，入口也有杆去重，因此本用例证明辅助函数自身缺少防护，尚不能证明正常玩家操作必然造成重复。需检查所有调用点、恢复状态与异常路径。

### F4 玩家计分上报异常可截断联合结算

【当前事实】玩家加分、历史罚棋扣分和红棋撤分都同步调用 _carromReportScore，摘录未见异常隔离。普通棋回调先置 scoreFinished=true，再更新分数、历史和 HUD，随后上报，最后才移除飞分节点。

最小输入为 player 非犯规进一颗普通棋，令 _carromReportScore 抛出异常，并在延迟结算强制 finish 时触发。预期分数和历史已提交，但回调异常中断 forEach，红棋决策与胜负判断未执行，飞分节点可能残留。后续再调用同一 finish 因 scoreFinished 已为 true 而直接返回，无法补完。

红棋预入账时抛错可能更早中断循环。历史罚棋上报抛错时，历史与分数已变更且动画已建立，外层 pending 赋值和后续结算安排可能未完成。红棋回退上报抛错时，返棋、删除历史和扣分已发生，而 queenState 尚未替换。

【限制】_carromReportScore 的实现缺失，若其内部已捕获所有异常，该风险不触发。最小修复方向为确保上报失败不截断规则事务，并单独记录失败。

### F5 胜负检查早于后续 50 分扣除

【当前事实】胜负分支位于 if (_0x4268e2 && !_0x5ebd99) 扣分分支之前，胜负成立立即 return。Freestyle 开始时 _0x4268e2 被置 false，其后是否被其他逻辑置 true 未提供。

最小状态输入为进入延迟决策时 playerScore=T、opponentScore<T、actor=player、queenPhase 非 pending、_0x4268e2=true、_0x5ebd99=false。静态预期为直接调用玩家胜利，后面的 -50 不执行。若该扣分应计入本杆最终分，期望先得 T-50，再判定未获胜。T 为 _0x153877。

【条件性缺陷】需确认该布尔组合在当前完整工程可达，以及 50 分扣除的产品语义。摘录只能确认执行次序。

### F6 达标方与胜负参数可能不一致

【当前事实】达标条件为 playerScore>=T || opponentScore>=T，而 _0x47e567 的参数仅由当前 actor 决定。

最小输入为 actor=player、playerScore=T-1、opponentScore=T、queenPhase 非 pending。预期调用 _0x47e567(true)。交换双方与 actor 后，预期调用 false。两方同时达标时同样仅依据当前 actor。

【条件性缺陷】若该函数布尔参数表示玩家胜负，则上述输入会判错赢家。需读取函数实现及正常状态可达性，尤其是 pending 阻断胜负期间的回合流转。修复方向为显式选定达标方，并明确双达标规则。

### F7 异步回调保护覆盖 round，未完整覆盖 turn 与结束态

【当前事实】计分和返棋回调有局有效标志、round 检查及局部一次性标记。延迟结算检查 round，但未再次检查 expectedTurn 或 settledTurn，也未见独立结算完成标记。

建议复现输入为同 round 内安排旧杆延迟回调后推进 turnId，再触发旧回调。观察旧杆是否仍执行红棋决策、罚分或胜负。另一用例为胜负后触发未完成飞分，核对 _0x3fddb3 是否已经变 false。

【推断】正常流程强制 finish 和入口去重减少了风险。当前缺失计时器取消、回合推进和结束函数，无法断言重复结算或赛后加分真实可达。修复前应先验证这些生命周期契约。

## 已存在的有效防护

普通棋回调使用 let 捕获每颗棋的类型及队列索引，可避免循环变量共享。红棋预入账后的飞分回调只做清理，可避免正常回调再次加红棋分。延迟决策强制调用尚未完成的飞分与返棋 finish，局部一次性标记阻止自然动画回调再次提交。入口有 turn 去重，主要动画回调有 round 检查。历史罚棋等待提供第 20 次轮询强制 finish 的补救。这些防护不能替代对缺失状态机与外部回调契约的核验。

## 其他组合观察

历史数组的普通棋写入顺序跟随动画完成顺序，player 飞分时长带随机量。记录含 turn 和 queueIndex，未来若按历史尾部选择罚棋，应显式排序，不能把 push 顺序当入袋顺序。当前严格单条资格下不存在多条选择行为。

当杆犯规返棋的延迟兜底直接调用 finish，没有看到 Tweener.extract。自然动画之后可能继续作用于已移除表现对象，局部标记会阻止重复创建棋。是否产生资源残留取决于 Tweener 实现。

state.cancel 置 pending=false 并删除动画对象，但已删历史和已扣分没有恢复。新局销毁时可能合理，同局取消时可能破坏棋数与积分一致性。需检查调用方，不将其直接定为正常流程缺陷。

## 原型规则与验收契约

本轮沿用现有 Carrom 玩法。核心循环为瞄准与击球、物理运动、入袋收集、等待停稳、当杆返棋或计分、红棋决策、最终胜负与下一杆。最小状态包含 roundId、turnId、settledTurn、actor、foul、当杆入袋队列、双方积分、带来源的历史、红棋状态和未完成的表现任务。

结算验收建议采用一个规则结果对象，明确本杆入账、撤分、返棋、红棋状态和赢家。分数、历史、棋盘和 HUD 提交完成后再触发外部计分上报。具体罚棋优先级、红棋覆盖规则、双达标处理保持待补证状态，避免擅自改变玩法。

规则输入窗口为同杆仅结算一次。返棋、飞分与 pending 决策未完成时，下一杆能否输入需要检查摘录后半段及输入处理。界面沿用棋盘、双方 HUD、瞄准与结算反馈，具体布局及默认语言未从当前完整界面核验。后续新增玩家文案默认英文，原生 Web 页面默认 lang=en。

物理步长、长帧补步、碰撞算法、入袋阈值、停稳阈值和坐标误差均未在当前摘录出现。_0x56abf7 的实现缺失，不能认定停稳检测正确。旧模块的 16 单位半径注释不能当成当前参数。本轮审查不重新制定物理数值。规则层可接受误差为精确的积分、历史条数和返棋数量一致，物理坐标容差需取得当前配置后定义。50ms 是结算轮询参数，不能视作物理步长。

后续验收应覆盖 F1 至 F7 的状态用例，分别测试双方、两类普通棋、红棋单独入袋、同杆红棋加普通棋、pending 后空杆/犯规/换方、目标分上下边界，以及自然动画完成和延迟强制完成两种次序。断言每颗棋只返一次、每次积分只提交一次、旧局回调零副作用、最终积分有限、历史与积分符合已确认规则、赢家取自最终结算结果。物理层另以固定输入和固定步长比较快慢帧、边缘碰撞和重开，不以这些状态注入替代完整玩法浏览器验收。
