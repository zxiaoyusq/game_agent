## 结论

证据支持一种明确的结构关联：以旧调用方入参 S 为基址时，访问器从 S+8 调用，将读取 S+0x2f8 槽位；0x1a0c248 也由该调用方以 S+8 为入参调用，所以其相对入参的 +0x2f0、+0x298 分别换算为 S+0x2f8、S+0x2a0。这里证明的是条件成立时的槽位地址相等，不是不同时间读出的指针必然相等，更不是容器对象与索引来源对象为同一实例、某字段代表棋色或某返回值代表红棋规则。

## 寄存器与偏移复核

令 S 为 0x1aa2eb0 入参 x0；其0x1aa2ed0保存 x19=S。下列跟踪限于所示正常控制流及符合调用约定的被调函数。

| 位置 | 可核查传递 |
| --- | --- |
| 0x1aa2fa0–0x1aa2fac | x0=S+8；调用0x1a0ab20后，按操作者摘录 x0=load64(S+0x2f8)；随后x1=load64(S+0x2a0)，调用0x1ab1744 |
| 0x1aa300c–0x1aa3014 | x0=S+8，x1为调用方保存于x20的第二入参；调用0x1a0c248 |
| 0x1aa30ac–0x1aa30b0 | x0=S；直接调用0x1aa3458，旧JSON索引与旧反汇编对此一致 |
| 0x1aa347c、0x1aa3494–0x1aa349c | 候选函数自身保存x19=S；传x0=S+8给访问器，返回后从返回对象+0x20、+0x28加载两个64位值 |
| 0x1aa3614–0x1aa3624 | 再次传S+8给访问器，x1=load64(S+0x2a0)，调用0x1ab1744后比较w0与1 |

访问器按操作者提供的指令可写为 getter(B)=load64(B+0x2f0)，不是返回 B+0x2f0，也不是直接读取S+0x2f0。B=S+8时，0x8+0x2f0=0x2f8。

对0x1a0c248：若其入口mov x19,x0之后，到相关加载处x19一直保存入口B，且两次加载结果到BL前未被改写，则调用参数为x0=load64(B+0x2f0)、x1=load64(B+0x298)。该旧调用点B=S+8，所以对应load64(S+0x2f8)、load64(S+0x2a0)。0x8+0x298=0x2a0。

操作者只给出0x1a0c384附近加载和0x1a0c3a4调用摘要，两者之间仍有指令区间未提供。x0/x1属于调用者保存寄存器，不能跳过中间赋值、BL/BLR、分支合流检查，直接认定BL时仍是这些参数。x19通常属于被调用者保存寄存器，但当前函数可自行重赋值，仍需全路径核查。其他调用者也不一定传入S+8。

旧调用顺序尤其需要注意：0x1aa2fac先读取；随后0x1aa3014调用0x1a0c248；再经其他调用到0x1aa30b0进入候选函数。中间函数可能改写相关槽位或所指对象，即使三处使用同一个S，也不能把不同时间的加载值等同。旧候选函数自身也在0x1aa3498与0x1aa3618两次调用访问器，不能在缺少写入与生命周期证据时自动视为同一快照。

## 0x1ab1744 的最小语义

按操作者提供摘要，令A为调用时x0，P为调用时x1：

```text
start = load64(A + 0x68)
end = load64(A + 0x70)
if start == end:
    return 0  // 依据操作者对该分支的描述
index = load32(P + 0x1c0)
return load32(start + zero_extend(index) * 4)
```

ldp x8,x9,[x0,#0x68]加载两个相邻64位值，第二个位于+0x70。cmp只比较两个值是否相等；这与连续序列的起止指针布局相容，尚不足以确认具体C++容器类型。非空路径把x8用作基址。

ldr w9会零扩展到x9，覆盖此前保存第二个指针的x9；因此末条不是用end索引，而是用P+0x1c0加载的32位值乘4索引。负的32位位型会按零扩展形成巨大正偏移，不能擅自把它还原为有符号下标。给定摘要没有显示索引上界校验；校验可能来自调用方或数据不变量，不能声称完整程序没有校验。也未显示空指针检查。

返回值是32位表项，写w0将x0高32位置零；不能仅凭加载指令确定业务上的有符号性、枚举、棋色、积分或布尔类型。空路径返回0与非空表项恰为0在该接口返回值层面不可区分。旧候选0x1aa3624只说明此处生成了返回值等于1的谓词。

这条数据流表明A提供表、P提供索引，两者存在运算依赖；不要求A=P，也不证明P是棋子、玩家、当前回合对象或红棋。

## 与旧 queenCovered 候选逻辑的关系

候选名称源于旧报告中的字符串引用定位，不是已确认函数签名或完整规则实现。旧摘录中，0x1aa349c取得一对值并按0x60步长遍历记录。记录+0x20的32位值记作tag，P=load64(S+0x2a0)。记录首先满足tag==0或tag==load32(P+0x1c0)，再经过记录+0x40起的字符串样式字段与P起始字符串样式字段比较。确切字符串类型仍需独立布局证据。

对通过这些过滤的记录，w24计数加一；w23在以下任一条件下被置1，并在后续循环中保持：

```text
(tag == 0 && mode == 2) || (mode == 4 && load32(record) == 0)
```

这里mode来自x20+0x18。x20并非S+8或访问器返回值：0x1aa3488先调用0x18d750c，其返回值再传给0x18d7948。按操作者提供的add/ret，若前者返回G，则x20=G+8，mode的有效地址为G+0x20。0x18d750c未在本轮读取，不能称G为单例、全局状态或指定业务类。

w23随后在0x1aa36fc取最低位，并进入0x1aa3708附近字符串键构造及后续处理链；这与旧报告的queenCovered定位相容。0x1ab1744返回值等于1的谓词则在0x1aa362c构造，并经更早的键处理链传出。两者是不同的数据流，不能把返回值==1直接改称queenCovered。未读取对应字符串字节、0x1aa763c、0x2706868及下游0x1aa38b8实现，故不能证明精确键值绑定、最终JSON/网络发送或实际生效规则。候选函数更像在汇集派生信息，但本轮不把此解释升级为已证明的序列化协议。

## 潜在误关联

1. 混淆S、S+8、load64(S+0x2f8)三种不同值；把嵌入子对象地址当成解引用指针。
2. 把相同槽位地址当成跨调用、跨时间的相同指针或相同对象生命周期。
3. 将0x18d7948的G+8与S+8混为同一个来源；它们分别来自不同上游。
4. 把P+0x1c0在比较和索引中的复用直接解释为棋色。现有证据仅表明它参与过滤和4字节表项选择。
5. 用同一寄存器名跨函数认定同一对象；旧候选在0x1aa3644等位置还将x19改为栈临时量，后续x19已不再是S。
6. 由地址邻近、FDE范围、字符串键名或直接BL边推断业务owner、实际可达或完整调用图。
7. 把新增摘要默认为旧包同构建，并忽略参数加载至调用之间的未见指令。

## 只读下一步：区分字段语义

建立假设表而非先命名：P+0x1c0可能是座位/玩家索引、阵营枚举、棋子分类索引或其他表键；A的32位表项可能是映射结果、状态枚举或数值。对每项分别找写入来源和消费方式。

优先寻找自然出现的可区分场景：座位相同但棋色分配改变；棋色相同但当前行动者改变；同局切换回合而物理棋子保持；红棋入袋未覆盖、随后覆盖、失败回置；普通棋子入袋与犯规；重开及新局。若游戏不支持某种场景，不人为声称已完成对照。每次记录同一生命周期中S、B、A、P、index、start/end、表项、mode、过滤结果与w23，并标记观测时点。

若index随座位固定而不随棋色改变，支持座位假设；若反之则支持棋色假设，但仍需写入来源印证。若表项只随回合变动，优先考虑回合状态而非固定棋色。单次相关不足以定名；应结合协议字段、构造参数、多个读取者及反例。对0、1、2、4等值维持中性命名，直到出现可区分证据。
