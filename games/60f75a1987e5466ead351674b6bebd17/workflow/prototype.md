# Freestyle 得分记录接入只读审核

## 范围与结论

本轮只分析用户正文提供的当前函数片段，不修改源码、不生成游戏、不推进美术、代码或测试阶段。总体结论：NEEDS_CONTEXT。接入已具有逐球类型捕获、固定得分方标签和部分跨局保护，但不足以证明真实入袋顺序、逐事件幂等及完整生命周期安全。若将数组顺序解释为真实入袋顺序，该解释为 FAIL。

任务走玩法逻辑审核方法，先定位记录与结算的 owner。所选模块具体引擎适用范围为 Cocos；本片段使用 PIXI/Tweener，因此仅采用证据分层、唯一 owner、稳定提交与生命周期分析方法，不套用 Cocos API 或案例数值。

## 当前调用链与规则状态

片段中的流程为：检查预期 turn 与 settled turn → 等待运动检查返回静止 → 标记本杆已结算 → Freestyle 分支复制待处理集合 → 逐球创建回收或计分动画 → 回调加分、追加历史和更新 HUD → 延迟检查胜负、犯规及切换行动方。

可见结算入口 owner 为 `_0xbdafb3`；玩家和对手分数/历史的直接写入 owner 为各自动画完成回调；另有延迟函数写入犯规扣分并推进回合。物理入袋事件 producer、待处理集合的排序 owner、新局及退出 owner 不在当前片段，不能确认全工程唯一写入者。

最小状态涉及 active、round、turn、settled turn、双方分数、待处理棋子、犯规/续杆标记及 history。原有界面可见双方分数目的节点；未提供历史展示界面，本轮不新增布局或玩家文案。

## 具体发现

### 1. 类型、颜色、分值与得分方

PASS（仅静态局部）：`let _carromScoredDiscType = _0x34b477._type` 位于循环体，每次迭代具有独立词法绑定，避免所有回调读取最后一个棋子类型。记录类型在创建动画前捕获，而不是从之后可能移除的棋子读取。

NEEDS_CONTEXT：`_type` 的合法枚举、颜色资源映射、混淆属性 `_0x5a7eab(0x284)` 是否对应同一字段，以及 `_0x1c2aac` 分值表均未给出。因此不能认定某 type 就是白、黑或红，也不能宣布颜色分值配对通过。points 从计分文本节点的 value 类属性读取，且与本回调加分读取相同属性，局部上来源一致；仍需核对数值类型、有限性及是否会被其他代码修改。

PASS（仅静态局部）：`_0x209883` 在安排动画时选择分支；玩家回调固定给 `_0x4d3bf1` 加分并写 actor='player'，对手固定给 `_0x41f634` 加分并写 actor='opponent'。回调没有重新读取行动方来决定 actor，因此之后行动方变化不会直接把这两条记录的 actor 翻转。actor 表示得分方，不等于棋子颜色或棋子所有者。实际 `_0x209883` 与玩家身份的映射还需当前调用方佐证。

### 2. 同杆多球异步顺序

FAIL（若要求真实入袋顺序）：history.push 发生在动画 onComplete。玩家动画 time 为 `0xf + Math.random()*0xa`，完成顺序可能与集合迭代顺序相反；对手固定 time=0xf 也不能建立真实物理先后保证。即使回调完全按创建顺序完成，待处理集合自身是否保存物理入袋顺序仍未证实。round/turn 只能分组，不能还原杆内先后。

当前数组准确语义至多是“成功执行计分回调的提交顺序”。若需要真实入袋顺序，应在真实入袋 producer 捕获不可变的 round、turn、discId、actor、type、points 和 pocketSeq；同一物理步中的多事件还应定义可复现的平局排序。这是建议，未实施。不得用排序动画时长或增加延迟来伪装物理顺序。

### 3. 重复结算与重复回调

PASS（有前提）：入口检查 expected turn 等于当前 turn 且未 settled，并在安排动画前设置 `_carromSettledTurn`，能阻止同一有效 turn 再次从此入口安排整批结算；依赖 turn 标识管理正确。

NEEDS_CONTEXT：入口去重不等于回调去重。两个计分回调均没有逐球 eventId/consumed 标记，重复调用同一 onComplete 会再次加分和 push。现有片段没有证明 Tweener 会重复回调，也没有证明所有来源恰好一次；应将其登记为缺少幂等防线，而非宣称已经发生重复计分。若 `_carromReportScore` 或清理抛错，前面的加分和 push 已发生，也不能靠盲目重放整个回调恢复。

### 4. 迟到回调、退出与重开

PASS（局部条件保护）：计分及回收动画回调先检查 active 与捕获 round 是否仍等于当前 round。若新局在旧异步工作执行前可靠更新、不复用 round，该保护可阻止旧回调给新局加分或追加记录。round 在 `_0xbdafb3` 本次调用时捕获，turn 通过参数闭包保留。

NEEDS_CONTEXT：仅将 history 清空不足以隔离旧回调；还需确认新局更新 round、turn/settled 的顺序及唯一性。若新局复用 round、只清空数组或仅暂时切换 active，旧回调可能写入新数组。递归静止检查只带 expected turn，不带 round；若跨局 turn 可复用，旧重试可能重新进入新局。

计分回调不检查当前 turn 是否仍是 expected turn，同局迟到回调仍会入账且标记旧 turn。不能简单规定 turn 不同就丢弃：若旧杆分数仍应有效，直接丢弃会漏账。正确边界取决于“整杆提交完成后才推进”或显式 pending/commit 政策，需要当前实现证据。

片段末尾延迟函数只有 active 检查，没有 captured round/turn 检查。若定时器未由新局/退出统一取消，旧任务可能检查新局分数、扣分或推进新局行动方。这是静态可见的保护缺口，实际是否可触发取决于 `_0x338c29` 及清理 owner。

失效回调仍会移除旧表现节点；若对象池复用节点，该清理也需验证对象身份，不能仅依靠 parent 存在就证明安全。没有对象池证据，当前仅登记条件风险。

### 5. 动画完成、胜负及输入窗口

NEEDS_CONTEXT：延迟结算用 `_0x4e7344`（初始0x1f4，处理球后0x3e8），动画 time 使用0xf等值；不能在未读调度器/Tweener实现时假设这些时间同单位，也不能证明固定延时必然覆盖所有动画。若延迟胜负判断先于最后计分回调，会使用部分分数；若结局关闭 active，未完成回调还可能被拒绝。

片段显示任一分数达到 `_0x153877` 时，以当时 `_0x209883` 调用胜负函数，不直接以达到阈值的一方选择胜者。正常单杆只给行动方加分时可能符合规则，但迟到跨杆计分会破坏此前提。胜负检查位于犯规扣50之前，同杆达到阈值并犯规时，当前顺序会先走结束分支；是否应先扣罚属于待明确政策，不自行判定为规则错误。

核心循环应在规则层完成整杆唯一提交后再决定胜负与下一输入窗口，动画只呈现结果。这是后续建议。当前未提供瞄准/发射输入锁、暂停、时钟单位或完整结束状态，不能宣称动画期间输入和终局提交已安全。

### 6. 红球与后续犯规政策

NEEDS_CONTEXT：未见独立红球判定、cover/待覆盖状态、退球/补球、红球失效与后续撤销规则；不能从普通加分回调推断红球立即永久得分，也不能自动套用正式 Carrom 规则。`_0x530863` 分支回收/重建棋子且不写本次 history，其真实含义须当前定义证明，不能直接称为红球或某种犯规分支。

当前 history 只记录这两个正向计分回调。可见后续犯规分支给行动方扣0x32（50），没有对应 history 事件。因此它不是完整净分账本；在该扣分发生时，“正向记录总和=最终分数”不成立。`_0x52e61d` 的具体退球行为未提供，不能认定它撤销哪些记录。

后续需先确定记录目标：若是“曾经成功加分的棋子”，可保留历史事实并另标撤销/返还；若是“当前有效得分棋子”，需稳定discId及有效状态；若是“可重算净分账本”，需 penalty/reversal/queenPending/queenConfirmed 等符合实际规则的事件与关联，不能只用 type 找最后一条删除，同色多球会产生歧义。本轮不替用户选定红球或犯规新政策，也不修改实现。

## 验收条件建议（均未执行）

| 场景 | 后续应取得的证据与判据 |
|---|---|
| 颜色与归属 | 当前枚举、贴图映射、分值表及双方各色真实入袋；type、points、actor逐项吻合 |
| 多球顺序 | 同杆至少两球，强制反向完成动画；物理pocketSeq不变，回调顺序单独记录 |
| 重复与缺失回调 | 同事件重复回调只提交一次；取消动画不导致应得分数或记录丢失 |
| 同局迟到 | 下一杆/结局边界前后释放旧回调，归属、总分、胜负及记录符合明示政策 |
| 新局与退出 | 在静止轮询、计分动画、延迟扣罚三个窗口重开/退出；释放旧任务后新局分数、history和行动方不变 |
| 红球与犯规 | 覆盖成功、未覆盖、同杆犯规、后续返还/撤销、达到目标同时犯规，按已确定政策核对 |
| 阈值与推进 | 所有本杆有效事件提交后判胜负；结束后不再重复推进或领奖 |
| 物理与输入 | 用固定输入/时间步和快慢帧记录真实入袋事件；核对输入锁与暂停恢复 |

本轮不定义或更动物理参数：当前物理步长、碰撞体、睡眠阈值、输入窗口、最大补步及位置/速度容差均未提供，不能编造。后续物理复测需记录实际参数与允许误差；账本事件身份、数量、actor、整数points及生命周期归属应精确一致，不能用物理误差解释重复或错归属。
