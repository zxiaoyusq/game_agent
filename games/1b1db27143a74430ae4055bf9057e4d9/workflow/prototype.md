## 核心结论

1. 145041.2ms 记录的是普通玩家棋即时入袋；该记录明确为 `piece=1, actor=true, pendingBefore=false, queen=1, player=1, opponent=3`。不是145041ms已经覆盖红棋的证据。
2. 145116ms 首次采样到 `q=0,pending=true`；145720.5ms 才采样到覆盖图标可见且未填充。这是规则状态与表现动画的先后，不能用图标出现时间充当红棋入袋时间。
3. 147417.7ms 玩家计数从1变2，与145041.2ms普通棋的延迟结算相容；不能将该计数变化算作红棋之后新进的一颗覆盖棋。
4. 157423ms 采样到红棋在盘数量恢复为1、pending清除、图标隐藏、turn=false，符合源码未覆盖时返场后换方的路径，但日志不足以唯一证明触发原因、确切执行时刻或杆号。
5. 当前普通棋入袋分支对两种棋色都无条件清除pending；续杆资格却按棋色和出杆方分别设置。这是源码可定位的状态条件不一致，其是否违反目标产品规则仍需明确规则契约；不能借竞品规则作裁决。

## 字段语义与采样限制

`pockets`为普通棋即时入袋记录，14条；`queen`为约每100ms检查、发生变化才保留的状态快照，46条。JSON本身没有附带采集脚本，采样机制及字段命名采用任务提供的说明，无法独立核验钩子位置、数据是否完整或时间源。时间按同一日志的相对毫秒关联，不换算为现实钟点。

源码中类型1被创建为`player`、类型2为`oponent`、类型0进入红棋数组`_0x3231b3`。`actor/turn`与`_0x209883`的玩家/对手标志相容，不能当成棋色；实际黑白贴图映射尚未完整解码，报告使用玩家棋、对手棋而不武断指定黑白。`q/queen`按盘上红棋数量解释；`visible/filled`按覆盖标记的表现解释，并非整颗红棋是否可见。

变化日志未列出的区间不能视为没有发杆、没有物理变化或没有短暂状态；同一方可连续获得回合，turn不变不代表没有换杆。100ms是名义采样周期，不是已验证的最大误差；没有原始每次采样时间和调度延迟，不能给出严格±100ms保证。

## 源码状态路径

### 即时入袋与延迟计分

`_0x49d791`先检查红棋数组，再检查玩家棋、对手棋。距袋心不超过`0x14`（20个逻辑坐标单位）触发入袋；即时移除刚体及盘上数组成员，执行袋口动画。普通棋通常进入`_0x31089b`等待结算。

红棋入袋即时将`_0x5ebd99=true`及`_0x4268e2=true`，保存`_carromPendingQueenPocket`。非Freestyle模式经过15 tick袋口动画及20 tick飞往HUD动画后，保存`_0x404020`并显示填充/未填充标记。状态早于图标可见是源码的正常分层，不能单独视为漏球。

普通模式的`_0xbdafb3`等待物体停止后启动飞向所属HUD的动画：玩家棋20至不足30 tick，对手棋20 tick；完成回调才分别增加`_0x4d3bf1`、`_0x41f634`。约1000ms结算回调还会强制提交尚未完成的计分回调，并以完成标记去重。因此计数变化晚于入袋，且包含运动等待、结算和动画，不能拿两者差值只测动画耗时。

### 覆盖与续杆条件

两种普通棋的四个袋口分支均执行：若pending则更新填充纹理；记录`_carromQueenClearedThisShot`；随后无条件`_0x4268e2=false`。玩家棋只有actor为玩家或模式为Freestyle时才设置`_0x5ebd99=true`，对手棋则只有actor为对手或Freestyle时设置该标志。

所以覆盖清除与续杆判断不是同一条件；非出杆方棋色也能清除pending。这是当前代码行为，不代表已证明合法或非法。普通棋先入袋而红棋后入袋时，前者无法预先清除尚未建立的pending；晚到的计分回调也不重新执行覆盖。这解释了为何147417.7ms计数上升不必令pending变false。

但现有日志缺少shotId/turnId与红棋即时钩子，不能证明145041.2和红棋离盘属于同一杆；更不能据此宣称已实测所有同杆先后顺序。红棋循环先于普通棋循环还使同一模拟tick的处理顺序由代码组别决定，不能代替连续物理时间的真实先后。

### 157423ms返场的可达路径

普通模式结算在`pending && !续杆标志`时走返场。模式1中若红棋仍在入袋动画，先把`_carromPendingQueenPocket`移交`_0x404020`；随后`_0x52e61d(callback)`搜索中心附近位置，播放15 tick返场动画，完成后新建类型0刚体并压回红棋数组，清除pending、隐藏标记，再推进回合。该顺序与157423ms快照一致。

新玩家/AI回合分别重置续杆、犯规及本杆覆盖标志，并递增`_carromTurnId`，pending可以跨回合保留。未覆盖的后续回合、超时、AI无合法候选等均有进入结算的代码路径；犯规还可能恢复待覆盖标志。由于缺少`_0x5d148e`、`_0x5ebd99`、`_0x530863`、turnId、计时器与调用栈，不能断言157423ms就是某一具体路径，更不能用12.307秒直接定义覆盖输入窗口。

## 当前实现契约与体验问题

现有循环为观察棋盘→基线摆放→拖拽瞄准释放→物理运动及入袋→停稳结算→续杆/换方/红棋返场/终局。源码为PIXI表现与Planck（别名box2d）物理，不能因本轮profile选择原生Web而将已有实现称为纯DOM或SVG。界面已有左右计数/HUD、棋盘、摆放滑条、瞄准提示、回合计时框及覆盖标记；本轮未查看实际截图或文字资源，不评价最终视觉与默认语言验收。

| 项目 | 源码所示 / 审查结果 |
| --- | --- |
| 物理步长 | 每次更新`world.step(1/60,10,10)`；ticker增量累加，`while(accumulator>1)`补步。可见循环未设置补步次数上限；大delta可能集中补步并阻塞输入。长帧真实影响未执行验证。 |
| 入袋与碰撞 | 入袋采用离散位置到袋心距离≤20；实体碰撞交给Planck。固定步长不保证高速必不漏过袋口，需高速轨迹验证。不能将入袋阈值20误当碰撞半径或误差容许值。 |
| 输入窗口 | 玩家准备状态且玩家回合、未暂停、指针身份匹配才开始瞄准；释放力度≥0.25才出杆，力度上限1、发射参数为力度×125。回合计时按tick递减，具体turnTicks来自未提供的CarromDiscRules，不编造秒数。 |
| 成功失败 | 普通模式依赖外部`hasWon`及红棋盘上数量、actor判断；Freestyle阈值160且依赖外部freestyleQueen。日志始终result=false，未观察终局；外部模块未读，不能给出完整规则保证。 |
| 可接受误差 | 本轮无已测物理容差。后续应要求离散规则事件与计数严格一致；轨迹位置容差单独校准，不以空间误差允许重复计分或错误换方。 |

需要关注的缺陷与风险：

1. **覆盖条件缺少棋色/所有者约束（源码确认）**：pending被任意普通棋清除，而续杆条件不同；如产品要求本方棋覆盖，会出现覆盖提示与回合结果不一致。目标规则未确立前，不称为违反官方/竞品规则。
2. **得分提交依赖动画（源码确认）**：存在明显反馈延迟，玩家可能将后到的计数误认作覆盖。已有强制提交与去重防护，不能夸大为已发现重复计分或丢分。建议后续将规则提交和飞行动画分开，并记录提交原因。
3. **普通模式按对方剩余棋数跳过入袋队列（源码确认）**：玩家棋在模式1且对手盘上数组为空时不入队，对手棋对称处理；分支及动画完成分支为空。可能出现已离盘却不计数、节点残留或终局受影响，需构造末局复核，不能说本快照已触发。
4. **返场搜索无明确失败结果（源码确认）**：`_0x1f3ae5`轴向、对角与网格搜索均失败后仍写回原位置；检查仅针对棋子距离，没有在该函数中显式校验盘界。拥挤场景可能重叠，需边界验证。本次返场快照没有位置，不证明实际重叠。
5. **终局检查先于未覆盖返场（顺序确认，后果待验）**：普通模式先判`hasWon`再执行pending返场；盘上红棋数量0不能区分已覆盖与待覆盖。应补测最后普通棋、红棋待覆盖、犯规组合；外部规则缺失，暂不宣布已发生误胜。
