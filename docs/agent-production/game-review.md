## 回归 A：360px 设置按钮命中区相互覆盖（已关闭，以下为原失败证据）

优先级 P2。位置：`src/main.mjs:270`，`showSettings()` 的声音、数字辅助、快速动画行；`button()` 把命中高度统一扩大到 44 CSS px，行中心间距仍固定 58 设计单位。

真实复现：

1. 独立 360×640 context 打开设置。声音按钮中心 `(180,380)`，高度 44；数字辅助中心 `(180,418.6667)`，高度 44。
2. 两者中心差只有 38.6667px，命中区重叠 5.3333px。
3. 点击声音目标内部的底边 `(180,401)`，距离其中心 21px。
4. 实际声音保持 `true`，数字辅助从 `false` 变 `true`：点击被后创建的相邻按钮接走。

根因：只放大 UITransform，没有同步增加同一面板内相邻控件的间距。数字辅助与快速动画的排列使用相同间距，也需一起核验。

最小修复建议：让设置面板中所有相邻按钮的实际 CSS 命中区域互不相交，同时保持至少 44px，并检查小屏下整面板不越界。回归应覆盖每个设置按钮的上下边缘，核对只有对应设置改变；不能仅断言 UITransform 数值为 44。

## 回归 B：截断历史撤销后刷新丢局（已关闭，以下为原失败证据）

优先级 P2。位置：`src/storage.mjs:51`，`anchored` 仅在 `session.history.length===500` 时允许历史从合法中间状态开始。

真实复现：

1. 用与现有“500条截断历史”单测相同的规则路径构造合法长局：经典第 1 关先 1→4、加空管，随后 4→5、5→4 往返 500 次。每一步都由当前 `applyMove` 计算，500 个保留快照逐笔合法；没有注入无效移动或胜利。
2. 将这份长局快照放进独立 context 的存储并刷新，游戏正常接受：`moves=501, extra=true, storageRecovered=false`。
3. **实际点击撤销按钮**，状态变成 `moves=500`，保存的历史长度 499。
4. 再刷新，变成 `moves=0, extra=false, storageRecovered=true`，提示“已修复异常存档”；合法长局被丢弃。

边界：长局快照通过规则构造并注入，未在浏览器实际执行全部 500 次动画；导致错误的撤销与刷新是实际界面操作。其初始快照与代码阶段已有单测所接受的截断历史一致。

根因：是否截断由“当前历史数组恰好为 500 条”推断。撤销合法地缩短数组后，起点依然是中间状态，却被要求重新等于初始棋盘。

最小修复建议：显式保存并校验历史截断事实及基点，在移动、加管、撤销、保存、恢复中一致维护；区分正常从初始局开始的历史与确有截断依据的历史，继续逐笔验证合法事务。不能简单允许所有非初始快照。至少回归：达到上限→撤销一次/多次→刷新、再移动后刷新、旧未截断存档、伪造截断元数据与现有损坏历史拒绝。

## 4. P2：恢复历史不检查相邻事务，可撤销到错误棋盘

位置：`games/ball-sort-fusion/src/storage.mjs:28`、`:34`，`validSnapshot()` 和 `session.history.every(...)` 只检查尺寸、颜色总量、类型及步数上界，没有验证历史相邻状态的合法关系。

最小复现：

1. 新 context 经典第 1 关依次操作 1→4、3→1，当前步数 2。
2. 正常的最后历史条目为 `board=[[2,2],[3,3,1,1],[1,1,2,2],[3,3]], moves=1, extra=false`。
3. 仅将 `session.history[1].board` 替换为初始棋盘 `[[2,2,3,3],[3,3,1,1],[1,1,2,2],[]]`，保留 `moves=1`，刷新。
4. `storageRecovered=false`，无恢复异常提示。点击撤销后直接跳回初始棋盘，但步数仍是 1。

实际影响：一笔撤销跨过了两次有效移动，历史与步数不一致。颜色守恒的历史损坏仍会被静默接受。

预期：恢复时核对历史相邻状态及其到当前状态的可逆关系，合法一步只能对应一次规则允许的移动或增加空管；坏历史应按原型可见恢复，不能供玩家继续撤销。需要兼容现有 500 条历史截断上限，不要求无限保留历史。

## 5. P1：每次重绘留下 Cocos 节点，持续操作明显增加保留内存

位置：`games/ball-sort-fusion/src/main.mjs:59`，`clear(parent)` 仅 `removeAllChildren()`；`renderBoard()`、`updateHud()` 在选中、取消选中、移动、撤销时重复调用。

最小复现：新 context 经典第 1 关，不进行移动，在同一支非空管上连续真实点击以交替选中/取消。设计坐标 `(123,473)`；540×960 下与鼠标坐标相同。每 200 次点击等待 100ms，然后通过 CDP `HeapProfiler.collectGarbage` 主动回收，再调用 `Runtime.getHeapUsage`。使用 `Runtime.queryObjects` 查询当前引擎模块 `cc.Node.prototype` 的实例，读完计数后释放整个调试对象组，避免调试器自身持有查询结果。

独立新页面的实测结果：

| 累计点击 | GC 后 JS 堆字节 | Cocos Node 实例 | 无 parent 的节点 | 试管节点 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 8,554,216 | 65 | 3 | 4 |
| 200 | 43,752,188 | 5,466 | 1,004 | 804 |
| 400 | 77,296,488 | 10,866 | 2,004 | 1,604 |

可见棋盘始终只有 4 支管，状态仍是初始棋盘，400 次点击后却保留 1,604 个试管节点。另一独立测试的 GC 后堆为 8.96MB→45.18MB→80.16MB，增长方向一致。正常测试过程中没有发生浏览器崩溃，因此不把崩溃写作已复现事实；持续线性保留对象会增加移动端长时间游玩的内存压力。

预期：更换界面内容时显式销毁旧子树，或安全复用节点；等待销毁帧并强制 GC 后，节点数量和堆大小应稳定在有限范围。修复后重复同一点击场景，确认旧节点、事件及 Graphics 资源没有持续累积，同时验证重新绘制和点击仍正常。
