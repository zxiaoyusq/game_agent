# 按交付需求选择技术配置

先选目标平台和需要的能力，再选实现。品类与引擎是两个维度：排序可以使用不同渲染方式，同一引擎也可承载多种休闲游戏。

| 配置 | 选择依据 | 本项目证据与边界 |
| --- | --- | --- |
| Cocos Web | 需要场景/节点/组件、精灵和音频等引擎能力，接受对应工具链 | 当前可执行，已有 Ball Sort 官方 Cocos 3.8.8 Web 案例；其他品类须独立验收 |
| Canvas Web | 轻量 2D、独立规则和简单绘制足够，愿意显式处理输入/资源/生命周期 | 执行协议已适配，待完整项目验收；初始指南，尚无完整四阶段成品验证 |
| Creator 原生/小游戏 | 需要编辑器工程或平台专属包、插件和发布流程 | 待适配方案，不是当前可执行技术配置；须增加环境、构建、预览或设备验收接口 |
| Unity / Godot | 团队或产品明确需要对应编辑器、生态或目标平台能力 | 待适配方案；已有研究资料不等于工作流具备对应构建执行器 |

当前受支持配置统一提供 `npm run build`、`npm test`、`npm run check` 与 `dist/index.html`，遵守已确认报告及资源清单契约。配置只表达实际执行接口，不能靠更换下拉框名称把 Web 执行器包装成原生构建能力。

原型报告记录选择理由、版本/依赖、目标平台和不覆盖的能力。需要“最新”版本时核对官方发布信息并固定实际版本；案例中的固定版本不自动更新。引入新引擎前先完成最小构建、真实运行、输入与资源加载的可重复证据，再标为受支持；不为未来可能使用的引擎预先创建复杂适配层。

复用品类知识、交付契约和经验证的独立模块，避免先复制整个 Ball Sort 工程再删除不需要的机制。框架或品类改变后重做相应原型决策，已有成品的验收结果只作为案例依据。
