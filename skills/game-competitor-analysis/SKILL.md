# 游戏竞品拆解与融合设计

接受一句话输入游戏名，产出足够支持后续策划、美术和原型制作的研究报告。重点解释“设计如何起作用、对谁有效、有什么代价、如何独立实现”，不是拼接商店介绍。

## 输入与默认决策

- **具体产品名、包名或商店链接**：先确认开发商、平台和产品身份，以该产品为研究主体。用户只要求单款时保持单款；要求竞品或综合设计时再补充同类对照，不把指定产品替换掉。
- **玩法名称或泛称**（如 Ball Sort Puzzle、螺丝消除）：默认从同一核心玩法选择 3 款材料充分的代表产品。满足条件不足 3 款则说明缺口，不用邻近玩法凑数。
- **明确列出多款**：逐款核实，按用户名单和数量分析。不要擅自换成所谓更头部的产品。
- 默认中文详细报告。平台、市场沿用上下文；仍缺省时优先研究 Google Play 公开资料，注明地区/语言，跨平台材料单独标注。研究日期取本次实际日期。
- “AI 容易实现、美术轻量”来自用户要求或已有上下文时，作为融合方案的重要约束；不要把所有类型游戏都强改成低成本休闲游戏。
- 同名歧义只有在影响研究主体且无法从上下文消除时才询问；同时继续不依赖身份选择的资料整理。其余非关键缺省值直接在报告范围中说明。

## 1. 确认身份与选择样本

先查看用户提供的已有报告、榜单和资料，随后联网更新易变化的数据。读取 [研究与证据规范](references/research-and-evidence.md)，按包名/App ID 建立身份与来源表。

选择竞品同时考虑：同玩法可比性、规模或当期榜单证据、设计差异、公开材料覆盖程度。说明“头部”采用的口径；累计下载不能证明当前收入、活跃或新增排名。用户给定榜单的原有样本与联网新增样本要分开标注。没有可靠排名时使用“代表产品”，不要声称“全球前三”。

不把之前 Guru、HM Games、Infinite Joy 的结论、日期、数字或名单套到新任务；每次重新核实实际研究对象。

## 2. 收集资料并真正查看视觉证据

优先访问官方商店、开发商网站、帮助/更新说明；补充有时间信息的评论、实机视频和第三方指标。查询困难时尝试可用官方地区页面或替代可靠来源，仍不可访问就记录限制，不无限重试或冒充已读。

每个产品优先覆盖：主界面/棋盘、一次操作、局部完成、失败或恢复、通关、成长/主题、特殊模式等关键状态。商店图可以作为起点；8 张/款是历史案例数量，不是通用硬指标。

- 只对实际查看的图像作画面判断；把“收集”“查看”“实机验证”分开记录。
- 商店展示图不等于实机截图，营销文字不等于当前解锁规则。
- 视频记录实际观看区间；没有观看和测量就不填写动效毫秒、音频描述或广告频率。
- 本地已有图片直接复用。远程图片使用当前工具允许的查看方式；不能为了绕过显示限制下载。确实支持保存研究材料时记录来源及文件，保存不可用则保留链接和缺口，不阻塞其余研究。
- 无需为了产品研究自动下载或反编译 APK。用户另行要求工程拆解时，再衔接 APK 分析流程。

## 3. 逐款拆解，再比较和取舍

读取 [分析维度与报告结构](references/analysis-and-report.md)。完整覆盖用户要求的玩法、爽感、美术、核心设计；其他维度按真实相关性和证据扩展。

每个重点设计按以下链条解释：

> 可观察设计与证据 → 玩家动作/决策 → 即时反馈 → 满足的需求 → 生效条件与代价 → 可借鉴的独立实现 → 验证方法。

标注 `官方声明`、`画面观察`、`实测/视频观察`、`玩家反馈`、`设计推断`、`新作建议`。不要把观察到的按钮推成内部算法，不把一条差评推成用户比例，不把设计建议的参数写成竞品实测数据。

融合方案需要明确取舍：哪些保留、哪些改造、哪些舍弃，冲突如何解决。给出 MVP、后续阶段、关键资产规格、验收标准和实验假设。不能承诺把所有优点相加必然成功；也不要把竞品素材复制当作原创美术方案。

## 4. 产出可阅读、可追溯的报告

读取 [交付与验收](references/delivery.md)。默认输出到新的产品研究目录，文件名/目录名根据本次主题生成，不覆盖旧报告：

- `report.md`：详细报告源稿，正文就近引用来源。
- `index.html`：带目录、表格和展示图的阅读/打印版。
- `sources.json`：产品身份、来源、访问日期、指标口径和证据覆盖。
- `screenshots.json`：已收集/查看图像的来源、类型、观察与限制；没有图像时使用空列表并说明原因。
- `evidence/`：可用的本地研究材料，不保证所有网页都可离线保存。

默认报告源稿遵循本技能约定的 Markdown 格式；若用户明确指定其他格式或目的地，以其要求为准。无需为了产出文件新建外部 Page。只有用户要求时才发布到现有知识库/外部页面，不自动修改知识库分类。

报告内容完成后，可使用通用渲染脚本：

```bash
python "$SKILL_DIR/scripts/render_report.py" --source "$OUTPUT/report.md" --title '实际研究主题：竞品拆解与融合设计' --output "$OUTPUT/index.html"
```

`SKILL_DIR` 是此技能目录，`OUTPUT` 是本次产物目录。环境缺少 Markdown 时按 `scripts/requirements.txt` 安装到项目允许的环境；脚本不执行联网搜索，也不自动编造分析。只渲染 Agent 写出的可信源稿，不把抓取网页原样作为 HTML 输入。

脚本内嵌本地图像并记录真实格式，远程图像保留在线依赖；输出的渲染清单只验证技术结构，不能证明研究真实或分析完整。有浏览器工具时检查目录跳转、表格、图片和移动端排版。最后给出报告链接、研究对象、已查看图像数量与重大证据限制。
