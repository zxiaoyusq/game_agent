# One Connect 后续迭代 Implementation Plan

> 2026-10-30 更新：DSH 最终交付及用户最新单入口要求的执行顺序，以 [DSH 结果驱动开发计划](One_Connect_DSH结果驱动开发计划.md) 为准；本文保留历史计划与未冲突约束。

**Goal:** 在保留 Construct 2 原版可运行基线的前提下，逐步建立可配置关卡、可靠棋盘、引导、道具和统一 UI，参考 Tile Connect 的已验证体验。

**Architecture:** 沿用 `game/` 中 Construct 2 导出运行时，通过已有配置编译器和经过验证的事件钩子扩展；先在独立验证副本实施，确定运行边界后再合入。关卡、牌面、引导与广告策略分离配置，不能将 Unity 竞品数据或代码直接当成 C2 可运行数据。

**Tech Stack:** Construct 2 H5、JavaScript、Python 关卡编译工具、现有浏览器测试及 MuMu Android WebView；目标宿主 AHA。

## 全局约束

- 每轮开发检查两个指定 DSH 会话的实时状态、最新公开进展及交付物：逆向调研 `session-f2e79f49-7150-4f0c-88ae-8d7f9a34b729`；美术生成及简单 QA `session-2c2bed39-0b88-42d9-8df8-6224aa2df638`。核对结果后继续主线开发，完成后及时验收并安排后续任务；运行中不抢占或重复派发。生图返修限定轮次并由主代理复核。后续子任务不再派给 Codex 子代理。
- 定期盘点并清理开发中的废弃 QA 临时文件和可重建缓存；核对归属与用途，保留用户资料、原包与基线、当前候选、未验收成果、必要验收证据和回滚材料。向两个 DSH 会话派任务时同步此约束，各自只清理其明确创建且已确认废弃的临时文件。
- 定期执行加载速度和对局卡顿的性能排查，记录版本、设备、缓存和场景，先定位资源、解码、主线程或帧时间瓶颈，再优化并同条件复测；包体大小、加载表现和对局性能均以不差于 AHA 原版项目为目标，真机及 AHA 宿主验证与本地测试分开记录。
- 原始 ZIP、原始解包和 `baseline/` 只读保留；修改前记录当前 `game/` 的版本、差异与可回滚副本。
- 先整体评审玩法、生成、道具与 UI 的关系；竞品 IL2CPP 深入分析由 DSH 进行，结果未到时只落实不依赖其结论的工作。
- 竞品现有证据覆盖 1–10 关，11 未通关，15/20/30 未到达；区分自动操作、人工操作、静态数据与推测。CSV 中冲突状态需核实。
- 用户已通过的当前美术风格继续沿用；原版连线及消除特效不替换。斋月备用 20 张已通过，仅在需要新增牌面时使用；禁止猪及不适合目标市场的内容。
- 仅 IAA：不开发竞品内购、订阅、支付、定价和礼包商业化；平台、广告位及参数尚未确定，模拟结果不能称为真实 SDK 验收。
- 实施时对体验变化保留原版模式和配置开关；无配置时保留原行为。效果、交互、构建与设备证据分别记录。
- 预装性能比较使用同一 MuMu、同版本容器、同缓存状态与相同测量点比较原版和当前版；目标优于原版，无 3 秒硬门槛。性能未测得之前不宣称达标。

**涉及**：`baseline/data.js`、`game/data.js`、`game/board-hooks.js`、`extract/c2_project_model.json`（原始拆解目录）、`tests/`；新增 `analysis/后续迭代/规则对照.md`。

- [ ] 定位原版棋盘创建、配对、路径、提示、洗牌、无解检查、计时和消除事件；记录 SID、变量及调用时机，以当前包为准。
- [ ] 构造直连、一次转弯、两次转弯、外环绕行、遮挡、不可连和无合法对的可控盘；先用纯逻辑对照，再在运行副本中操作。调试布盘只能用于规则验证，不能称为自然进度。
- [ ] 分别验证开局、消除后和手动洗牌后是否触发无解判断；记录是否自动洗牌、是否消耗次数和对倒计时的影响。
- [ ] 读取 DSH 后续代码追踪结果，逐条链接证据，区分竞品已确认与 One Connect 已确认。无法确认的规则不反向填成事实。
- [ ] 产出：规则差异、可安全挂接位置、死局现状和设计决策。验收：每个关键规则均有可重放局面或标记为未确认。

**涉及**：`config/levels.json`、`config/board-validation.json`、`tools/compile_levels.py`、`关卡编辑.html`、`tests/test_levels.py`、`tests/board-editor.cjs`；新增 `analysis/后续迭代/首批关卡方案.csv`。

- [ ] 先依据竞品配置及原版规则设计首批小规模关卡，逐关列出编号、目标体验、计时、可用牌型数、棋盘与教学触发；不能把竞品 30 种图集上限直接等同实际牌种。
- [ ] 现阶段只将现有固定 6×12、1–20 牌型和时间能够表达的示例写入独立配置；未支持的空洞、尺寸及方向字段仅留在方案中。
- [ ] 维持配置编译的输入校验、失败不覆盖旧产物和默认回退；新增可导入导出、重复编号与错误提示的必要检查。
- [ ] 为至少两个代表关卡验证编辑→导出→编译→游戏加载→自然完成→进入下一关；保留截图、配置和日志。
- [ ] 产出：可编辑配置、示例、使用说明。验收：修改和新增关卡确实生效，未配置关卡仍按原行为运行；后续编号推进须独立验证。

## 目标 3：可解性和自动洗牌

**涉及**：经目标 1 确认的棋盘逻辑与 `game/board-hooks.js`；新增独立棋盘规则/校验模块及 `tests/` 中对应测试。

- [ ] 以已核实的路径规则建立纯逻辑判定，覆盖障碍、外环、零至多次转弯和不同棋盘边界；用原版局面逐例交叉验证。
- [ ] 将“能找到下一对”和“存在一条完整解”分为两个接口；对求解超时返回未知，不把超时当无解或有解。
- [ ] 依据目标 1 的原版行为决定是否保留或新增自动洗牌；新增策略应限制尝试次数，失败时提供可恢复处理，确保牌种数量和剩余数量一致。
- [ ] 覆盖无匹配、只有一对、连续洗牌仍无结果、动画中输入、暂停/恢复、时间、计数和重开；不得消耗玩家手动道具，除非产品明确选择。
- [ ] 运行自然操作回归：实测清除、出现死局、处理后继续及胜败；记录实际触发证据。验收：不死循环、不丢牌、不误计数、可继续操作。

- [ ] 研究图集空间、帧定义、编号、配对、渲染、随机生成、保存及洗牌的扩容边界；不改原资源源文件，测试副本中实现并保留图集回滚。
- [ ] 先用少量新增帧做纵向验证，再批量处理；每张牌保持可辨识、符合原主色约束与目标市场文化要求。

## 目标 6：新手引导与道具

**涉及**：目标 5 的方案、`game/event-hooks.js`、经验证的 C2 事件位置、`config/`、`tests/`；独立的引导与道具配置和脚本按事件边界建立。

- [ ] 为首关设计固定教学棋盘与步骤：指定目标、高亮、手势、遮罩、错误反馈、暂停计时和完成标记；配置可关闭，旧存档不强制重置。
- [ ] 对提示、刷新、锤子等逐项评审现有能力与新增价值，定义目标选择、库存、解锁、效果、失败反馈与引导免费次数；不把竞品静态字段当成实测效果。
- [ ] 对引导测试误触、重复点击、退出重进、重开、暂停、横竖屏及目标不可用；对道具测试零库存、使用中断、动画、死局、计数一致性。
- [ ] 自然游玩首关并进入后续关，用真实点击验证教学、计时恢复及道具；事件记录教学开始、完成、道具使用和异常，不上报外部服务。
- [ ] 验收：手势指向正确、不会卡死或误扣次数、状态可恢复、原有未开启引导的流程正常。

## 目标 7：异形、落位与外围流程

**涉及**：经确认的棋盘模型、编辑器、生成器、UI 状态与测试；新增机制配置需要独立版本及默认关闭。

- [ ] 逐项评审异形、空格、上下左右落位及其他机制的意义、实现成本和与原版规则冲突；先完成一种简单样例，不同时引入所有机关。
- [ ] 对选定机制实现配置、编辑、运行、无解检测与回归；校验落位后的坐标、点击、路径、洗牌、引导与计时。
- [ ] 胜败、复活、地图或奖励流程按已评审需求逐个实现，不加入内购。每个流程提供正常、失败、取消、重复触发及返回路径。
- [ ] 验收：至少一个实际可玩的机制关卡，完成前后棋盘与交互均正确，可正常过关、失败和重开；未选定的系统不提前合入。

## 目标 8：IAA 接口及完整回归

**涉及**：`game/host-adapter.js`、`game/ad-policy.js`、`game/event-hooks.js`、`迭代接口文档/`、现有广告和性能测试。

- [ ] 整理插屏及激励广告调用、加载/展示/关闭/失败、超时、取消及奖励幂等语义；没有宿主时保证玩法可恢复。
- [ ] 本地模拟无广告、成功、失败、关闭、不回调及重复回调，确保奖励只在确认成功时发一次，计时和输入能恢复。
- [ ] 将平台待提供参数与真实 SDK 验收单列；未接入时明确为模拟，不声称实际展示成功。
- [ ] 综合回归三个主题、新牌面、关卡加载、引导、死局、道具、暂停、胜败和重开；在 MuMu 记录实际触控和运行错误，AHA 宿主与真机按可用环境分别验证。
- [ ] 同口径对照原版预装启动、对局流畅度、包体和加载；发生退化则定位后再发布。更新开发入口、构建、配置、接口、回滚和已知问题文档。
