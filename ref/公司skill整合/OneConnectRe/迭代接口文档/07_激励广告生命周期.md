# 本地激励广告生命周期接口

## 当前独立候选接入（v190）

候选 `analysis/ui_iteration_candidate_v190/game/` 已有四种道具的补给界面。页面安装完成后，宿主可通过 `window.oneConnectToolRewardCandidate.setProvider(provider)` 注入广告适配器；未注入时显示不可用。适配器实现 `show(callbacks, attempt)`，将平台的展示、奖励、关闭和错误事件转换为 `shown()`、`earned(proof)`、`closed()`、`cancelled()` 或 `error()`。本地测试使用模拟 provider，不代表真实广告已接通。

独立本地模拟供应商位于 `examples/reward-local-provider.js`，不会自动加载或注入。仅在隔离的本地测试页面手动加载该文件，并在候选入口安装后调用：

```js
oneConnectToolRewardCandidate.setProvider(
  oneConnectLocalRewardProvider.create({mode: 'reward', delayMs: 250})
);
```

`mode` 可设为 `reward`、`closed`、`cancelled` 或 `error`；切回无供应商可调用 `setProvider(null)`。模拟的 `verified: true` 只是测试标记，不是广告平台验证；`reward` 会实际修改当前候选页的道具数量，应使用隔离存档，禁止用于生产或接入真实 SDK。`tests/reward-local-provider.test.cjs` 使用生命周期模块验证四种状态；`tests/reward-local-provider-tools.test.cjs` 使用四道具入口、生命周期及模拟供应商联合验证各自加 2 和取消不发奖。两者均为内存模块测试，不代表游戏或平台验收。

只有适配器确认平台奖励有效后才调用 `earned({verified:true, ...})`；这个布尔值本身不是平台凭证验证。关闭、取消、普通 Promise 成功或本地计时结束都不会发奖。若平台奖励回调可能晚于关闭，适配器必须按平台契约先完成顺序归一化；本组件在终态之后忽略迟到的 earned。`show()` 异步拒绝会被视为错误。

候选实际发放数量为每次 2 个：提示和洗牌写入本局变量并尝试保存棋盘快照，锤子和换肤更新各自本地库存。当前四种发奖均为同步路径，存储失败时可能仅保留内存结果；页面关闭、跨页面并发及异常中断后无法保证发奖恢复或幂等。画面中显示的本地请求编号不是平台交易编号。

提示和洗牌在原生关卡初始化时会被重设，当前回合快照在结算后清除；因此不能承诺广告奖励跨关保留。观看过程中对局结束或返回主界面会取消请求，终态后的回调会被忽略；真实 SDK 必须先具备可靠交易凭证、持久发奖和迟到回调对账，再替换候选发奖路径。

异步发奖实验在超时后返回 `grant_pending`；同一奖励管理器中仍有未完成提交时，新的领取编号也不能启动新请求，直到提交返回。此约束只存在当前页面内存，刷新后不持久。切换关卡或结束对局会取消尚未发奖的请求；真实平台适配必须处理已经展示广告但返回较晚的奖励，并通过可信交易标识与持久账本或服务端对账，不能直接以这套候选方案上线。

以下各节保留早期实验记录；其中 `game/reward-lifecycle.js` 是基础版本，候选构建会替换成 `tools/reward_lifecycle_candidate.js`，不要混同其能力或状态。

## 独立候选异步发奖准备

`tools/reward_lifecycle_candidate.js`（v138 独立候选中的 `reward-lifecycle.js`）接受同步布尔值或最终解析为布尔值的 Promise。只有得到严格的 `true` 才标记本会话已领取；等待提交期间，关闭、取消或展示超时结果会延后，重复奖励回调不会重复调用发奖。可配置 `grantTimeoutMs`；到时返回 `grant_pending` 并释放本次暂停，未结束的同一领取标识在本会话中保持等待，不能重新发奖。迟到成功会在本会话标记已领取；Promise 拒绝或返回非 `true` 不记为成功。此等待标记只存在内存中，刷新后必须由事务账本和平台可信标识对账，不能以超时推断交易失败。

v139 候选要求暂停门控的 `pause` 与 `resume` 成对提供，否则创建时拒绝配置，避免只暂停无法恢复。暂停方法自身仍须原子执行；若暂停后抛错，模块不能判断宿主是否已部分暂停。

当前四道具入口仍使用同步发奖，此变更只是后续事务接入的接口准备；未接入 IndexedDB、真实 SDK 或跨进程幂等。实际事务仍须绑定平台可信交易标识，并解决库存迁移、道具扣减与游戏状态的一致性。

## 两件奖励事务实验

`examples/inventory-idb-candidate.js` 是独立实验，接受数据库名称与候选旧库存键，在同一 IndexedDB 读写事务中迁移初始数量、按领取标识发放两件、去重和扣减。`tests/inventory-idb-candidate.test.cjs` 使用隔离空白页面验证同源两页面并发、失败回滚、容量、损坏旧值及重载；不操作游戏。

它尚未接入任何道具入口。旧 localStorage 到 IndexedDB 的迁移不是跨存储原子操作，旧页面继续写旧键会产生分歧；领取标识必须由真实平台可靠提供，不能以当前时间生成的本地标识代替。棋盘操作和扣减也不是同一事务，崩溃恢复及真实 WebView 支持均未验证。

`examples/reward-idb-bridge-candidate.js` 将候选异步生命周期接到实验账本：需要供应商适配层提供已验证的 `transactionId`；账本确认已领取的同一标识不会重复增加库存。空白页面测试覆盖一次成功、跨实例重复标识、缺失标识和未验证凭据。示例不验证平台凭据本身，也未接入游戏；`verified:true` 只是适配层的内部约定，不能单独作为可信证明。

实验账本还支持按操作号预扣、确认或退款，并可保存操作前上下文；相同操作号的上下文不一致会被拒绝，同一上下文不能同时重复预扣。待确认操作会预留退款容量；相同操作的重复预扣或退款不会再次改变库存。隔离测试覆盖双页面并发、重载后待确认记录及与原有棋盘证据分类实验的连接。账本不会猜测中断时游戏操作是否完成：证据分类器要求可信标记和已恢复快照，当前游戏尚不自动提供该标记，故此接口还不能直接接管游戏道具。

入口：`game/reward-lifecycle.js`，在 `game/game.html` 加载；当前没有连接真实广告、正式奖励入口或经济系统。测试示例见 `tests/reward-lifecycle-browser.cjs`，实际在游戏页面以本地模拟供应商和内存计数器完成一次请求与去重。

`oneConnectRewardLifecycle.create({loadTimeoutMs, gate, grant})` 创建实例：

- `gate.pause(attempt)` / `gate.resume(attempt)` 由调用方负责暂停归属；本模块只释放自己成功取得的暂停，不直接控制游戏或覆盖用户暂停。暂停操作应当原子完成。
- `grant(claim, proof, attempt)` 必须同步完成一次业务交付并返回 `true` 才标记本会话已领取。当前无持久化交易账本；真实接入必须将发奖与持久幂等一起设计，不能以这个内存标记代替经济落盘。
- `setProvider({show(callbacks, attempt)})` 只接收已经适配、可信的供应商；它必须先按实际 SDK 契约归一化结果。`shown()` 表示开始展示，`earned({verified:true})` 只表示供应商适配层已确认奖励，`closed()`、`cancelled()`、`error()` 分别结束请求。组件不会因为关闭或普通 Promise 返回而发奖。当前合同中终态后的迟到回调被忽略；若平台允许关闭后再发送奖励，适配层需要先等待并归一化，不得直接照搬。
- `request(claim)` 返回状态：`rewarded`、`closed`、`cancelled`、`error`、`timeout`、`show_timeout`、`unavailable`、`busy`、`already_claimed` 或 `invalid_claim`。请求身份在调用供应商前分配；并发请求返回 `busy`。`cancel()` 可解除等待；展示前超时适用 `loadTimeoutMs`，已展示后不以加载超时截断。可选 `maxShowingMs` 启用独立展示阶段看门狗，尚未成功发奖时超时返回 `show_timeout`；若先前已成功发奖则返回 `rewarded`，并释放本组件的暂停。默认不启用。该计时使用墙钟，包括后台时间，也不能关闭或证明关闭真实广告；只有在平台明确支持超时、关闭和前后台处理后才应配置，不能把本地模拟当真实广告验收。

本地测试覆盖同步回调、重复回调、失败、关闭、无供应商、加载超时、展示后回调、展示后失联、并发、取消、迟到结果及不可信凭据。测试门控和计数器均是模拟，**不证明真实广告、真实暂停、AHA SDK、持久发奖或经济链已接通**。实际商业化接入前须由平台明确广告位、结果顺序、超时、证据及暂停/奖励所有权，并补真实业务入口、可恢复持久发奖和设备验收。

供应商 `show()` 若返回 Promise，异步拒绝会结束当前请求并返回 `error`，释放本请求持有的暂停；Promise 正常完成不代表广告完成，也不触发奖励。若奖励此前已获确认，则保持 `rewarded`；终态后的迟到回调不发奖。适配层仍须根据实际 SDK 契约归一化，避免将与本次展示无关的后台任务失败作为展示失败。浏览器运行页和 MuMu 隔离副本已验证模拟异步拒绝，未验证真实 SDK。

## 本地锤子奖励示例

`examples/reward-hammer-local.js` 是独立测试示例，不加载进正式游戏。开发者可在正在对局的本地页面加载该脚本，创建 `oneConnectLocalHammerExample.create({loadTimeoutMs: 2000})`，通过返回实例的 `setProvider` 注入模拟供应商并用 `request('本次唯一标识')` 发起。模拟供应商调用 `shown()`、`earned({verified:true})`、`closed()` 后，示例给现有锤子库存加一；`tests/reward-hammer-local-browser.cjs` 验证了发奖后实际使用锤子、同实例重复请求和取消后的迟到回调。此示例不处理真实广告、正式入口或持久化奖励事务；会话结束、多个实例和页面重载之间不保证去重。

暂停尚需真实宿主联调：实际检查发现 `cr_setSuspended(true)` 会触发原游戏自己的暂停状态，随后恢复引擎并不等于恢复对局。本示例不操作暂停，也不模拟真实广告播放；接入真实 SDK 前需确认前后台、手动暂停和广告暂停的所有权并在设备上验证。

暂停来源已进一步定位：Construct 的挂起回调触发 `Browser.OnPageHidden`，原游戏随后进入自己的暂停菜单；恢复引擎后菜单仍保留，需要玩家点击继续。浏览器测试 `tests/suspend-pause-recovery-browser.cjs` 验证暂停期间计时不变、继续后计时恢复，且已有手动暂停在挂起和恢复后仍保留；MuMu 隔离副本测试 `tests/android_preview/suspend-pause-recovery.cjs` 验证触控继续及计时恢复。这是受控引擎挂起测试，不能证明真实广告返回时的宿主行为，也不提供广告结束后自动继续。

## 持久领取实验（未接入正式游戏）

`examples/hammer-ledger-candidate/` 为隔离候选，运行 `tests/setup-hammer-ledger-candidate.py` 后生成测试副本。候选在单条本地记录中保存锤子数量和领取标识，初次从现有库存读取；相同标识在重载及新实例后拒绝再次发放。浏览器验证写入失败时不消除牌，MuMu 验证模拟发奖、实际使用及重载后去重（`tests/evidence/mumu_hammer_ledger_candidate.json`）。

这不是正式发奖方案：多页面并发写入没有互斥保证；旧版只读取 v1 库存，直接回滚可能读取过时数量；清除本地数据会丢失领取记录。固定最多 5000 个标识的容量、异常恢复、失败补偿、真实 SDK 奖励证明和服务器幂等等均需明确方案并验证。候选代码和示例都没有加载到正式游戏，不应以此宣称真实广告或跨设备持久发奖完成。

`examples/hammer-ledger-idb/hammer-stock-idb.js` 是进一步的异步存储实验：使用同一个 IndexedDB 读写事务修改库存与领取标识，优先迁移 v2 实验数据，否则读取 v1 库存。浏览器中两个页面并发相同领取、不同领取和扣次后重载，结果一致；写入失败不会留下半笔记录，损坏的旧实验记录会拒绝迁移。MuMu 验证单页面并发请求及重载，设备数据见 `tests/evidence/mumu_hammer_stock_idb_experiment.json`。这个异步接口还没有连接正式锤子按钮或奖励生命周期，不能保证库存扣减与引擎消除跨崩溃原子完成；旧版回滚、多设备、平台证明及服务器幂等仍未解决。该实验会创建独立的本地数据库，不应在正式存档上直接试运行。

该实验支持按唯一操作号 `reserve(id)` 暂扣、`resolve(id, true)` 确认和 `resolve(id, false)` 退款；重复操作不会再次扣除或退款。待确认操作占用库存上限额度，避免后续发奖使退款溢出。浏览器双页面和 MuMu 单页面验证了重载后退款和确认（`tests/evidence/mumu_hammer_stock_journal.json`）。调用方仍须建立可靠的游戏棋盘证据，才能决定中断后的待确认操作应确认还是退款；记录本身不能推断牌是否已消除。操作记录最多 5000 条，尚无清理规则，也未接入正式对局。

进一步的棋盘证据实验位于 `examples/hammer-ledger-idb/round-evidence.js`，使用 `tests/setup-hammer-round-candidate.py` 建立独立副本。操作可绑定有限长度的操作前稳定快照；规则仅对已验证且已实际恢复的相同棋盘建议退款，对带可信操作标记、并且恰好少一对同类牌的有效稳定快照建议确认，其余情况返回未知。浏览器与 MuMu 以第 7 关实际锤子消除及页面重载验证了样本（`tests/evidence/mumu_hammer_round_evidence.json`）。目前标记由测试代码在消除后手动添加，库存操作和游戏锤子各自独立；没有自动接管正式锤子，没有验证异常强杀、过关清除快照、并发游戏页面及标记来源可信性。不能将实验规则直接用于正式扣费或宣称实现崩溃原子性。
