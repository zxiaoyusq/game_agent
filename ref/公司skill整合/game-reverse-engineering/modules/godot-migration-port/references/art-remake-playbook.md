# 美术重制 Playbook：烘焙页 + 动态组件同位（Unity→Godot）

> **何时读我**：哥哥要重绘/重制美术页、要落实单层纪律（值同零绘制 / 值异原始贴图覆盖）、要用色值反查纹理、要擦除烘焙页、要实测 9-slice margin，或要查 tween bind 参数顺序时。
> **读完能做到**：给每个 UI 元素定出「零绘制」或「原始贴图覆盖」的唯一路径，把实测纹理与几何写进代码注释，并用双证据（拼图对比 + diff%/blob）与分层指标完成一次美术重制交付。
> **范围**：`GENERAL_DEFAULT` + `GENERALIZED_PATTERN` + `CASE_ONLY_MAGICSORT`；整页截图作底图的路线仅用户明确接受时才可走，用户要求原切图、可编辑控件或完整交互时改走原生还原门禁。

> 7.4.0 适用边界：本文仅适用于用户接受整页截图作为实现底图的特定原型/复刻路线。用户要求原切图、可编辑控件、完整交互或预制体时，必须走 [原生还原门禁](native-restoration-gates.md)，不能套用本文“值相同零绘制”来保留截图中的静态数字。固定场景序列化与整页截图烘焙是不同操作。

> 范围：`GENERAL_DEFAULT`（原则/决策表/检查清单）+ `GENERALIZED_PATTERN`（方法）；
> 章节「该案例专属」为 `CASE_ONLY_MAGICSORT` 字面值，其他项目禁止照搬（见 `references/scope-map.md`）。

适用场景：S3 UI/表现迁移时做「美术重制」——用原版整页截图（烘焙页）+ 原版切片纹理（media 切片）
重建运行时界面，目标是**像素级还原且每个 UI 元素只出现一次**。

## 1. 核心原则：单层纪律（本项目两次拒收的根因）

同一视觉元素出现 2 份 = 双层：烘焙页一份 + runtime 一份、或 runtime 自叠两份。
用户可感知的表现：pill 叠 pill、图标后面露出另一枚图标、数字旁边多一个白板、贴图边缘露 1-4px 裂缝。

**在已选定截图底图路线内的两种覆盖路径（不适用于原生切图路线）**：

| 情形 | 路径 | 做法 |
|---|---|---|
| 动态值 == 烘焙页的值 | A：零绘制 | runtime 对该元素**什么都不画**，烘焙页原样显示 → 像素级一致，diff→0 |
| 动态值 != 烘焙页的值 | B：同纹理覆盖 | 用**原始贴图**（9-slice 或原尺寸 icon）画在烘焙副本正上方，几何 ≥ 烘焙 bbox（留 1-3px 余量），动态文本/图标画在盖层上 |

铁律：

- ❌ 平铺色块做「背板」（flat stylebox/pill_bg）盖在烘焙贴图 pill 上：色差/圆角/描边不一致，用户看到的就是双层（哪怕 diff 百分比很小）。
- ❌ 在烘焙已有元素的位置再画一个更小/偏移的副本：金币双币、生命「5」白板、heart 偏移露边。
- ✅ 在该截图路线且状态完全一致时可零绘制：0 diff、0 新增缺陷、0 纹理拉伸风险。

## 2. 逆向阶段：找对纹理与几何

1. **色值反查纹理**：从烘焙页采 body/border 颜色 → 在 media 里逐纹理采样中心/边缘像素匹配。
   - 例：烘焙页 body `(8,20,82)` / border `(115,65,247)` ↔ `LevelPanel_normal.png` center `(11,19,86)` / edge `(110,63,245)`（同一贴图，9-slice 缩放引起 ±3 级差）。
   - 同一贴图可被多处复用（`bg_currency_home.png` 既是金币 pill 又是生命 pill）。
2. **文件名陷阱**：代码注释/记忆里的名字常错（`Heart.png` ≠ `heart-Home.png`）；引用前先 `glob/ls` 确认。
3. **几何实测**：颜色掩码 bbox 必须**限定窗口 + 多行/列 profile 交叉验证**，掩码污染源清单：
   - gold 掩码 → 抓 pill 金边/金币高光，bbox 蔓延到整个 pill；
   - cream 掩码 → 抓相邻头像光芒/高光；
   - red 掩码 → 抓 heart 辉光/红点；
   - 反例：本案例金币 bbox 三次修正（205→240→243 起）都因掩码污染。
4. **实测结果写进代码注释**（如 `coin pill body 270-425 x 86-152, gold coin 243-306 x 88-152`），
   回归时可直接核对，避免反复肉眼猜测。

## 3. 烘焙页编辑（仅在必要时）

- **优先「盖」而不是「擦」**：擦除复杂背景（砖墙/渐变）上的元件，inpaint 会拖出污痕。
- 必须擦时：**erase 区域绝不穿过亮色 UI**。逐列垂直插值会把穿越的亮内容垂直涂成条纹
  （案例：`ingame_L7` erase 区 y300 切到「Level 7」文字 → 白色竖纹；改 y345 后图面干净）。
- 亮元素上下都要留安全区；宁大勿小。
- 备份纪律：编辑前 `tools/baked_backup/` 留原图（备份目录最终要移出仓库，避免膨胀）；
  脚本幂等（backup 存在即跳过；同一区域重跑结果一致）；改错区域先 git/备份恢复再重跑，不要继续叠补丁。

## 4. 动态组件同位（运行时绘制）

- **9-slice margin 从纹理实测**：边框像素宽 == margin。`bttn_purple_back` 用 28 在小 pill 上风格不符；
  `LevelPanel_normal` 边框约 6-10px → margin 14。
- **盖层尺寸必须 ≈ 烘焙 bbox**：过大/过小都会让纹理内部渐变错位，边缘出现 1-4px 可见「双层边」。
- **icon 直拉伸的副作用**：`TextureRect` STRETCH_SCALE 会连半透明辉光一起拉伸 → 辉光盖到相邻元素
  （案例：`heart-Home.png` 红雾罩住 pill）。保持纹理长宽比、按烘焙**含辉光 bbox** 对位；
  或值相同时（路径 A）完全不画。
- **动态文本**：字体与原版必然不同（默认字体 vs 原版粗体），属「合理差异」；
  对齐烘焙文本 bbox 的位置与字号即可，**不要**在文本外加平铺背板。
- **z_index 只同父生效**；透明命中区（hit zone）与视觉层分离，避免点不到/点错。

### 4.1 快照页转功能页：四联契约

整页截图只能继续承担背景和标题等静态美术，不能作为商品、排行、收藏、活动或小游戏的状态源。
把快照命中区替换为真实 UI 时，每个操作必须同时验证：

1. **可见状态**：按钮、数量、进度和已领取状态立即更新；
2. **持久化状态**：退出并重进后由 Save/Service 恢复，而不是由控件记忆；
3. **事务唯一性**：一次性奖励保持幂等，可重复购买/多次抽取则必须使用递增序号，不能共用固定 SKU 事务号；
4. **流程隔离**：支线/日挑/街机不得误推进主线关卡号、胜场或主线结算奖励。

功能化会暴露快照阶段看不到的后端缺陷（例如按钮能点但没有真实发奖）。因此验收不能只做截图：
至少补一条服务级状态迁移测试、一条 UI 入口/控件树测试，并在设备上完成一次操作后重进复核。

Godot `ScrollContainer + VBoxContainer` 中，`Label.autowrap_mode` 若在父级宽度尚未确定时参与
minimum-size 计算，可能把卡片高度撑到数百像素。单行卡片优先用 ellipsis；确需多行时先给文本列
确定宽度，并用独立可伸缩 spacer 吸收视口余高。

## 5. Godot 4.6 GDScript 坑（本案例踩实）

- **`tween_method(callable.bind(a, b), ...)` 绑定参数是「追加」**：回调签名必须是 `(t, a, b)`
  顺序，否则参数错位 → 表现为「没有动画/方向反」（案例：倒水动画缺失的根因之一）。
- `PanelContainer` 高度小于 margin 上下之和时 9-slice 被压缩：小控件用小 margin。
- 改 **PNG 才需要** `Godot --headless --import`；GDScript 解释执行，改脚本不需要。
- CLI 捕获后 exit 139 崩溃回溯（PE/COFF no debug info）**大多无害**：
  以 stdout 打出标记（如 `[S4-HOME-CAPTURE] path`）+ 文件存在为成功判据，不要被回溯吓到。
- 捕获配方固定为 argv 注入（`--shellcapture/--capture/--midcapture/--wincapture/--level/--board/--auto/--midat`），
  同一场景可重复回归。
- 会影响资源裁切/布局的模式标志必须在 `setup/build` 之前赋值；setup 后再切换只改变后续绘制，
  已缓存的纹理区域、坐标和尺寸不会自动重算。规范调色板/映射文件应成为所有消费者的单一来源，
  并用全 ColorId/ItemType 遍历测试防止“文档已正确、代码仍用旧占位值”。

## 6. 验证：双证据 + 指标分层

- 每个「修好」= ①同窗口上下拼图肉眼对比 ②像素 diff % + blob（行/列直方图）定位。
  只信数字（百分比反而变差）或只信眼睛都会误判。
- 指标分层：**静态美术 diff（目标≈0）**与**动态文本 diff（字体差异，进白名单/容差）**分开统计。
- Godot 本地捕获 + 真机模拟器（adb）截图双轨，真机是最终验收。
- 用户反馈「双层/画面混乱」→ 先枚举全部 runtime 绘制元素，逐个对照烘焙页确认**唯一性**，再谈其他。

## 9. Godot 中的结构先行换皮（2026-09-14 验证版）

> **适用范围**：`GENERAL_DEFAULT`。本章替代 2026-09-13 的固定 Bbox/质心/inpaint 配方。那套方法没有先证明实际资源 owner，也无法发现静态图冒充 Spine、附件语义画错和 QA 截图本身被拉伸。

### 9.1 建立三张权威表

1. **风格目标卡**：批准参考图、色板及用色比例、材质、边框/阴影、字体气质、插画抽象度、允许和禁止元素。参考工程只提供风格，不接管目标工程的布局与交互。
2. **运行资源链**：`页面/状态 -> .tscn -> 节点 -> 资源 -> atlas page/region -> 动画`。静态 fallback、Spine、粒子和普通 Sprite 分开记录。
3. **资产契约表**：原尺寸、模式、Alpha 哈希、atlas rect/rotate/trim/offset/pivot/border、NinePatch、宿主 transform、设计分辨率和 stretch/aspect。

先冻结这三张表，再生图。否则模型很容易画出好看的整页截图，却让章节、排行、每日、结算或动画附件失去原功能。

### 9.2 Sprite 与 UI Atlas

- 优先编辑权威原切片，在其语义轮廓内改颜色、材质和装饰。新造型必须适配原 mask；Alpha 相同仍可能把主体腰斩或把细节放到透明区，必须看运行画面。
- 生成图裁出主体后只允许等比 `contain` 或 `cover`。Godot 侧也使用保持宽高比的 TextureRect/节点缩放；禁止 X/Y 独立缩放生成图或运行节点。
- `contain` 产生的留白需显式选择透明、边缘延拓或已批准底色；`cover` 的裁切区域需人工验收。不要把固定像素的 inpaint/dilation 当作所有素材的通用答案。
- Atlas 回贴保持 page 尺寸和全部 region 元数据；旋转/trimmed 子图按真实元数据处理。重建后验证页内边界、切片像素、未改 region 和过滤边缘。

### 9.3 Spine 必须直接重绘真实 Atlas

1. 从已验证原 atlas 页开始，确认 page、region、rotate、slot/attachment 和动画名。
2. 对原附件做受控调色或逐 region 重绘；脸、眼、嘴、手、文字、彩带等仍是独立组件，不能把动画截图或整个人物截图塞回单一区域。
3. 保持 `.atlas`、`.skel/.json`、page 尺寸、region 坐标/旋转、Alpha、skin/slot/attachment 名、动画名和宿主 transform 不变。
4. 若工程维护 source/runtime 两套 Spine 资源，输出页必须同步且哈希一致。
5. 在 Godot 实际 Spine runtime 中播放，捕获起始、展开、峰值、结束/回收帧；atlas 展开图和静态 fallback 不能证明动画正确。

### 9.4 截图与屏幕适配门禁

命令行 `SceneTree` 捕获脚本必须显式设置 `root.size` 为项目设计分辨率。例如竖屏项目先按 1080×1920 渲染，再等比缩成 540×960。禁止使用桌面默认横屏 Viewport 渲染后强制 `Image.resize(540,960)`；这种脚本会制造纵向挤压、节点出画和“全局适配被改坏”的假象。

排查形变按以下顺序分层：

1. `project.godot` 的 viewport/stretch/aspect 与基线 diff；
2. 当前场景的 anchors、offset、Control size 和 TextureRect stretch mode；
3. 资源适配脚本是否按两个轴独立 resize；
4. 截图脚本的真实 Viewport 与输出宽高比；
5. 最终 Android/设备安全区和系统缩放。

只有第一层发生变化时才能归因于全局屏幕适配。局部锚点差异和证据脚本错误必须单独报告。

### 9.5 五层验收与失败回写

- **结构层**：非视觉代码零差异或严格白名单；场景节点、信号、交互和动画宿主仍在。
- **位图层**：所有改动 PNG 的尺寸、模式和 Alpha 与基线一致；生成图保持比例，无旧皮肤 halo。
- **图集层**：region 元数据、旋转和边界合法；Spine source/runtime 页哈希一致。
- **运行层**：各页面状态、真实 Spine/粒子中间帧、返回和交互回归；不能只看首页静态图。
- **设备层**：最终构建在目标设备复验方向、安全区、缩放、层级、输入和日志。

任何失败都记录为 `资产/状态 -> 现象 -> owner -> 根因层 -> 修复 -> 回归证据`，并更新 manifest 与交接文件。已验证的典型反例包括：庆祝 Emoji 的脸部 region 被重画成无关装饰物；静态 fallback 被误报为 Spine 已换皮；生成图强制拉伸；横屏截图强拉竖屏。它们都是流程门禁问题，不能靠继续批量生图解决。
