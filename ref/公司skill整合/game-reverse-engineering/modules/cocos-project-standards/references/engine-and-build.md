# 引擎与构建规范（版本 · 装配 · 出包）

> **何时读我**：要开新工程、拉取/升级框架层、配置编辑器扩展、排查"别人能跑我不能跑"时。
> **读完能做到**：正确装配工程（含子模块）、知道哪些目录/文件不该进版本库、构建纪律清楚。
> **范围**：`[COCOS]` + `[CFW]`（框架装配部分）。

## 1. 引擎版本锁定

**规范 `[COCOS]`**：引擎版本写在工程清单里（Creator 生成的 `package.json`），**以该字段为唯一真源**，不要在文档里另记一份。

```json
{
  "name": "<工程标识>",
  "uuid": "<工程 uuid>",
  "creator": { "version": "3.8.7" }
}
```

**纪律**：

- **升级引擎是独立决策，不与业务改动混提**。3.x 内部小版本也可能改变 prefab 序列化字段与资源导入行为 → 混提会让"业务回归"与"版本回归"无法区分。
- 升级前先确认**框架层支持的引擎区间**（见第 2 节），框架与引擎版本是**成对约束**。
- 升级后至少复验：prefab 能否打开、资源导入参数是否被重置（尤其 `trimType`，见 `resource-contract.md` 第 4 节）。

## 2. 框架层装配（子模块）

**原则 `[COCOS]`**：自研框架层作为**独立仓库**挂在工程里（`extensions/<framework>/`），**不使用复制粘贴**。

来源项目做法 `[CFW]`：

- 框架位置 `extensions/framework_cfw_cocos`，由 `.gitmodules` 声明为 **git submodule**。
- 工程内通过**导入别名**访问：`db://driftsand-framework`（对应框架内的 barrel 导出 `index.ts`）。
- 业务代码**只经该别名**导入，不深入框架内部路径（见 `framework-boundary.md` 第 1 节）。

**装配步骤（新机器 / 新同事）**：

```bash
git clone --recursive <工程仓库>        # 或克隆后 git submodule update --init --recursive
```

**升级框架层**：

1. 在框架仓库侧拉取目标版本；
2. 更新工程里的 submodule 指针；
3. **按框架 `CHANGELOG` 逐条核对破坏性变更**；
4. 跑一遍 TS 检查与构建。

**红线**：**不要在工程里直接改框架层源码**（那是另一个仓库）。确需改就走框架仓库的提交流程，否则下次同步即冲突或丢失。

## 3. 编辑器扩展

工程可挂编辑器扩展做自动化（`extensions/` 下）。来源项目装配了 MCP 通道类扩展（`[DADA]` 具体扩展名）：

- 用途：让 AI/脚本操作编辑器做中间自检（触发资源重新导入、构建、状态查询）——走 `cocos-mcp-channel` 模块。
- **端口与地址属项目/环境值**，不要写进通用规范；使用前**实测探测**当前工程的端点，不要照抄别处的端口。
  > 实测教训：同一台机器上不同工程/不同扩展版本的端点可能不同，照抄旧文档的端口会连不上。

## 4. 不该进版本库的内容

| 内容 | 原因 |
|---|---|
| `library/`、`temp/`、`local/` | 编辑器本地产物，可由资源重新导入生成，且体积大 |
| 编辑器**个人状态**文件（如 `settings/**/information.json` 之类记录面板布局/最近打开的） | 每人不同，提交即冲突 |
| 子模块 gitlink 之外的框架内容 | 由 submodule 管理，不应重复提交 |
| Office/Excel 锁文件（`~$*`） | 编辑器崩溃残留，进 `.gitignore` |
| `.bak`（压缩/后处理残留） | 会被当资源打进包，白涨体积（见 `resource-contract.md` 第 6 节） |
| 构建产物目录 / 签名文件 | 体积 + 密钥风险 |

**建议**：`.gitignore` 里显式列出以上项；`.gitignore` 本身要评审，它决定"事故能不能回滚"。

## 5. 构建纪律

- **构建前清场**：清掉残留构建进程 + 删产物目录。**禁止并发构建**——并发会互写同一 build 目录，产物混合多源状态，事后无法判断包里到底是哪版。
- **Windows 下的 stdout/stderr 陷阱**：构建命令若通过管道捕获输出，可能因管道缓冲区写满而**假死**（EPIPE 类现象）。做法：让输出重定向到文件，或**分离 stdout/stderr**。
- **成功判据不是"没报错"**：以构建日志中的**完成标记** + 资源库恢复可用 + 真实产物可加载为成功证据；只看退出码容易把"中途失败但退出 0"当成功。
- **面对"预览黑屏"**：先查配置/数据一致性（见 `config-pipeline.md` 第 8 节），再查工程引用修复（`cocos-creator-repair`）。**不要**直接怀疑引擎。

## 6. 构建与验收的分工

**本模块只到"怎么构建"；"构建出来能不能装、能不能跑"由验收模块判定。**

- 构建出包 → `cocos-qa`
- 模拟器/真机截图与视觉回归 → `vision-device-testing`
- **包哈希与签名必须记录**：这是"这个包到底是哪一版"的唯一凭据（走 `cocos-qa` 的证据要求）。

## 7. 未取证项

- 来源项目的**具体构建命令与参数**（平台、压缩方式、ABI 拆分）未逐项取证。
- **热更 / 远程配置 / ABTest** 相关能力在框架层存在（`[CFW]` 的 hotfix 系列），但其**业务侧使用规范未取证** → 若目标工程要用热更，需单独取证后再补本章。
- 编辑器扩展的**完整清单与版本**为项目值，未复制。
