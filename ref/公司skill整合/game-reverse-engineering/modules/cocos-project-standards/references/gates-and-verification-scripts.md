# 专项校验脚本与交付门禁

> **何时读我**：要为一个系统/界面建立"改完自动能验"的静态门禁，或要判断"专项校验通过"到底证明了什么时。
> **读完能做到**：写出一个可重跑、失败可定位的 `verify_*` 脚本，并知道它与总集门禁脚本、与运行/真机验收的分工边界。
> **范围**：`[COCOS]` 方法论（脚本形态与断言类型）+ `[DADA]` 来源工程实测值。

**为什么需要它**：手工验收**无法在每次改动后重跑**。而工程里最容易不同步的接缝恰好是三类——**配置表的数据形状**、**代码的关键接线**、**prefab 的节点结构**。这三者在改动时经常只有一处被改，靠人记不住。把它们写成脚本，就把"我以为改对了"变成 `[FAIL] <可定位描述>`。

## 1. 脚本形态（统一约定）`[COCOS]`

| 项 | 约定 | 理由 |
|---|---|---|
| **位置** | 按工具域分目录：业务专项与预制体专项分开 | 便于按改动类型只跑相关的一批 |
| **命名** | `verify_<系统或界面>.py`；辅助工具用 `check_*` / `dump_*` / `diff_*` | `verify_*` = **断言**；`dump/diff` = **产出/比对**，职责不同 |
| **定位工程根** | `ROOT = Path(__file__).resolve().parents[N]` | **禁止硬编码绝对路径**，否则换机器/换目录即失效 |
| **失败约定** | `def fail(msg)` → 打印 `[FAIL] <描述>` → `SystemExit(1)` | 退出码非 0 才能被批处理/CI 捕获；`[FAIL]` 前缀便于日志检索 |
| **断言辅助** | `require(content, tokens, source)` 逐 token 检查，缺失时报出**来源文件** | 失败信息要能直接定位到"哪个文件的哪个 token 没了" |
| **读生成物** | 用 **BOM 容忍**编码：`encoding="utf-8-sig"` | 生成的 JSON 可能带 BOM；按 `utf-8` 读会直接抛错 |

`[DADA]` 形态示例（断言直接读工程产物，不依赖运行时）：

```python
ROOT = pathlib.Path(__file__).resolve().parents[2]

def fail(message: str) -> None:
    print(f"[FAIL] {message}")
    raise SystemExit(1)

def require(content: str, tokens: tuple[str, ...], source: str) -> None:
    for token in tokens:
        if token not in content:
            fail(f"{source} 缺少: {token}")

# 读配置产物（BOM 容忍）
data = json.loads((ROOT / "assets/bundle/config/data.json").read_text(encoding="utf-8-sig"))
# 读 prefab 并取节点名集合
def names(objects):
    return {o.get("_name") for o in objects if o.get("__type__") == "cc.Node"}
```

## 2. 断言什么：三类接缝 `[COCOS]`

| 类别 | 断言对象 | `[DADA]` 实测例 |
|---|---|---|
| **配置形状** | 表的行数、枚举取值序列、必填字段非空、数值关系、文案与数值一致 | "某表必须且仅包含 4 项"；"目标系统必须依次配置为 无/喂食/大厅互动/激励视频"；"说明文案必须体现每轮需完成次数"；"标题/说明/图标/次数/可领取次数不得为空" |
| **代码接线** | 关键方法名、事件名、状态转移顺序、UI 接线 token 是否存在于源码 | 状态延迟抢占顺序、某状态的特例处理、两处 UI 的接线 token 齐备 |
| **prefab 结构** | 节点名集合是否齐备、是否用了语义名、绑定组件是否存在 | 弹窗节点与绑定名核对（配合 `dump_prefab` / `diff_prefab_fields` 做比对） |

**写法要点**：断言要写成**期望的完整形状**（"必须且仅包含"、"依次为"），而不是"包含某些值"。只写"包含"会漏掉多余项与顺序错误。

## 3. 纳入交付流程 `[COCOS]`

```
改动 → 跑本系统的 verify_* → 全绿 → 才更新推进记录 → 才交付
```

- **每个系统配一个**自己的 `verify_*`；跨系统的通用硬缺陷由总集门禁脚本兜底。
- **失败即阻断**：`[FAIL]` 未消不能进下一步（与总集执行协议的"做完标准"一致）。
- **推进记录只在通过后更新**——记录写"通过"而脚本红着，就是伪造状态。

## 4. 与总集门禁脚本的分工

| 脚本 | 覆盖面 | 归属 |
|---|---|---|
| `modules/cocos-project-standards/scripts/check_program_standards.ps1` | **跨系统通用硬缺陷**：图标 meta、禁用产物、事件 on/off、节点命名反模式、产物可解析 | 本总集（可跨项目） |
| 项目内 `verify_*` | **本系统的契约**：该系统的配置形状、接线、prefab 结构 | 各项目自己维护 |

**不要把它们合并**：前者是"任何 Cocos 工程都该过"的底线，后者是"这个系统特有的约定"。混在一起会让通用门禁充斥项目细节，无法复用。

## 5. 边界：静态校验**不能**替代运行/真机验收 `[COCOS]`

这是最容易误读的一点：

- 静态校验产出的是**静态证据**；能否真的跑起来、画面是否正确，必须由**构建 + 运行/真机**判定（走 `cocos-qa` + `vision-device-testing`）。
- `[DADA]` 来源项目在推进记录里**始终把"专项静态校验通过"与"Creator 验收通过"分开写**：多处标注"代码+配置完成，Creator 验收待做"。这是正确做法。
- **禁止**用"`verify_*` 全绿"表述成"功能已验证"。

## 6. 来源工程现状（如实记录，含不均匀处）

`[DADA]` 实测（非理想态，供对照）：

| 项 | 现状 |
|---|---|
| 脚本数量 | 业务专项 12 个（含 1 个 `.cjs`、1 个 `complete_*` 补数据脚本）+ 预制体专项 6 个 `verify_*`/`check_*` |
| **约定覆盖率** | **不均匀**：11 个业务 `verify_*.py` 中仅 **5 个**采用统一 `fail()` 约定；读生成物的编码 4 个用 `utf-8-sig`、其余用 `utf-8` 或不指定 |
| 定位根 | **全部**用 `parents[2]` ✓（这一条是齐的） |
| 统一运行器 | **未取证到**（文档中只有逐条提及，未见"一键跑全部"的脚本） |
| CI 集成 | **未取证**（看起来是手工跑） |

**结论**：**约定方向已被实践验证有效**，但**落地不彻底**。新项目直接按第 1 节约定起步，比补旧账便宜。
