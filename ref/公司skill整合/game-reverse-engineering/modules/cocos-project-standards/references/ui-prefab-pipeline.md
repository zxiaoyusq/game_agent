# UI 预制体生成链路（生成器 + 绑定声明）

> **何时读我**：要用生成器产出预制体、要给界面挂 `@property` 绑定、发现"编辑器里改了但一生成就被覆盖"时。
> **读完能做到**：正确维护生成器与绑定表，知道哪些文件绝对不能手改、怎么验证生成是确定性的。
> **范围**：`[COCOS]` 方法论 + `[DADA]` 具体脚本与字段名（不可复制）。

## 1. 核心红线：派生文件禁手改

**`.prefab` 与 `.meta` 由生成器产出时，它们就是派生文件。**

- **禁止手改**生成器输出的 `.prefab` / `.meta`。
- 要改结构 → **改生成器或它的输入（设计稿布局数据 / 绑定表）后重跑**。
- **精修稿例外要显式管理**：美术在编辑器里精修过的 prefab，必须由**专属补丁脚本**维护，并禁止通用生成器覆盖它。
  > 判据：如果某个 prefab 既被通用生成器写、又被人手精修，那它**必然**在某次重跑后丢掉精修——发现这种双重所有权时，先解决归属，再继续开发。

## 2. 为什么用生成器而不是手搭

| 收益 | 说明 |
|---|---|
| **可复现** | 结构来自数据，不依赖某个人记得怎么拖节点 |
| **可批量** | 几十个界面同构部分一次产出 |
| **可校验** | 生成结果与绑定声明可机械比对（见第 6 节） |
| **可回滚** | 出问题回到生成器输入的上一版即可 |

**代价**：生成器本身要维护，且必须有确定性（第 4 节）。**只有当界面数量与同构度足够时，生成器才划算**——界面很少、结构差异很大的项目，手搭更快，别硬上生成器。

## 3. 生成器输入与输出

典型形态 `[COCOS]` 模式：

```text
输入：设计稿布局数据（每个界面的节点树 + 节点 id + 尺寸位置）
      + 绑定声明表（prefab → 脚本 + 属性映射）
输出：assets/bundle/<域>/ui_prefabs/*.prefab  +  对应 .meta
```

- **设计稿节点 id 只用于生成映射**（生成器靠它把"设计稿的某个框"接到"运行时的某个节点"）。
- **最终 prefab 里的业务节点必须换成语义名**（见 `code-and-naming.md` 第 2 节）。设计稿 id 留在生成输入里，不进运行时。

## 4. 确定性要求（必须可验证）

**生成必须确定性**：同样的输入重复运行，产物**逐字节一致**。

- 实现手段（实测做法）：**资源 uuid 基于文件名做 uuid5 派生**，而非随机生成。随机 uuid 会让每次生成产生全量 diff。
- **验证方法**：**双跑比对哈希**——连续生成两次，比对产物哈希；不一致即视为生成器缺陷，必须修掉。
- 这一步不能省：不确定的生成器 = 无法用 git 判断"这次改动到底改了什么"，生成器的全部收益都会失去。

## 5. 绑定声明表

把"prefab 上的哪个节点绑到脚本的哪个 `@property`"写成**声明式数据**，而不是靠人在编辑器里连：

```jsonc
{
  "<PrefabName>": {
    "script": "<脚本 uuid>",
    "props": {
      "btnConfirm":  "ConfirmBtn",     // key = @property 名, value = 布局节点 id
      "txtTitle":    "TitleLabel",
      "pgbExp":      "ExpBar"
    },
    "multiLang": { "<property名>": "<多语言key>" }
  }
}
```

约定（`[DADA]` 字段名，方法是 `[COCOS]`）：

| 约定 | 说明 |
|---|---|
| `props` 的 **key = `@property` 名** | 与 `code-and-naming.md` 的"节点名 = 属性名"配合，可机械核对 |
| `props` 的 **value = 布局节点 id** | 指向生成输入，不是最终节点名 |
| `btn*` **自动挂 `Button`** | 前缀即类型（同 `@property` 前缀表） |
| `pgb*` **自动挂 `ProgressBar`** | 同上 |
| 控件多的弹窗用 `groups` / `panel_groups` **归纳** | 避免扁平上百节点 |
| 组合按钮用 `group_buttons` **挂总容器** | 组合按钮的点击要落在总容器上 |
| 需多语言的文本属性在 `multiLang` 声明 | 生成时自动挂多语言组件 |
| 以 `_base` 结尾的节点视为按钮容器 | 同前缀的 `_icon` / `_label` / `_value` / `_coin` 等**自动挂为其子**，省去逐个声明 |
| `dst` 可覆盖输出子域 | 缺省输出到主域，跨域复用资源时显式声明 |

### 已有完整覆盖模块时用 `visual_groups` `[COCOS]`

**当设计稿中某模块被一张完整背景图整体覆盖时，必须用 `visual_groups` 作父容器，禁止再生成同尺寸的空容器。**

来源：实测出现过"背景图 + 同尺寸空容器"并存 → 空容器挡住点击或造成层级混乱。这条属于**层级与点击热区**类缺陷，静态看不出来，往往到真机才暴露。

## 6. 校验（每次改完必跑）

| 校验 | 目的 |
|---|---|
| **专项 `verify_*` 脚本** | 逐个界面的结构与绑定断言 |
| **生成器双跑哈希** | 证明确定性（第 4 节） |
| **TypeScript 检查** | 属性名对不上时在此暴露 |
| **多语言改造时**：语言 key 存在性 | 防"显示成 key" |

**顺序**：生成 → 双跑哈希 → 专项 verify → TS 检查。**任一不过不进下一步。**

## 7. 合成节点（美术稿里没有的代码节点）

代码需要但设计稿没有的节点（如动态列表容器、占位节点），**也应由生成器以稳定标识创建**，不要运行时 `addChild` 临时拼。

- 理由：运行时拼出来的节点在编辑器里看不到，无法所见即所得，也无法静态校验。
- "稳定标识"指：同一逻辑节点每次得到同一个 fileId/uuid，保证 diff 可控。

## 8. 与其它模块的衔接

- 生成器产出的是**骨架**；要开发一个新界面的完整体验（效果图 → 控件切分 → 重组 → 视觉 QA → 固化）走 `ui-feature-pipeline`。
- 要把运行时换肤结果**固化回 prefab** 走 `prefab-bake`。
- 生成器的中间自检可走 `cocos-mcp-channel`（编辑器通道）。
