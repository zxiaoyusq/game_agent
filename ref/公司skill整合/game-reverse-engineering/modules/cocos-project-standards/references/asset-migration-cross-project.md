# 跨工程资源与 Prefab 移植

> **何时读我**：要把**另一个 Cocos 工程**里的某个 prefab 及其关联文件（图片、动画、脚本、字体）搬到当前工程，并让它在新工程里正确关联、可运行、可维护时。
> **读完能做到**：挖全依赖（含**不在 prefab 里的**隐性依赖），在零 uuid 冲突的前提下整体落地，并区分"该删"与"删了会坏"的旧资源。
> **范围**：`[COCOS]` 方法论 + `[DADA]` 具体项目值。

**为什么单独成篇**：跨工程移植的失败几乎都不在"拷贝文件"，而在**依赖挖不全**和**旧资源去留判断错**——两者都到运行期才暴露。

## 1. 先侦察，再动手（禁止边拷边试）

只读侦察要产出一张**清单**，并在动手前把疑问**一次性问全**。

`[DADA]` 实测的侦察结论形态（可直接作为模板）：

```
源 prefab：纯排版界面（29 节点，仅 2 个 Sprite）
关键依赖：嵌套预制体 X.prefab + 字体 F.TTF + 工程脚本 S.ts
结论：与目标工程零 uuid 冲突 ✓
需要拷贝的文件：共 8 个（1 主 prefab + 2 嵌套 prefab + 1 动画 + 4 图）
目标工程已有同路径同 uuid 的：F.TTF / S.ts → 直接复用，无需拷贝
```

## 2. 四项前置核对（每一项都可能让方案推翻）

| # | 核对项 | 为什么必须查 | `[DADA]` 实测 |
|---|---|---|---|
| 1 | **两工程的设计分辨率是否一致** | 不一致则所有节点坐标/尺寸都要换算，**不是拷贝能解决的** | 两工程都是 750×1600 → 可原样搬迁 |
| 2 | **共享依赖（字体/脚本）是否已存在且 uuid 相同** | uuid 相同才能"直接复用"；不同则会产生两份同物异 uuid 的资源 | 字体与脚本**同路径同 uuid**（脚本字节数仅差 1，内容等价）→ 复用 |
| 3 | **是否有 uuid 冲突** | 同 uuid 不同内容 = 静默串资源，极难排查 | **零冲突** ✓ |
| 4 | **源 prefab 有没有控制器脚本** | 有逻辑就要一起移植并适配接口；没有则只搬版式 | 源工程**没有任何代码引用**它（纯排版）→ 无逻辑要移植 |

## 3. 依赖必须**递归**挖，且要挖"不在 prefab 里"的那一类

### 3.1 显性依赖：从 prefab 向外递归

逐层展开：主 prefab → **嵌套 prefab** → **动画 clip** → 图片/贴图 → 字体 → 脚本组件。

`[DADA]` 实测链：主 prefab 直接依赖仅 5 个，但**递归后共 8 个文件**（嵌套 prefab 又依赖第二个嵌套 prefab、动画 clip、字体、三张图）。

**要点**：
- **嵌套 prefab**（`Miscs/` 下的小件）最容易被漏——它们不在主 prefab 的文件里，只在组件引用里。
- **动画 clip** 与 prefab 是两个文件；漏了 clip → 组件在但动画不播。
- **同一张图在多处被引用**时要记录全部引用点，判断去留时用得上（见第 5 节）。

### 3.2 隐性依赖：共享行为组件 ⚠️ 最容易漏的一类

**"源界面的某个表现"可能根本不在这个 prefab 里**，而在源工程的**共享组件/框架**里。

`[DADA]` 实例：用户指出"源工程这个界面弹出时有动画，你搬过来没有"——实测**源 prefab 里根本没有 `cc.Animation` 组件**；那个弹出动画来自源工程的一个共享组件（`onEnable` 时 scale 0.01→1、0.3s、`backOut`；关闭 1→0.01、0.2s、`backIn`，并处理"复用不销毁"时的末态残留）。

**排查方法**：
1. 先确认源 prefab **自身**有没有动画/行为组件（`14 个含 Animation 的 prefab 里没有它` 这种反向证据也要记录）。
2. 若没有 → 在源工程里搜**共享的弹出/入场行为组件**（按功能名与服务多个 prefab 的事实定位）。
3. 判断目标工程**有没有等价机制**：有就复用目标工程的（**不要搬源工程的**，否则同一工程两套弹窗行为）；没有才移植。

> 结论纪律：**"搬了 prefab 就该有原版表现"是错的假设**。表现可能由工程级机制提供，必须单独取证。

## 4. 拷贝：带 `.meta` 一起搬，uuid 才能一致

**资源文件与它的 `.meta` 必须成对拷贝**。只拷图片不拷 meta → 目标工程重新生成 uuid → prefab 里的引用全部解析失败。

`[DADA]` 实测做法：7 个资源文件 + 各自 `.meta` 一起落地，**uuid 与源工程完全一致** → prefab 里的引用**天然可解析**，无需改写任何引用。

**跨 bundle 的归属**：源工程某资源原属 bundle A，目标工程可能没有 A（或不该引入 A）。`[DADA]` 实测：两张图原本属源工程的 `main` bundle，目标工程无此 bundle → 放进目标工程已有的 `lobby` bundle，**避免跨 bundle 依赖**。

## 5. 旧资源去留：删之前先查全工程引用（两个方向的误判）

移植后常会留下"源 prefab 独有"的资源。**删与不删都要有证据**。

| 情形 | `[DADA]` 实测 | 处置 |
|---|---|---|
| 被**其它界面**引用 | 字体 `F.TTF` 被目标工程的另一个 prefab 引用 | **不能删**：只把移植过来的 Label 改成系统字体，**字体文件保留**；要删得先改那个界面 |
| 只被**移植过来的** prefab 引用 | 渐变脚本仅被新 prefab 引用（4 处），别处零引用 | 移除这 4 个组件后即**死代码，可删** |

**判据**：删除前对**全工程**做一次引用检索（含 prefab、场景、脚本字符串）。**"我移植的那个文件不再用它了" ≠ "全工程没人用"**。

## 6. 覆盖目标 prefab：保留目标的 meta

要"用源版式替换目标 prefab"时，**保留目标 `.meta` 的 uuid**，让注册路径与外部引用零改动；同时处理 `__id__` 索引重映射与**组件注入**（移植过来的 prefab 通常缺目标工程的 UI 控制器组件）。

**完整手法见 `modules/cocos-project-standards/references/prefab-json-batch-editing.md`**（第 4 节），本文件不重复。

## 7. 适配层与接口约束

- **对外接口不变**是硬约束：调用方（系统/其它界面）不应因换版式而改代码。`[DADA]` 实测交付逐项列出了"`onOpen`/`onClose` 签名与语义不变"。
- 新结构需要新代码时，**新增脚本放在被指定的目录**下（来源任务的约束是"新增脚本都放 `<System>/UI` 下"），并可用**适配层**隔离新旧结构差异。
- 语言/文案：新增文案要**同时**加进语言表并重生成数据（见 `modules/cocos-project-standards/references/config-pipeline.md` 与 `modules/cocos-project-standards/references/i18n-and-text.md`）。

## 8. 验证（静态 + 编辑器，两层都要）

| 层 | 检查 |
|---|---|
| 静态 | 引用 uuid **全部可解析**（未解析 = 0）；脚本组件类型**全部解析**；移植资源**全部就位**；目标工程旧组件/死脚本**零残留**；多语言 key **都在表里**；字体策略符合决定（如"全部系统字体"） |
| 编辑器 | 触发导入并**读编辑器日志**：各文件 Import 成功、被删脚本 Destroy 被认、**无 TS 编译错误** |

**已知良性噪声**：删除脚本后打包器可能报一次**陈旧缓存 error**，**下一轮编译自清**；判据是"之后刷新不再复现"，不必当故障（想彻底清可重启编辑器）。

## 9. 交付纪律

- **备份**：按阶段分目录（覆盖前 / 注入前 / 字体改动前 / 配置表原表），支持逐步回退。
- **超范围改动必须显式声明**：`[DADA]` 实测为对齐目标工程惯例补了按钮音效组件，交付里单列一节"我超出了源 prefab 的额外改动（你说一声就撤）"。**默默加东西 = 把判断责任转移给用户而不告知。**
- **默认不提交**：等用户在编辑器里验收后再提交/合并。
- **给出可视化验收步骤**（打开哪个 prefab、跑什么流程、看哪三点），而不是只说"已完成"。
