# 广告未接入反馈与奖励生命周期

> **何时读我**：遇到广告未接入、点广告按钮没反应、失败后按钮卡住、重复领奖，或旧请求的结果发到了新场景/新关卡。
> **读完能做到**：把每个广告入口的真实调用与证据等级盘点清楚，定出反馈方式分级，并设计请求身份、attempt/claim 双重幂等、失败终态、加载与播放计时、暂停归属和可跑通真实业务链的 QA。
> **范围**：`GENERALIZED_PATTERN`

范围：GENERALIZED_PATTERN。来源是已落地的离线重建案例。迁移时重新确认当前业务入口、provider 契约、领取单位和暂停 owner，不复制案例广告位、奖励数、超时或按钮布局。

适用：广告未接入、主动广告按钮无反馈、失败后按钮卡住、重复领奖、旧请求影响新场景。只修这些问题时，无需启动完整供应商替换、联网隔离或新增商业玩法流程。

## 先盘点真实入口，再判断反馈方式

对每个实际调用记录：业务 owner、玩家动作、展示格式、资格、请求方法、成功消费者、失败消费者、取消/离场路径、证据等级。调用方到奖励写入要可追踪；广告配置或资源名字存在不能证明业务已接通。

- 玩家主动点击的激励入口：失败应有可关闭反馈，并留在原业务界面。
- 自动横幅/插屏：按原版流程与产品要求降级，通常静默跳过；不可把每次刷新和切页变成失败弹窗。
- 只存在于 metadata、图标或候选目录的每日/复活/宝箱/付费入口：标记未实现或待证，不自动新增玩法、发奖或开放资格。
- 无 SDK、未同意、禁用、策略抑制、加载失败和用户取消是不同状态。反馈不能顺便开启 SDK、写入同意或模拟观看完成。

## 原版证据必须拆开证明

语言键只证明文案存在；prefab 证明序列化结构；方法名证明接口表面；调用链与受控运行才证明触发条件和事件顺序。

“有重试/确认两条翻译”不能证明广告错误弹两个按钮；“有未就绪 Toast 方法”不能证明网络错误 prefab 承接它；按钮无序列化回调也不能证明运行时未绑定。

缺少动态证据时，分别记录“原版文案已确认”和“当前交互为重建”。沿用已证文案，按钮只执行可用动作。没有 SDK 或真实重试路径时不提供伪重试；单确认布局也不得包装成原版固定行为。

## 请求身份必须先于任何可能的回调

Null adapter、资格拒绝、隐私门禁和缓存结果可能在请求方法返回前同步发信号。

下面的调用顺序不安全：先调用 show，返回后才保存 pending_request_id，而结果处理器只接受该 ID。同步失败会被当成外来结果丢弃，按钮永久等待。

优先在调用前预分配并登记 attempt/transaction ID，调用时传入，所有同步和异步结果沿用同一身份。若只能由 provider 返回 ID，可由 facade 原子地建立映射，或明确延迟分发；不要未经兼容检查改掉已有同步 API。监听器和 pending 状态必须先就绪。

还要区分：非空请求 ID 仅表示一次请求已编号，不表示展示成功或赚取奖励。

## 一次请求与一次业务领取是两种幂等

- attempt ID：每次重试唯一，防重复 callback 和取消后迟到结果。
- claim key：按当前游戏已证规则，例如一次完成记录加 placement，防同一业务领取被多次不同请求支付。不得把案例的 run 含义套到别的玩法。

只有相同 attempt 的去重账本，不足以阻止连点产生多个不同 attempt。请求等待时锁住对应入口；等待结束后恢复按钮；领取成功后保持该 claim 已领，新业务上下文按规则复位。重开同一上下文不应重置已领取状态。

奖励消费者同时核对 pending attempt、placement、claim 上下文、奖励类型与金额。不要仅按 placement 收取全局广播。离场和换关要明确取消、转交持久 owner 或延迟交付，不让旧结果发到新场景。

非空 proof 只是接口基本检查，不等于供应商真实性验证。正式接入需要由可信 adapter 验证结果来源。奖励和业务已领记录的持久化须有原子提交或可恢复交付；先写“已付账本”再依赖可能销毁的 UI 发货，会留下已提交却未到账的缺口。

## 失败终态、加载超时和事件乱序

将门禁拒绝、失败、超时、取消、无效奖励凭据收口到对应请求：清 pending、恢复入口、取消计时器，不发奖。重复终态不得重复恢复或再弹窗；自动展示失败不能升级成主动提示。

加载超时只管尚未展示的阶段。shown/impression 以后不能用加载上限截断仍在正常播放的视频。展示后失联和应用被终止的恢复策略另按当前 provider 合同设计。

reward_earned、closed、dismissed 不一定按所有厂商相同顺序到达。先验证具体合同，再由 adapter 规范化；若允许关闭后才发 earned，保留有界等待或可恢复交付，不能机械地将 closed 永久判取消。该次业务未获得有效 earned 时，不能因为 closed 就发奖。

## 资格策略、弹窗和暂停 owner

资格策略与入口语义必须同时验证。结算视频可能由自身 modal 请求；若全局“有 modal 就禁止广告”，接口虽存在却永远被抑制。只按当前资格和已可交互状态豁免该点位自身 modal，不删除全局动画、拖拽和其他弹窗守卫。

弹窗需要单例或明确栈顺序。确认、键盘与系统返回只关闭顶层；无伪重试循环。恢复不是简单写 paused=false：记录提示、系统后台、用户暂停各自的归属，最后一个暂停原因释放后才恢复。

至少覆盖这些顺序：提示先开→切后台→在后台关闭→回前台；先切后台→失败提示才到→回前台→关闭；用户本来已暂停→开关提示。最后一块或结算等待期必须拒绝不兼容请求，或补偿暂停期间错过的完成回调，避免永久停在 resolving。

横幅还需跟随业务 owner 显示/隐藏，不能认为 Godot/Unity 页面隐藏就自动隐藏原生 SDK 窗口。自动插屏需携带真实完成上下文；暂停退出不是完成事件。

## QA 必须经过真实业务链

最低链路：实际按钮/调用者 → facade → 可注入 adapter → 结果/凭据 → 业务消费者 → 持久化结果。

直接 emit 奖励信号、直接调用 grant handler、只断言源代码含 placement 字符串，最多证明局部函数，不能验收入口和发奖链。

应按本次变化覆盖：同步失败和异步失败、拒绝同意/禁用/策略抑制、未就绪、无效 proof、超时、shown 不被加载超时杀掉、取消重试、连点、重复结果、乱序回调、换关/离场迟到、同 claim 重开、新 claim 复位、后台与返回、最终经济落盘。失败分支必须断言经济不变和入口可恢复。

独立工程、独立用户目录及显式 save/consent/ledger 路径共同隔离；测试还要主动拒绝非隔离环境。截图验证真实弹窗文本和输入层级。桌面结果不替代最终 APK/MuMu/真机或供应商后台回执。测试数量是本轮结果，不是其他项目的固定门槛。
