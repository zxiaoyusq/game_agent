# Android Cocos 离线运行时：材质、特效、广告与回归防线

> **何时读我**：BlockMaster 离线包出现清屏材质不换或变两次、特殊材质预消除消失、Replay 卡死、广告只显示 Loading、Banner 消失，或要在发布前跑真机回归矩阵时读我。
> **读完能做到**：按 owner 与事件顺序定位材质/Trait 回归根因，把材质与效果组成一个 PresentationBundle 在稳定边界一次提交，并逐条跑完真机回归矩阵与三块可解保护。
> **范围**：`CASE_ONLY_BLOCKMASTER` + `GENERALIZED_PATTERN`

范围：`CASE_ONLY_BLOCKMASTER`，包含 `GENERALIZED_PATTERN`。其他项目可复用证据和 owner 方法，但不得复制 BlockMaster 的边界、SDK、事件名和阈值。

本参考来自 BlockMaster（Cocos Creator 2.x JSB）离线重建与真机验收。它适用于“资源已经在 APK 内，但断开原服务器后材质、特效、广告或埋点表现不稳定”的项目。

## 1. 先建立证据等级

不要把桥接函数返回、日志中的 `dispatch` 或 SDK 初始化当成业务成功。

- 广告成功至少要看到对应广告源的加载/展示回调，展示画面，以及关闭回调。Hisavana 聚合层日志不能单独证明最终供应商；需要供应商字段或展示链证据。

- Athena/传音埋点成功至少要看到正确 appId、事件入库/组包、上传请求和服务端成功码。JS 调用完成只证明“交给桥”，不证明“平台收到”。

- Firebase Remote Config、Firebase Analytics、Athena 是相邻但独立的链路，必须分别验证。

- 模拟器只做启动、语法和玩法回归；广告库存、白名单、供应商和埋点上传必须在真机验证。

## 2. 新手引导必须读取持久化完成状态

保留在场景树里的 guideLayer 或缓存字段可能在引导结束后仍存在。仅凭节点存在、`activeInHierarchy` 或 `SkinInfo._isFinishedGuide` 判断，会长期把正常玩家误判为新手，导致清屏材质永远不切换。

优先读取游戏自己的持久化进度，例如：

```js
Storage.storage.getItem("classGuideStep", 0) > 2
```

确认引导完成后立即返回非引导态，再以当前 guideLayer 子节点作为未完成阶段的辅助判断。引导首次清屏按已证实规则保持原表现，不切材质、不播放 SSS，避免低端机瞬时卡顿。不要把这条规则扩展成跨局“前 N 次清屏”预算，除非原代码或产品规则另有证据。

## 3. Replay 只去重，不等待配置

Replay 的第一条新局事件必须同步放行。配置准备、材质预热和本地模型更新可以后台进行，但不得 `await` 后再投递原事件；异步任务不返回会直接造成 Replay 卡死。

- 使用短时间同步闸门只丢弃重复 `E_Game_Start(newGame=true)`。

- 第一条事件立即进入原游戏流程。

- Replay 换外观不等于连续清屏，禁止触发 `showSSSWhenSkinChange`。

- Replay 广告关闭后恢复游戏和 Banner；不要让广告回调再次制造第二条新局事件。

## 4. 材质和特效必须是一个原子 PresentationBundle

特殊材质、普通配色、消行、连击、清屏、分数、棋盘和警告效果不是互相独立的随机器。原版 Trait 往往由同一个所有者在同一生命周期内提交。离线实现应把它们组成一个 `PresentationBundle`，一次选组、一次提交、一次落盘。

错误模式：

1. 自定义选择器先调用 `changeSkin(special)`；

2. 原生 `SkinTraitInfo` 或清屏 Trait 动画结束后再调用普通色；

3. 玩家看到一帧特殊材质，随后普通配色覆盖，形成双重变色。

诊断时给每次清屏分配 epoch，并同时记录：

- `SkinTraitInfo.changeSkin` 调用者、目标 skin、时间和 epoch；

- `E_Skin_Update`、`E_Skin_DataUpdateCompleted`、清屏开始与动画结束；

- PresentationBundle id、材质 id、效果组 id；

- 本 epoch 是否已经提交。

每个 epoch 只允许一个最终视觉提交。不要通过关闭整个原生 Trait 来“消重”，因为这些 Trait 常同时拥有清屏、多消、棋盘和 SSS 动画；关闭后会得到“材质能换但特效全没”的假修复。正确做法是保留原动画所有者，让本地控制器在其提交入口提供统一 bundle，或只抑制确认重复的第二次材质写入。

### 原版 owner 优先于全局清理

预消除、特殊材质显隐和动画恢复通常由同一个 handler 成对管理。不得遍历所有 proxy、调用名字相似的 clear/hide/remove、清对象池或任意延迟清理。这样会绕过原版 restore，造成特殊方块在预消除中消失，甚至整类特殊材质动画被关闭。

异步 bundle/Trait 加载完成也不能立刻热启用。加载只进入 pending；在 touch、预消除或动画结束后的稳定边界再 commit。完整反例见 `modules/gameplay-logic-reverse/references/blockmaster-v123-v124-lifecycle-regression.md`。

## 5. 特殊材质池：资源存在不等于运行时可用

APK 内有 120+ 材质目录，并不代表当前客户端都能直接加载。启用前逐项验证：bundle 索引可读、HEK 状态匹配、版本/config 存在、公共依赖已加载、`SkinThreeLoadInfo` 注册完成、`SkinThreeInfo.isSkinResReady(id)` 为真。

- 两份实际运行入口（主 assets JS 与 remote_seed/patch JS）必须同步。

- 等待 SeedCopier 完成标记后再预热，避免读取半拷贝包。

- 可采用惰性预热：先保证少量已验证材质可用，再逐批扩大；未 ready 的材质只能延期到下一次切换，不能在动画结束后晚到覆盖本轮外观。

- 使用“特殊材质优先牌堆 + 普通配色穿插牌堆”，相邻不重复，整池轮完前不重复；状态损坏时重建牌堆。

## 6. 广告链路的常见回归

- 不要叠加第二套全屏广告预加载器。重复 preload 会争用缓存、重置状态或使 Replay/失败广告只显示 Loading。

- Loading 兜底应短且可结算；项目目标为约 2 秒。奖励广告必须按 `onRewarded` 与 `onClosed` 组合结算，并自动回游戏，不能再次要求 Tap to Continue。

- VAST 关闭按钮要阻止落地页误跳转，但不能吞掉 `onClosed`。

- Banner “已加载但不可见”与“没有库存”不同。全屏广告会覆盖或隐藏 Banner；关闭后调用原生 `ensureCurrentBannerVisible()`，若缓存失效再重新 load。

- 常驻 Banner 需要健康检查和退避重试，不能高频无限创建广告对象。新手引导可延迟显示，结束后立即恢复。

- debug 包与正式签名包的包名、签名、appId、白名单和广告库存可能不同；两者必须分开记录结果。

## 7. 启动卡 Loading 的回归防线

这类项目通常同时存在 base 主 JS、remote seed patch JS、files/patch 缓存和 settings 哈希。只改一个入口会因安装方式和缓存不同表现为“上一版能启动，这一版卡住”。

- 每次改动同步两份运行 JS，并校验语法、标记和哈希/索引。

- 覆盖安装不能证明冷启动正确；最终必须清装验证。

- 不得粗暴禁用全部远程加载或 JSB 反射。应仅拦截已确认的原厂域名，并返回 schema-compatible 本地响应。

- 若启动卡住，先确认真实执行的是 APK assets 还是 files/patch，再排查 SeedCopier 时序、HEK/明文混用和原生崩溃。

## 8. 低端机降级不是删表现组

低端机策略应降低粒子数量、持续时间、并发、分辨率或帧率上限，同时保留 PresentationBundle 的语义一致性。不要把“关闭材质 Trait / 清屏 Trait”当作降级，否则玩法仍运行但美术规则被破坏。质量档只在安全边界切换，避免清屏动画中途重建棋盘或材质。

## 9. 三块出题必须做最终可解保护

离线泳道和历史模型只影响策略倾向，不能替代硬性可解检查。生成三块后，模拟三块的全部顺序、每个合法放置位置和每步可能触发的行列/区域消除；至少存在一条能放完三块的路径才交给玩家。若无解，重新抽取或使用当前泳道的安全候选。该保护应在最终出块出口执行，防止上层算法随后改写结果。

## 10. 必跑真机回归矩阵

1. 清装启动、Welcome 首次点击可关闭、引导首次清屏不换色不播 SSS。

2. 正常局新局和 Replay 各验证一次；Replay 不阻塞、不重复开局、不误触发 SSS。

3. 普通清屏、多消、连续清屏、清屏警告分别截图和记录事件；每次只发生一次外观提交，材质与效果组匹配。

4. 特殊材质与普通配色都能进入，牌堆轮换相邻不重复；棋盘边框和粒子无偏移。

5. 连续生成多组三块并执行可解模拟；真机长玩不能出现明显死局。

6. Banner 冷启动显示、全屏广告前后都恢复；Replay 插屏、失败复活奖励、关闭自动继续分别闭环。

7. Athena、Firebase、广告供应商分别取得网络/回调证据；原厂域名 PCAP 为零。

8. 至少一台低端机做长时帧率、ANR、FATAL 和内存观察。

## 11. Git 与交付

- 只提交源码、构建脚本、测试、配置快照和报告；排除 APK、out、tmp、日志、截图、反编译目录与缓存。

- 静态测试、两份 JS 语法检查、zipalign、签名、ABI、版本和正式证书都必须重新验证。

- 报告必须区分“静态通过”“模拟器通过”“真机观察到”“平台后台确认”。未闭环项不得写成已修复。

## BlockMaster 状态记录规则

旧版本曾分别证明过原厂网络隔离、六套本地快照、本地玩家模型、Replay 非阻塞、奖励自动结算、VAST 关闭保护和特殊材质预热，但这些能力在后续补丁中出现过回归。不要把“某一旧包曾通过”写成当前包仍通过。

每次交付重新按矩阵验收，并把结果绑定 APK SHA-256。V124 仅作为当前调试签名的视觉生命周期 QA 基线：V123 已回退破坏特殊材质预消除的全局清理，V124 又把异步 Trait 激活推迟到稳定边界。广告、埋点、PCAP、正式签名和长时稳定性仍需对具体候选包单独闭环。
