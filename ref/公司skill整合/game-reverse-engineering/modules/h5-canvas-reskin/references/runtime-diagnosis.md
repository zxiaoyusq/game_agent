# 运行时诊断：卡死 / 操作无反应

> 范围：`GENERALIZED_PATTERN`。手法可迁移；代码片段来自来源案例，**类名函数名必须按当前项目重新定位**。

## 0. 先分成三类，别混为一谈

用户说"卡死"时，实际可能是三件完全不同的事。**用三套不同证据区分**：

| 类型 | 表现 | 需要的证据 | 排查方向 |
|---|---|---|---|
| **画面停摆**（渲染死） | 步分在变、`fps` 仍 60、**画面完全静止** | **截图逐像素一致** + GPU/合成器告警 | 渲染 / GPU 合成器 |
| **逻辑停摆**（状态死） | 进度信号长期不变，**且期间发过足够输入** | 运行时对象快照 | 玩法逻辑 / 异步回调 |
| **输入被关**（能跑但操作无反应） | `fps`/时钟/动画全正常，**只有操作无效** | **"是否允许操作"判断函数的每个条件项** | 输入闸门 / 锁存标志 |

> **第三类最难找**，因为所有"游戏是否活着"的指标都正常。**见 §2。**

## 1. 取证纪律（这几条不遵守会自己骗自己）

### 1.1 正在被别的脚本驱动的 App，不要用第二个客户端判断它的状态

来源案例：界面采集脚本在跑的同时又连了一个客户端，读到游戏时钟**两次完全相同**，
一度以为抓到卡死现场 —— 实际是两个客户端互扰，**游戏本身健康**。

### 1.2 判断"游戏是否活着"必须**一次读全**

只读状态名会把"空闲无动画"误判成卡死。一次读全：

```
状态名 / 游戏时钟 / fps / paused / 渲染类型
场景根子节点数 / 补间数量 / 分数 / 步数 / 窗口层子节点数
画面像素颜色数（纯色 = 空白帧）
```

### 1.3 不要用游戏时钟当停摆判据

时钟**永远在走**（只要主循环活着），拿它当进度信号 → **永不触发**，
会给出"跑了 N 小时 0 卡死"的**假阴性**结论。时钟只用来确认主循环活着。

### 1.4 进度信号要选"只有真实推进才变"的量

- ✅ 步数 / 分数 / 关卡进度
- ❌ 场景树几何和（空闲动画一直改坐标）
- ❌ 游戏时钟

### 1.5 只按"进度不变"判停摆会误报

玩家没做出有效操作时进度本来就不变 → 必须加"**期间已发过足够多次输入**"。
另外：**没有进度信号的状态（如地图）不要判逻辑停摆**，交给画面检测。

### 1.6 随机压测命中率极低 → 改**确定性枚举**

少数坏路径，随机采样打不到。把**入口全部列出来逐个走**：
从代码里提取所有弹窗/界面方法名，逐个调用并检查健康状态。
来源案例：随机 800+ 次操作打不到，**21 个弹窗枚举一遍就定位了**。

### 1.7 "点了没反应"不等于"游戏卡死"

消除类游戏**随机拖拽绝大多数不形成消除**，所以"拖了 N 次步数没变"**不能**推出输入失灵。
要区分"渲染死 / 状态死 / 输入被关"，只能用 §0 的两套证据。

## 2. 「能跑但拖不动」= 输入被**锁存标志**永久关掉

### 2.1 典型代码形态

```js
// 锁存标志：由信号开，由另一个信号关
bus.on("onWindowOpened").add(function(){ this.anyWindowOpen = true  })
bus.on("onAllWindowsClosed").add(function(){ this.anyWindowOpen = false })

InputController.prototype.canMakeMove = function() {
    return !this.locked && !!this.board.actionManager.noAction
        && !goalAchieved && !this.anyWindowOpen      // ← 锁存标志
}

// 而"关"的那次，被放进了**补间动画的 onComplete**
Window.prototype.closeWindow = function() {
    this.closing || (this.lockInput(), this.closing = true, ...
        tween(this).to({alpha:0}, 200).onComplete.add(function(){
            bus.dispatch("onWindowClosed")   // ← 只在补间完成时派发
            this.destroy()
        }))
}
```

**脆弱点**：只要**任意一个窗口被"绕过 `closeWindow`"地销毁**
（补间被打断 / 状态切换清掉 tween / 外部直接 `destroy()`），
派发永不发生 ⇒ 标志卡在 `true` ⇒ `canMakeMove()` 永久 `false` ⇒ **拖不动，而游戏照跑**。

### 2.2 实测复现与反证（来源案例）

| 步骤 | 锁存标志 | `canMakeMove()` | 窗口层子节点 |
|---|---|---|---|
| 起始 | false | true | 0 |
| 开窗 | true | false（正确，窗口挡着） | 1 |
| **绕过关闭直接 destroy —— 修复前** | true | **false** ❌ 永久卡住 | 0 |
| **同上 —— 修复后** | true | **true** ✅ 恢复 | 0 |

### 2.3 修法：**完全弃用锁存标志，改实时读真实状态**

```js
// ❌ 错：`||` 保留了锁存，同样步骤依然卡住
&& !((this.state.windowLayer && this.state.windowLayer.children.length > 0) || this.anyWindowOpen)
// ✅ 对：只信实时状态
&& !(this.state.windowLayer && this.state.windowLayer.children.length > 0)
```

> **弃用就要弃干净。** 来源案例第一版补丁写成"实时状态 `||` 锁存标志"，
> **用原始复现步骤仍然能卡住** —— 这个坑只能靠复现抓出来。

### 2.4 通用排查手法（这类问题都能用）

1. 先确认游戏是活的（`fps`/时钟/场景节点都正常）**却操作无反应**
2. **去找"是否允许操作"的那个判断函数**（常见名 `canMakeMove` / `canInteract` / `isInputAllowed`），
   把它返回的**每一个条件项逐个打印出来**
3. 哪个条件项卡住了，就顺着它查**谁负责把它置回**
4. 若它是**锁存标志**（信号开、另一信号关），重点查**"关"的那一次会不会被跳过** ——
   尤其是把"关"放进**补间 `onComplete`**、**定时器回调**、**异步回调**里的写法
5. **修复方向**：锁存标志一律不能作为最终判据，要改成**实时读真实状态**

## 3. 画面停摆检测（渲染死）

每 N 次采样抓一张真机截图，**连续 M 张逐像素完全一致**即判渲染停摆
（只取截图的字节指纹即可，不需要解码图像）。

**必须自证**：人为停掉渲染（如把渲染函数置空），确认它真的会触发。
**没验证过的看门狗给出的"0 卡死"不能作为结论。**

**来源案例自证输出**（症状与"能跑但拖不动"极易混淆，要靠这个区分）：

```
[!] 画面停摆：连续 3 次截图逐像素一致（游戏状态仍在变）
    运行时: { "state":..., "tweenCount":…, "fps":60 }
```

**两类检测都要有**，因为成因、证据和修法完全不同（见 §0 表）。

## 4. 广告 / 异步回调链路：整条链上没有超时

常见形态：游戏 → 桥接脚本 → `postMessage` 给宿主 → 宿主 SDK →
回调 `postMessage` 回来 → 触发 success/failure。

**风险**：只要任何一环不回，**而代码里没有超时**，游戏若在此等待就会**永久卡住**。

**排查**：

1. 看游戏调用广告的地方带不带回调；**不带回调的调用不会挂**
2. 确认当前包的域名/宿主环境走的是哪条分支 ——
   来源案例里代码是 `域名 == "某站点" ? 走广告 : 弹一个自动销毁的提示`，
   **在 APK（`file://`）里根本不走广告**，所以这条被排除
3. 若确实走广告：**实测一次**，观察回调是否返回；不返回就是这个原因

## 5. 取证时要假定的两件事

- **游戏可能把 `console.log` 屏蔽了**（`console.log = function(){}`）。
  看不到游戏自身日志时，只能靠 `window.onerror` + 设备 logcat。
- **异常会被"吞"在异步回调里**。挂 `window.onerror` 并包一层
  `JSON.parse`（或其他高频入口）记录**调用栈**，能直接定位到出错函数。
