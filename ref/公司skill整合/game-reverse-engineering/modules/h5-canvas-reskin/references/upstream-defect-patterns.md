# 上游缺陷模式与补丁纪律

> 范围：`GENERALIZED_PATTERN`。**缺陷模式可迁移**；具体文件、函数名与行业语境必须按当前项目重新定位。
> 换皮会把整条链路压到边界，**把上游早就存在的缺陷暴露出来** —— 命中时不要第一反应怀疑自己改的东西。

## 0. 心态前提

本文档里的缺陷**都在原版里同样存在**（非美术文件逐字节一致已经证明换皮没引入它们）。
换皮只是让它们**变得可达**。发现后应当：**显式修、显式声明、显式反证**，而不是绕开或隐瞒。

## 1. 模式 A：未钳制的数组下标

### 形态

```js
// 钳制了变量，却用未钳制的参数去索引
this.index = Math.min(list.length - 1, a),
data       = JSON.parse(JSON.stringify(list[a]))    // a 越界 → undefined → 抛异常
```

### 症状（**这是"状态初始化失败"的指纹**）

- 场景根子节点数 **`world.children === 0`**（被清空）
- 状态名**仍是对局态**、`fps` 正常、**时钟照走**
- 画面只剩背景底色
- 有 JS 异常，但可能被异步链路吞掉

### 边界测试法

直接对可疑数组做取值测试，看从哪里开始抛：

```
a = len-2 → ok
a = len-1 → ok
a = len   → THROW
a = len+1 → THROW
```

### 修法

```js
Math.min(list.length - 1, Math.max(0, a|0))
```

> ⚠️ **补丁陷阱**：只写 `Math.min(len-1, a)` **不够** ——
> `a` 为 `undefined` 时 `Math.min(449, undefined)` 得到 **NaN**，索引依旧 undefined、照样崩。
> **必须用 `a|0` 把 undefined/NaN 归零。**
> **这个坑只能靠"用原始触发路径复测"发现**，读代码看不出来（来源案例第一版补丁就栽在这）。

### 同款模式要全扫一遍

同一个项目里这类写法常有**多处**。扫描所有 `JSON.parse(JSON.stringify(list[...]))`
与 `list[...]` 访问，逐处判断：
- **编辑器专用**的可以跳过（不在发布路径）
- **上一行已钳制**的可以跳过
- **既不钳制又可达**的必须修

## 2. 模式 B：无兜底的持久化读取

### 形态

```js
// 初始化时有检查，读取时没有 —— 同一个键两套写法
init:       var a = storage.getItem(K); a ? (this.data = JSON.parse(a), ...) : (...)
窗口 A:      JSON.parse(storage.getItem(K)).points        // 无检查
窗口 B:      JSON.parse(storage.getItem(K)).points        // 无检查
```

### 症状

**窗口构造中途抛异常** ⇒ 窗口半成品、**输入可能被留在锁住状态**（表现为"卡死无法拖动"）。

### 触发条件

初始化只建内存对象、**不立即写回** ⇒ "全新安装到第一次写入之间"该键是缺失的；
或者**存储本身写入失败**（配额、隐私模式、WebView 存储被禁）。

### 实测确认法

```js
// 直接复现那两行的写法
var had = storage.getItem(K);
storage.removeItem(K);
try { JSON.parse(storage.getItem(K)).points } catch(e) { /* 应抛 "reading 'points'" */ }
if (had) storage.setItem(K, had);   // 复原
```

### 修法

```js
(JSON.parse(storage.getItem(K)) || {}).points || []
```

## 3. 模式 C：锁存标志 + 异步回调关闭

见 [运行时诊断](runtime-diagnosis.md) §2。要点复述：

- 标志由**信号 A 开**、**信号 B 关**
- 而"关"被放进**补间 `onComplete` / 定时器 / 异步回调**
- ⇒ 回调被跳过（补间被打断、状态切换清 tween、对象被直接销毁）时**永久卡住**
- **修法：完全弃用锁存标志，改实时读真实状态**；`||` 兜底等于没弃用

## 4. 补丁纪律（**改上游代码必须做到**）

改上游 JS 是必要手段，但必须做成**流程里的声明步骤**，不是手改：

1. **写成声明式补丁列表**：每条含意图注释 + **精确原文** + 替换文
2. **命中次数必须校验**（应为 1）—— **不为 1 就中止**，避免产出未修复的包
3. 验收脚本把该文件登记为「**已声明修复**」，与「**未声明的代码改动**」严格区分 ——
   **未声明项必须为 0**
4. **修复后必须用原始触发路径反证**，不能只看代码对

### 建议的补丁列表结构

```python
CODE_PATCHES = [
    # ① 用途说明（为什么会崩、实测边界、修复原理）
    ("精确原文…", "替换文…"),
    # ② …
    ("精确原文…", "替换文…"),
]
```

**原文必须是唯一匹配的完整片段**（含必要的前后文与换行/空格），
否则会命中错位置或 0 次。命中 0 次说明原文抄错了，**不要放宽匹配**。

### 验收脚本侧的写法

```python
DECLARED = {"js/某个文件.js"}          # 已声明的有意修改
undeclared = [x for x in diff_nonart if x not in DECLARED]
add("非美术文件逐字节一致（除已声明修复）", not undeclared,
    "未声明 %d 个；已声明修复 %d 个" % (len(undeclared), len(diff_nonart) - len(undeclared)))
```

## 5. 这类问题的通用排查顺序

1. **先确认是不是自己引入的** —— 非美术文件逐字节比对；是 0 差异就往上游找
2. **看症状是不是"状态被清空"** —— 是的话优先查**状态初始化路径**有没有异常
3. **挂错误钩子拿调用栈** —— 包一层高频入口（如 `JSON.parse`）记录栈，直接定位到函数
4. **边界测试定位数组下标** —— `len-2 / len-1 / len / len+1` 逐个试
5. **确认可达性** —— 编辑器专用 / 已钳制 / 需要特定条件的，分别标注
6. **修 → 声明 → 用原始路径反证**

## 6. 哪些"缺陷"其实不是缺陷

| 看起来像 | 实际是 | 怎么判断 |
|---|---|---|
| 窗口调用抛异常 | **我调用姿势不对**（没传必需参数） | 从正常 UI 路径触发的对照一下；异常后场景**没有被清空**说明只是参数问题 |
| 广告回调不返回 | **当前环境根本不走广告**（按域名/宿主分支） | 读那条三元表达式，确认当前环境走哪个分支 |
| 某资源 404 | **原包就没有这个文件** | 阶段零的原版基线对账 |
| 某元素"缺失" | **原图本来就是空的**（alpha 全 0） | 同上 |
| 进不去对局 | **直接 `state.start('Game')` 不带参数**会建出坏状态 | 必须走**正常入口**；这条也会污染 A/B 对照（见 `wrong-approaches.md` E 组 #32） |
