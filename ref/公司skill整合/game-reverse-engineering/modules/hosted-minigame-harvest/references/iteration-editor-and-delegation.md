# 宿主游戏迭代：关卡工具、跨会话解码与经验回写

范围：`GENERALIZED_PATTERN`。具体引擎、牌面编号、存档 key、SDK、设备和路径均需重新取证，不复制案例值。用户指定开发路径、是否运行 QA、由谁拆解及允许修改的范围优先。

## 持续迭代与回写

- 项目持续目标或计划明确「技能沉淀」时，在每个可交付里程碑、重大阻塞解决或一批相关迭代结束后，检查新经验是否适合通用化；没有新证据就记无更新，不凑条目。可继续开发时不能把长报告当成产出。
- 经验回写先区分已运行验证、静态/结构证据、推断、候选和失败；只把跨项目适用的方法写入对应模块，项目专属事实、地址、素材或未经验收代码放项目文档并标身份与版本。
- 核对实际维护源及各入口的链接关系，先读现有内容，做最小增补并保留原流程；链接到详细参考，避免在总路由复制大段操作。检查格式、相对链接及变更范围；按照用户要求决定是否提交、同步或推送，不能擅自声称同步完成。
- 明确用户自己负责 QA 时，不操作其设备、不把静态构建或其他环境数据包装成 QA；记录用户待验收项。构建成功、文件存在和用户认可的视觉方向均不证明运行交互通过。
- 候选隔离要分别审计原程序、项目新增脚本与宿主封装的存储键；仅隔离棋盘快照不代表关卡、道具和设置都隔离。浏览器存储按 origin（协议、主机、端口）隔离，路径不同不隔离 localStorage；Service Worker 缓存更新还受注册 scope 影响。并存候选时分别规划端口、存储键与 scope，不清理用户正在使用的数据；未审计的第三方存储标为未知。

## 可视化关卡编辑器：数据、视图和提交分层

1. 先定位源码配置、编译输出、离线缓存和运行时 owner，明确导入、编辑、保存、编译、上线/回退边界；不要让页面显示旧编译输出却称为当前源配置。无法自动读取时明确版本、来源和手动导入步骤，提供可复现的刷新入口。
2. 逐关显示已配置和未配置/回退关；固定盘显示具体牌 ID，随机盘展示可用格、空格、尺寸、随机池/种子与数量，不把 mask、随机样本或求解路径伪称固定牌面。落位方向、时间、道具、引导和广告策略逐项标注来源、全局/逐关作用域、已实现/候选/未知。区分牌库上限、可抽池、实际不同种类和总牌数。
3. 编辑器与总览采用同一数据模型；定位某关后可实际编辑、导出并给出应用/重建步骤。总览跳转到尚未配置的关卡时，明确提示当前显示的关卡，并让用户触发的新增操作优先使用所请求的编号；不得静默显示另一关或自动覆盖配置。对导入文件与正式数据的切换、编号上限和错误处理也应明确。
4. 生成式盘面先校验形状、成对、牌型引用及动态规则，再区分「存在当前可连对」「找到完整路径」「搜索超时/未知」。同样的随机种子、重力、洗牌、存档恢复和旧配置兼容需分别验证；不能把固定样本当全量保证。功能、广告或经济规则若不在关卡配置中，不应展示成可逐关修改。
   若新增指定牌池而正式编译链尚不支持，可先在独立候选中以单独的牌池文件叠加，并检查关卡是否为生成盘、ID 唯一且落在各主题可用帧范围、池容量不小于实际抽取种类数。映射使用独立随机流可避免改变既有棋盘生成顺序；池上限、实际抽样种类、固定盘与竞品真实 ID 分开记录。草稿导入失败须保留原数据，候选构建成功不等于运行验证。
5. 页面坐标、引擎图层坐标、画布 CSS 与 backing buffer/设备像素的映射必须确认；高 DPI 设备上避免对同一坐标重复缩放。布局变更要同时考虑棋盘、道具、实际点击范围、引导高亮、遮罩和广告安全区。引擎行为以当前运行时代码和用户指定设备为准。
   对引擎按需创建的暂停等控件，先定位创建、隐藏、销毁和后台进入路径；移动原生对象时保留其交互事件及动画状态，保存原始几何，并在对象销毁后释放记录。不要仅根据竞品对象名推断按钮回调；静态接入、候选构建与用户实际验收应分别记录。
6. 交付本地 HTML 时保留资源链接和数据来源；浏览器 file/http、缓存版本、乱码、缺失资源、导入导出及原始项目不被覆盖需要在获准的环境实际检查。用户暂不允许 QA 时只交未验收版本，不能报告通过。

## 关卡覆盖与回退循环

- 对原版、竞品和自研配置分别列来源、版本、关卡号、盘面形状、固定或随机、机制与验证状态；将“可进入的关卡数”“独立配置数”“独立盘面数”和“有证据还原的数量”分开统计。仅有数组、截图或一个随机样本时不要声称逐关完整还原。
- 若用户要求未配置关卡循环复用，明确有效配置集合、顺序、起点、缺号与边界、固定/随机规则、哪些属性复用及后续新配置如何并入；不要把某次项目的循环范围或缺号政策作为默认规则。对末个已配、首个回退、循环边界、新增配置后的映射和旧存档恢复做可重复检查，区分模拟与自然运行。

## 引导、道具与闲置保底的联动

- 先按各引导阶段记录目标区域、输入拦截、正常完成、跳过粒度（当前步骤/整段）、持久化、下游事件、恢复和超时；一次点击目标外是否计数、计数重置和是否吞掉触摸须由产品规则明确。跳过不能伪造消除、推进条件或产生意外的贯穿点击。
- 道具的解锁时机、库存、首次免费效果、引导标识与真实效果分别溯源；配置和用户预期冲突时明确差异并按已授权规则处理。闲置辅助如有要求，定义计时起点、有效操作、重复触发、适用关卡和提示目标；独立确认是否消耗、发奖或解锁，不以调用提示效果隐式更改库存或解锁。
- 组合检查引导锁定目标与辅助提示是否一致，避免推荐不可操作对象；验证暂停、弹窗、后台、洗牌/动画、关卡切换、胜负、重开和存档恢复时的计时及清理。脚本模拟与触屏、宿主验收分开报告；具体等待时间和策略由项目决定。

## 星级与结算接入

- 先核实分数的 owner、单位和生命周期：累计分、单关增量、配对分、时间或随机奖励可能不同；不能因为变量都叫 score 就套用其他游戏的阈值。对配对、奖励、胜败、重试及恢复分别追踪事件和存档，区分代码证据与实际行为。
- 如果单关增量依赖开局基准，将基准与同一局快照一并保存；旧快照缺基准、记录损坏或无法证明属于同一局时返回未知，不以恢复时的累计值伪造开局值。候选存档独立命名，接入前确认写入失败和并发行为。
- 单关星级、每关历史最高星数、星图累计与星匣进度分开建模；逐项核实胜败、重玩、领取和存档写入。历史最高星数的增加量不自动等于奖励或星匣进度；调用边、方法名和同名配置不能单独证明完整分支。
- 竞争产品阈值的公式与阈值输入来源需分别证实；项目自定阈值应标记设计依据，关卡盘面或计分变化时重新校准。候选示例若所有胜利都必然满星，应明确它不能证明难度或差异化评分已还原。

## 授权的 DSH 跨会话协作

- 用户明确指定 DSH 会话或授权委派时，使用 `dsh-guidance` 先核对完整 session ID、标题、项目身份、运行/队列/goal，再向指定会话发送任务；没有明确发送授权时不发送、不修改其目标。遵守用户对设备、视觉与数据访问的限制。
- 任务写清包版本/ABI/哈希、输入路径、要恢复的执行链和状态写入、具体输出路径、禁止覆盖范围、证据等级和完成条件。方法名、字段名、配置和截图分别只能证明各自内容；Unity IL2CPP 中先验证 metadata→native 地址映射，不能将不明指针表、方法名或推测当函数体。
- 通过回执区分 accepted、queued、consumed、消息落盘、AI 回复和最终交付；排队不等于执行、回复不等于结果。优先核查实际产物与原始证据，不重复发送相同任务，不擅自覆盖、清除或恢复其他 goal。
- 开发方先完成不依赖解码的独立工作；接收结果后对照目标版本、来源与已知不确定性再实现。竞品算法或评分不明时不伪造；项目自研替代要显式标注，真实 SDK 和付费规则不从对方市场直接推断。
