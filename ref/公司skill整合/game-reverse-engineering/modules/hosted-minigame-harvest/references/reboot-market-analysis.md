# 宿主小游戏重置立项：市场/竞品/平台分析与报告输出

> **何时读我**：用户已有宿主小游戏原包（或已完成拆解），要求"联网调研平台、用户画像、地区风格、同赛道头部产品，给出重置/迭代方向报告"；或在重置前要找可参考/可照搬关卡设计的竞品。
> **读完能做到**：按固定顺序收集背景、取证现状、抓竞品、产出 md + 带竞品图的 HTML 报告，并避开本次实测踩过的错误结论。
> **范围**：流程为 `GENERALIZED_PATTERN`；第 7 节 One Connect（AHA/传音）数值为 `CASE_ONLY_AHA`，不得复制到其他项目（`DO_NOT_COPY_LITERAL_VALUES`）。

## 1. 先提问，再调研（阶段 A）

调研前一次性问齐，缺项写入报告"待确认"，不要用常识补成事实：

| 必问项 | 用途 |
|---|---|
| 平台 SDK 文档/模板、包体上限、是否强制方向 | 广告方案、包体预算、布局 |
| 后台用户国家分布（DAU、占比，Top10+） | 语言、主题、配色、设备画像优先级 |
| 用户数据可信度（如共用手机导致性别失真） | 决定哪些画像维度不可用 |
| 目标市场与必须支持的语言 | 本地化范围 |
| 技术路线：原包上改 / 重建；人力 | 路线与工期 |
| 美术：是否有规范、是否允许 AI 生图 | 美术生产方式 |
| 平台能力：账号、排行榜、云存档、远程配置、联网率 | 留存系统能否在线化（离线优先时全部本地化） |
| 考核指标（DAU/留存/ARPDAU） | 报告优先级排序 |

用户发图片（如国家分布表）未成功到达时，**直接说没收到并请重发**，不要编数据继续写。

## 2. 现状取证（阶段 B，代码只读）

1. 读项目已有阶段说明/接口文档，复用已有证据，不重复造。
2. 包体按扩展名统计大小与数量；标出可删除壳（旧渠道 SDK、未用 CSS/JS）。**不要凭经验断言运行时依赖可删**（例：Construct 2 运行时通常依赖 jQuery，未验证前不可列为可删）。
3. 读宿主桥接与广告调用点（成功/失败/加载完成），列已知 bug（缺宿主接口报错、结算无返回等）。
4. **屏幕方向必须实测**：设计画布尺寸（如 data.js 的 1280×720）≠ 玩家看到的方向。用竖屏视口（如 390×844）与横屏视口各跑一次自然进入对局并截图，再下"横/竖屏"结论；同时核对运行时缩放模式与 orientations 字段。数据数组方向 ≠ 画面行列。
5. 版权：查原游戏是否仍在应用商店上架/更新（按包名/游戏 ID），代码里的原渠道 ID 是线索。若原版仍活跃，报告须单列版权风险与"美术/音频/名称全原创"建议，并请用户确认授权。

## 3. 平台 SDK 分析（阶段 C）

拿到 SDK 模板后：解压到项目内只读参考目录 → 读父页、游戏页、示例调用 → 写出 API 契约表（调用、时机、成功/失败回调、频控、失败是否必须继续流程）→ 映射到游戏现有调用点的改造清单。匹配 CombiMons 模板时按 [combimons-host-sdk-template.md](combimons-host-sdk-template.md)。注意远程加载的 SDK 不计入包体，但断网时广告必失败，流程须能继续。

## 4. 联网竞品采集（阶段 D）

**工具降级顺序**（本次实测）：内置 web_search 失败（余额/参数错误）→ DuckDuckGo HTML 会出人机验证 → Bing 可能空结果 → **Google Play 网页直抓可用**：

1. 搜索页：`https://play.google.com/store/search?q=<关键词>&c=apps&gl=<国家码>&hl=en`，用 UA 请求，正则 `details\?id=([A-Za-z0-9_.]+)` 取包名。按用户 Top 国家逐个 `gl=` 抓，取并集 —— 这比全球榜更贴近目标地区。
2. 详情页：`/store/apps/details?id=<pkg>&hl=en`。可稳定取 `og:title`、`og:description`、开发商链接、图标（`itemprop="image"` 或 `og:image`）、截图（`alt="Screenshot image"` 的 `play-lh` URL，追加 `=w360`）。下载量/评分的 DOM 正则不稳定，**取到后人工核对，取不到写"未取到"**，不要填 `0K+` 之类错误值。
3. 节流 ≥1.2s/请求；部分国家区会整批失败，记录失败国家。
4. **图片按 magic bytes 定后缀**：Play 的截图 URL 无后缀，实测同批混有 PNG（`89 50 4E 47`）和 JPEG（`FF D8 FF`）；按 `.webp` 统一命名会导致读图工具报错。下载后立即按 magic 改名。
5. 竞品分组：**直接同类**（同一玩法）/ **变体**（同题材不同规则）/ **同区强势品类**（留存与变现参考）/ **原版本身**（版权）。每款看截图判定玩法，不能按名称判定（同叫 "Tile Connect" 的产品可能是连连看，也可能是槽位消除）。

## 5. 报告结构（阶段 E）

在用户指定路径下新建独立文件夹（如 `分析报告\`），同时输出 `.md` 与 `.html`；竞品图放 `img\`，原始抓取数据存 `competitor_data.json`。

章节顺序：执行摘要 → 现状诊断（技术债表 + 包体分布）→ 平台 SDK 契约与改造点 → 用户国家分布（条形图 + 每国语言/设备）→ 目标用户画像 → 竞品（每款：图标 + 3 张截图 + 下载/评分 + 视觉风格/优势/可借鉴点）→ 共性总结（头部都在做 / 我们缺）→ 优化方向（广告、布局、关卡、美术规范、性能、本地化、伪社交）→ 版权风险 → 路线图 → 待确认清单 → 证据来源与边界。

HTML 要求：单文件 CSS、相对路径引用 `img/`、浏览器直接打开；生成后脚本校验每个 `src` 都存在（0 缺失）。

## 6. 本次踩坑与纠错（交付前自查）

| 错误 | 正确做法 |
|---|---|
| 把设计画布 1280×720 当成横屏，建议"改竖屏" | 先跑竖屏视口实测再下结论（见 §2.4） |
| 包体图表把 PNG 压缩收益写在音频行 | 每行说明对应同一资源类型；收益写在对应行 |
| 建议删除 jQuery | 运行时依赖未验证前不列可删 |
| 背景建议 1024×2048，未算体积 | 新增美术先估算体积（尺寸×格式），给出包体增量表 |
| 竞品安装量填了解析失败的 `0K+` | 解析失败写"未取到"，不入表 |
| 截图统一 `.webp` 后缀 | magic bytes 定后缀 |
| 宗教/人口比例等社会数据凭印象写 | 无来源的人口事实不写或标【待核实】 |

## 7. 关卡设计参考竞品的筛选法

用户问"哪些竞品玩法完全相同、关卡可参考或照搬"时：

1. 先写清原版规则（连线≤2 拐点、限时、提示/洗牌、棋盘尺寸与牌种数）。
2. 逐款看截图分类：同规则（连线路径消除）→ 可直接参考关卡曲线、棋盘尺寸、牌种数、时间、道具节奏；同题材不同规则（槽位/堆叠三消）→ 只借鉴进度系统与变现，不借关卡；
3. **"照搬"边界**：玩法规则与难度参数（尺寸/时间/牌种数曲线）可参考；具体关卡布局图案、美术、名称、文案属于他人作品，不照搬。可用其参数自建生成器，并对自己的棋盘做可解性验证。

### 案例（`CASE_ONLY_AHA`，One Connect，2026-10-29）

- 国家 Top3：巴基斯坦 13.88%、印度 13.21%、尼日利亚 9.86%；平台不支持远程配置、多数用户离线；包体 ≤20MB。
- 竞品截图判定：同规则连连看 = Boombox Onet（蝴蝶/动物，6 列，计时+提示+洗牌）、TerranDroid Onet、Higgs Tile Connect（节日主题大棋盘）、Ilyon Tile Link（不规则形状棋盘+计时）、Famobi 原版；**槽位三消（不可借关卡）** = Azur "Tile Connect"（7 槽位堆叠，名字误导）、Tile Explorer、Tile Club、Tiletopia、Triple Tile。
- 原版在竖屏视口自适应为 6 列×12 行，此前"横屏需改竖屏"结论已撤回。
