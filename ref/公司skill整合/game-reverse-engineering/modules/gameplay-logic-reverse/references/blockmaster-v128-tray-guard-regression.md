# BlockMaster V128 tray guard regression

> **何时读我**：哥哥说"tray 老是刷出 1x1"、"死局率不对"、"保护器/guard 把合法 tray 判死了"，或要在原版出块引擎外面加一层后验保护器而担心把分布改坏时。
> **读完能做到**：分清"原版 engine 偏爱小形状"与"后验 guard 判定过严 + 候选顺序偏置"两类根因，把 existential reachability 改回原版 solver 语义、把最小形状挪到候选末尾，并用八项通用测试矩阵 + 长序列 distribution 回归证明没有引入新的分布偏置。
> **范围**：`CASE_ONLY_BLOCKMASTER`

范围：`CASE_ONLY_BLOCKMASTER`。本文件记录 BlockMaster/Block Blast 10.4.7 直接基底中的具体类名、块 ID、补丁位置和测试证据。其他项目只迁移方法，必须重新定位自己的 producer、solver、形状表和提交边界。

## 已证实根因

- 原版 `BaubleTopic.solve()` 进入 `doSolve()`，内部已枚举三块的全部排列；只要存在一种顺序能把整组放完，就满足原版成功语义（existential reachability）。

- 本地保护器又逐个固定首块调用 `getTopicSolve()`，要求每一种首块选择都能完成。这把“至少有一条解”错误升级为“任意第一步都有解”，大量合法 tray 被判死。

- 修复候选池把块 ID `1` 放在第一位，而 `BlockShapeMap` 证明它是 `1x1`。保护器高频误触发后总是先命中最容易放置的候选，最终表现为连续大量 1x1。

- 因而故障不是原版出块引擎主动偏爱 1x1，而是后验 guard 同时存在判定过严和候选顺序偏置。

## V128 最小修复边界

1. 保留原版 producer，不重写泳道、Trait、分数阶段或形状分布。

2. `bmTraySolvable` 直接采用 `BaubleTopic.solve(board, blocks, true, true)` 的完整解结果，不再增加“all first choices”条件。

3. 原始 tray 只要满足原版 solver 就原样返回；保护器不追求“玩家任意摆放都不会失败”。

4. 确实无解时才搜索替代；先尝试最少槽位变化，普通小形状优先，块 ID `1` 放到候选末尾。

5. 扩大到两槽或三槽只允许发生在更小修改找不到解之后；每次试探从原始 tray 克隆，不累计失败候选。

6. `[1,1,1]` 仅是所有普通候选都失败后的绝对应急，并且仍须通过原版 solver；不得为了“零死局”无条件提交。

7. partial tray（已展示、已消耗一块、拖拽中）不可变；存储、渲染等多道验证 seam 必须幂等，并受同一出块 epoch 约束。

## 通用测试矩阵

以下测试属于 `GENERALIZED_PATTERN`，但本项目的块 ID 和函数名不可照搬：

1. 原 tray 有完整解，但某个首块顺序失败：必须原样保留，证明使用 existential 而非全称语义。

2. 真死 tray 只需替换一个普通块即可有解：只改一个槽，不得退化为 1x1。

3. 单槽方案均失败而多槽方案有解：只有项目确有扩大修复的规则时才进入下一层；保持未选槽不变。

4. 候选试探失败后再成功：每次都从原始 tray 和棋盘快照开始，不能污染棋盘、分数、RNG 或下一个候选。

5. 普通候选和 1x1 都能解：必须优先普通候选。

6. tray 已展示、已消耗或开始拖拽：晚到 guard 不得替换。

7. 旧局异步结果晚到新局：epoch 不匹配时丢弃。

8. 长序列 distribution 回归：比较保护前后 guard 触发率、替换槽位数、各形状频率、连续 1x1 长度和真实无解率，不能只断言“没有刷死”。

## V128 证据位置

- 原版 solver：`blockmaster_pro_swap/work/js_dumps/assets_main_index.75e4e.js` 的 `BaubleTopic`、`solve()`、`doSolve()`。

- 本地生成器：`blockmaster_v41_worktree/work/official_blockblast_capture/offline_suite_builder.py` 的 `bmTraySolvable` / `bmFindSafeTray`。

- 自动测试：`test_offline_suite_builder.py` 中“任一排列可完成则保持原 tray”和“真死 tray 优先非单格修复”用例。

- 运行时入口有主 assets 与 Seed/patch 两份，必须同时生成并在 APK 内检查旧判定字符串已消失；不能只检查源码模板。

这些路径只用于同一工作区的案例定位，不是其他项目的默认路径。

## 尚未由 V128 单独证明的内容

- V128 的小范围热修已消除“过严判定 + 1x1 排首位”这一直接洪水机制，但候选仍按固定顺序搜索；不能仅凭两个功能测试宣称长期形状分布已与原版完全一致。

- 后续若运行统计仍显示普通候选偏置，应在不改 producer 的前提下收集同级有效候选，再复用原权重或按 tray epoch 做可复现选择；搜索过程不得推进正式 RNG。

- 只有真机/模拟器长序列数据覆盖 guard 触发率、形状频率和连续极小块长度后，才能关闭分布回归项。

## 离线算法恢复边界

- 六套捕获快照、稳定账号分桶、近期对局记录和本地泳道可以选择原版已存在的参数组合；它们不是新的出块 producer。

- `algoSDK`、GBM、近期用户模型等缺失的实时服务输出只能用透明、确定、可测试的本地替代，不能宣称精确复刻服务器对当前用户的即时决策。

- 推荐职责顺序：原版引擎产出 -> 本地控制器在已证实的新局边界选择快照/泳道 -> guard 后验验证真实无解 -> 最小修复 -> 单次提交。

- 如果 guard 频繁触发，先查泳道参数、棋盘快照或 solver 调用是否错误；不要继续扩大万能候选池掩盖上游问题。

## 禁止回归

- 不恢复“每一种首块都必须成功”的过严判定。

- 不把 1x1、万能牌或最小形状放在修复池首位。

- 不用 guard 取代原版分布，也不以“死局率为零”单独证明体验正确。

- 不在 partial tray、拖拽、动画或跨 epoch 状态中热换块。

- 不把捕获快照等同服务器实时模型输出。
