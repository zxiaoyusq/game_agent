# 渲染与交付统一规范（所有引擎共用）
> **何时读我**：要跑 8 视角 1024 白底渲染、要判破面缺面与达标件数、要按四件套整理交付目录，或渲染长批次中途集体失败时。
> **读完能做到**：正确调用渲染工具（含中文路径绕 run.bat）、用文件系统判进度并处置尾部雪崩，按定稿判据（先过 7 个合成件自检）跑几何质量体检，产出四件套并写清面数口径与数据边界。
> **范围**：`GENERAL_DEFAULT`

## 渲染管线

- **官方去重工具**：`run.bat full -i <in> -o <out> -v 8 -r 1024` → 输出 RGBA → `alpha_composite` 纯白 (255,255,255)。8 worker，61 件约 39min、142 件约 60min；**同参数重跑按内容 md5 跳过已完成项**（可安全增量扩样）。实测吞吐（1024/8 视角/3 worker）：**约 29 s/件**，669 件 ≈ 3 h。
- **白模白底对比**：材质近白时（RE Engine clay 等）合成时 `point(lambda v: min(255, v*0.86))` 压暗。
- **含中文路径的正确调用（两条都做到才跑得通）**：
  1. **不要走 run.bat**：cmd.exe 按 GBK 解析命令行，路径含中文时直接报 `'E:\download\ȥ�ع���' is not recognized`。改直调工具自带解释器：
     `blender-4.2.*-windows-x64\4.2\python\bin\python.exe -B <tool>\main.pyc full -i <in> -o <out> -v 8 -r 1024 -w 3`
  2. 父进程转发子进程 UTF-8 日志前先 `sys.stdout.reconfigure(encoding='utf-8', errors='replace')`（本机 python stdout 默认 GBK，否则 `UnicodeEncodeError: 'gbk' codec can't encode character`）。
- 工具**接受 GLB 输入**（`.fbx/.obj/.glb/.gltf/.stl/.ply` 均在扫描白名单），GLB 可跳过中间 OBJ 直接渲染；OBJ 仅作交付口径核对。
- **长批次的"尾部雪崩"是资源耗尽，不是模型坏**（AC3R 实测）：669 件跑到第 600 件时，剩余 69 件在**同一秒**集体失败，Blender 退出码 `3221226091 (0xC0000142 DLL_INIT_FAILED)` 与 `1073807364 (0x40010004)`——是系统和 Blender 起不来了，跟模型无关。**处置**：确认无残留 `blender.exe` 后，把这批失败件复制到独立输入目录重渲（本次 **69/69 全成功**）；**不要**去逐个"修"那 69 个模型——结构自检（glTF JSON 块 + accessor 三角数）显示它们全部完好。
- **`md5_dedup.json` 是累积的，不会因换 `-i` 而重置**：换输入目录重跑 `full` 时它仍带着旧条目。本次就因此意外把 LOD0 的 669 件扩成了全 LOD 的 1,808 件（多吃 2.7 倍时间）。**更关键：渲染阶段根本不看 dedup 清单**——`render` 只遍历 `-i` 目录里找到的资产（实测把 dedup 剪成 667 条后，任务数仍是 1151+657=1808）。**要精确控制渲染范围，唯一可靠办法是把目标文件复制到独立输入目录再渲**（本次 69 件补渲就是这么做的：输入 `model\_retry69` → 输出 `_retry69_out`，`Render tasks: 69 to process, 0 skipped`，69/69 成功）。
- **进度用文件系统判断，不要信进度条**：`renders/` 下空目录数就是"未完成数"，`*.png` 总数 ÷ 视角数就是"已完成件数"。工具日志里的中文路径是 GBK 乱码，但目录名是 md5、文件数是可信的。

## 视角映射（不能想当然）

- **方位映射随模型而变**：燕云 006=正面、法环 000=正面、MHWilds 角色正视图 = view 6（270°）。逐批核验：目检 000/180 两张，左右轮廓对称性最高的一对即正/背。
- **45°（G）朝向 = F+1，不是 F-1**。批量交付前用二值轮廓 IoU 反查每行 F/G 实际视角并断言 `G == (F+1) % 8`；源模型已删时可用轮廓匹配从孤儿渲染目录反查归属。

## 交付四件套 + 质量门禁

- 目录：`model/ renders/ 提取流程.md 模型概况.html`；F/G 列单独另存别名文件。**每项目独立文档，禁止多项目合并**；概况 html 必须嵌该项目渲染图。
- **提取质量自验证（交付前必过）**：
  - 模型面数：交付口径以 OBJ/Blender 实测为准，格式头直读值只做初筛（FLVER 头与实测差约 45% 是正常）。
  - **GLB→OBJ 转换会略降计数，属正常**：Blender 导入/导出按位置去重顶点并丢弃退化三角。AC3R 实例 `10101_...Roof_15x9x8_02A_LOD0`：ATK 读出 verts 35,286 / faces 40,494；OBJ 实测 v 34,738 / f 40,452（-1.6% / -0.1%）。**差 1%～2% 不用查**；差 >10% 才说明解析或转换有真问题。
  - 贴图重组件：**输出体积必须逐字节等于理论 mip 链和**；解析出的几何必须过「mesh 表在文件内 + 面数为 3 的倍数」防垃圾值。
  - 渲染日志与 manifest 里中文路径按 GBK 乱码显示（`3D娓叉煋`）——渲染本身正常，但**不要拿 manifest 路径做后续定位**，改用 obj 内容 md5 直查。

## 几何质量体检（破面 / 缺面 / 面数达标）★ 有可复算脚本

用户问「多少个 10 万面、多少个破面缺面」时的标准答法。**目录里 `_geom_defects.py` 是可复用实现，直接抄**。

1. **直接解 GLB**（glTF JSON + BIN chunk，accessor 级 POSITION/indices），**按精确浮点位置合并顶点**，不经 Blender。
   - 为什么不用 OBJ：OBJ 已被 Blender 去重顶点、剔退化三角，计数与 ATK 源不同口径。
   - 为什么不用「量化到 1e-4」：实测与精确浮点几乎同结果（A 口径 1746 件 vs B 口径 1746 件），但精确值没争议。
2. **边界边** = 只被 1 个三角形使用的边；按共享顶点连成组件；组件边数 >2 面共用 = **非流形边**；共线/零面积 = **退化三角**。
3. **★ 最大的坑：独立四边形卡片会被全误报成破洞。**
   植被、线框（`GFX_WireFrame*`）、布料是大量**互不相连的单面四边形**，每个卡片自带 4 边闭合环。
   AC3R 实测：不排除卡片时「有破洞」= 1,575 件；**把「组件边数 ≤ 8」判为卡片并排除后 = 1,096 件**（差 479 件全是植被）。
   同样，用「闭合环」判据时必须要求**该组件所有顶点度数恰为 2**，否则会把单面壳体轮廓也算成洞。
4. **破洞大小用环长分档**（比面积稳，面积在非平面环上会被鞋带公式放大到 >包围盒面积的荒谬值——踩过）：
   AC3R 实测环长分布集中在 9~20，`≥6` 1,096 件 / `≥10` 1,062 / `≥16` 782 / `≥31` 335 / `≥101` 13。
5. **★ 第二个必踩的坑：开放边界会被当成破洞（比卡片坑更隐蔽）。**
   单面壳体（墙/屋顶/布料）与**切块地形/HLOD 瓦片**的边界边会连成一个**环绕整块的大闭合环**，
   它满足「顶点度=2 的闭合环」判据，于是整片地形被误判成"有破洞"。
6. **★★ 第三个坑（我在这上面连错两版）：破洞判定必须先过「已知答案合成件」自检，否则阈值是拍脑袋。**
   造 7 个答案已知的模型跑判据，**7 例必须全对**，否则判据不可用：
   完整立方体(0)、立方体缺 1 面(**1**)、立方体缺 2 个相对面(**2**)、立方体+独立卡片(0)、
   128×128 平面(0)、平面中间挖 2×2(**1**)、立方体每面独立顶点(0)。
   实测教训：用「环周长/包围盒对角线 ≤ 0.05 判洞」时，**"立方体缺一个面"被判成开放边界放过了**——
   最典型的破面当成了合格，方向是**假阴性/偏松**。阈值扫描显示只有 **0.8 ~ 1.0** 能同时过全部用例。
7. **定稿判据（三处缺一不可）**：
   - 卡片判定按**三角连通块大小**（三角数 < 3），**不是**按边界环边数
     ——"缺一面"的环正好 4 条边，按边数会被当卡片放过（我就这么错过）
   - 同一连通块内**周长最大的环 = 外围开放边界**（不计破面），**其余环一律计破洞**
   - 只有一个环的块：`环周长 / 包围盒对角线 > 0.8` 判开放边界，否则判破洞
   - 多环且最大环**不显著支配**（< 3 倍次大）→ 全部计破洞（对应"缺两个相对面"）
8. **初判 + 精修两段跑**：先用便宜的面数筛出 ≥10 万面候选（大文件几百 MB，全量重算十分钟级），
   再只对候选上完整判据。
9. **目视旁证**（必做，别只给数字）：把边界边按渲染视角做正交投影叠到白底图上（`_bnd_overlay.py`）；
   若给出"合格件"结论，还应对合格件 + 被判不合格的样本各渲一批做目检对照
   （合格件无可见缺口、不合格件能看到断缝/缺口）。**判据自检通过 ≠ 每个个体判定都对。**
10. **断缝假阳性要知道存在**：游戏资产常把长条结构拆件导出，两块视觉相接但位置差一点，
    接缝处即形成边界环 → 判成破洞。某一项通过率异常低（如 3%）时，首要怀疑它；
    另外哈希名（`81xxxxxx`）的件不排除是特效/技术网格而非角色模型。
11. **面数达标线要结合引擎结构说**：AC3R Boston 1,808 件里 **≥10 万面 = 0 件**（最大 59,364），
    因为它是建筑/道具模块化拆分（0~500 面占 50.6%）。**必须写明"这是资产组织方式决定的，不是提取漏件"**，
    否则会被当成提取失败。
12. **统计「达标件」必须先划清数据边界**：破面判定要读几何，所以**只有导出成 OBJ/GLB 的件才能判**。
    给数时要写清「本数只覆盖已导出产物」，并把只有面数台账（未导出）的库存单列，
    否则会把"没导出"误报成"不达标"。
13. AC3R 实测总账：闭合 94 / 卡片件 531 / 开放壳体无环 87 / 有破洞环 1,096（60.6%，共 11,279 环）/
    非流形边 240 / 退化三角 **0** / 完全干净 92。

## 面数口径与选品

- 单件 ≥10 万三角面为达标线；二次元/卡渲系整体降 T2（细节在贴图不在几何）；VR 游戏压 10 万面内属行业红线（Source 2 系）。
- **合并件口径要写清**：单件 vs 拼装（命运 2 实体含子件差一倍）、剔除项（HLOD 远景拼块/碰撞壳/水面特效）逐条注明。
- "包体大 ≠ 高模多"：先看引擎结构（模块化小件复用 vs 整张场景网格）再定预期。

## 资产落位规则

- E 盘 `3D渲染\<游戏>\` = 游戏逆向成果（model/renders/原素材/文档）；G 盘 `3D素材\公网高模库\` = 网络下载模型。两者不混。
- 原素材保全：解包产物中**最终资产**（模型源文件、贴图成品）拷入 `原素材*` 目录；纯容器/中间产物在核对无遗漏后删除。
